# feat-2-035 — 2차 대비 판례 도식화 (사실관계→쟁점→법조문→법리→포섭→결론)

> 목적: 2차 주관식이 **판례의 사실관계를 각색해 출제**된다는 현실에 맞춰, 판례를 답안 작성 순서 그대로 도식화해 제공한다.
> 성격: **설계 문서(계획).** 착수 승인 후 S0~S5 단계별 진행(각 단계 끝 하드스톱).
> 대상: **특허법 · 2005-01-01 이후 선고** 판례(운영 264건). **1차 샘플 = 2025년 14건.**
> ★사실관계는 **대법원이 아니라 하급심 판결문**에서 정리한다 — 자동 수집 우선, 실패분만 수기 투입(§4).
> 관련: [[feat-2-028 2차 전환 사다리]] · [[feat-2-029 판례 암기 사다리]] · [[feat-2-032 2차 논술 채점]].
> 작성일: 2026-08-19.

## 1. 배경 · Layer 1 판단

2차 답안은 **사실관계 포섭 → 쟁점 → 근거조문 → 법리 → 포섭 → 결론** 순서로 쓴다. 그런데 현재 판례 콘텐츠는
`summary_items`(쟁점별 요지) · `official_text_md`(원문) · `comment_body_md`(평석)로 **읽기용**이라, 학생이
답안 골격으로 옮기려면 매번 스스로 재구성해야 한다. 재구성 자체가 훈련이긴 하나(그건 feat-2-028 쟁점훈련이
담당), **정답 골격을 확인할 레퍼런스가 없다**는 게 빈 칸이다.

- YAGNI: 없이도 동작하나, 2차 대비 핵심 자산(판례)을 시험 출제형식에 맞춘 형태로 제공하는 건 spec 상 미충족 영역.
- KISS: 새 학습 러너를 만들지 않는다. **판례 뷰어/목록에 배지 + Sheet** 로만 붙인다(읽기 전용 레퍼런스).
- 기존 메커니즘 통합: 승인 파이프라인(`problem_review_status`) · Sheet UI · staff 편집화면 관례 ·
  PDF 텍스트 추출(`cases/lib/pdf-extract.server.ts`, mupdf) 을 그대로 재사용.

### 왜 `case_training_items` 확장이 아니라 새 테이블인가
`case_training_items` 는 **훈련 문항 행**(case XOR problem 소스, 1 판례에 N 행, 학생 응시 이력이 붙음)이다.
도식은 **판례 1건에 1개인 레퍼런스 산출물**로 축이 다르고 수명주기도 다르다(판례 본문이 고쳐지면 도식도 갱신).
훈련 테이블에 넣으면 "응시 대상이 아닌 행"이 섞여 학생 쿼리 가드가 또 하나 늘어난다(feat-2-028 Stage 1에서
이미 겪은 문제). → 분리.

## 2. 도식 구조 (원장 지정)

```
사실관계  ← 하급심 판결문 기준 (판례당 1개)
  ├─ [쟁점 1] → 법조문 → 법리 → 사안의 포섭 → 결론   ← 대법원 판결문 기준
  ├─ [쟁점 2] → 법조문 → 법리 → 사안의 포섭 → 결론
  └─ …
```

**★설계 결정 A — 쟁점 단위 블록 반복.** 사실관계만 판례 전체에 1개이고, 쟁점부터 결론까지는 쟁점마다 1세트다.
`cases.summary_items` 가 이미 쟁점 배열인 게 근거 — 쟁점 2~3개짜리 판결에서 법리·포섭·결론을 한 줄로 이으면
어느 쟁점의 결론인지 무너진다. (2025년 14건 실측: 쟁점 1개 5건 · 2개 5건 · 3개 4건.)

**★설계 결정 B — 소스 이원화.** 사실관계는 하급심, 나머지 5단은 대법원. 상고심은 법률심이라 사실관계를
"원심이 인정한 사실은 …" 로 압축해 버려 각색 출제의 원형이 되는 구체적 사실이 남지 않는다. 반대로 법리·결론의
권위는 대법원에 있다. 두 소스를 섞지 않고 **단계별로 나눠 귀속**시킨다.

**법리는 4축 분류**(원장 지정) — 각 축은 **선택(optional)**:

| 축 | key | 내용 |
|---|---|---|
| 문언적 해석 | `textual` | 조문 문언 자체에서 도출 |
| 취지의 해석 | `purpose` | 규정의 입법취지 |
| 목적의 해석 | `objective` | 법 전체의 목적(§1) 관점 |
| 형평성 고려 | `balance` | 타 규정과의 균형·체계 |

> ★한 판결이 네 축을 다 쓰는 일은 드물다. **없는 축은 비워 둔다** — 채우려 들면 없는 논거를 지어내게 되고,
> 그건 CLAUDE.md Non-negotiable 11 위반이다. 스키마가 축을 optional 로 두는 이유가 이것이다.

## 3. 데이터 모델 (S1)

```sql
create table public.case_diagrams (
  diagram_id    uuid primary key default gen_random_uuid(),
  case_id       uuid not null unique references public.cases(case_id) on delete cascade,
  facts_md      text not null default '',           -- 사실관계(각색 출제의 원형)
  facts_source_kind text not null default 'none',   -- 'lower_auto'|'lower_self'|'lower_manual'|'supreme_only'|'manual'|'none'
  facts_source_ref  text,                           -- "특허법원 2022허4635" 등 출처 표기
  facts_source_meta jsonb not null default '{}'::jsonb, -- {serial, file, fetchedAt} 재생성 추적
  blocks        jsonb not null default '[]'::jsonb, -- 쟁점 단위 블록 배열(아래 스키마)
  review_status public.problem_review_status not null default 'draft',
  generated_by  text not null default 'ai',         -- 'ai' | 'staff'
  approved_at   timestamptz, approved_by uuid references public.profiles(profile_id),
  rejected_reason text,
  created_by    uuid references public.profiles(profile_id),
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now(),
  deleted_at    timestamptz                          -- soft delete
);
```

`blocks[i]` (Zod 로 action 경계에서 검증, `app/features/cases/lib/case-diagram.ts` 에 단일 정의):

```ts
{
  issue: string;                 // 쟁점 (필수)
  statutes: string[];            // 법조문 — 표기 문자열 배열 ("특허법 제29조 제2항")
  doctrine: {                    // 법리 4축 — 각 축 optional(빈 문자열/미존재 허용)
    textual?: string; purpose?: string; objective?: string; balance?: string;
  };
  application: string;           // 사안의 포섭
  conclusion: string;            // 결론
}
```

- **v1 은 법조문을 텍스트로만 저장**(`articles` FK 링크 없음). 조문 링크는 이미 `article_case_links` 가 담당하고,
  도식 내부에서 다시 정규화하면 이중 소유가 된다. 필요해지면 별건.
- **하급심 판결문 전문은 DB 에 넣지 않는다** — 캐시 파일이 SSOT(§4.3), DB 에는 *정리된 사실관계 + 출처*만.
  저작물 전문을 학생 노출 경로에 올리지 않는다는 뜻이기도 하다.
- 테이블은 **과목 무관**. 특허·2005 는 *생성·노출 범위*이지 스키마 제약이 아니다(타과목 확장 대비).

**RLS**
- `select`: `review_status='approved' and deleted_at is null` → 전체 로그인 사용자. staff 는 전건.
- `insert/update/delete`: staff(instructor·admin)만. 쓰기는 요청 클라이언트 + action 게이트(adminClient 금지).

**인덱스**: `(case_id)` unique + 목록 필터용 `(review_status) where deleted_at is null`.

> 방식이라 크롤링 대상이 아님 ③ 무료 API 는 오래된 `허` 사건 상당수를 수록하지 않음.

### 4.1 자동 수집 경로 (1순위)

```
cases.official_text_md 의 【원심판결】 특허법원 2023. 6. 16. 선고 2022허4635 판결
  → 정규식 파싱 → 원심 사건번호 2022허4635
  → GET law.go.kr/DRF/lawSearch.do?OC=…&target=prec&type=JSON&nb=2022허4635   → 판례일련번호
  → GET law.go.kr/DRF/lawService.do?OC=…&target=prec&ID=<serial>&type=JSON    → 판례내용 전문
```

★`nb=` 파라미터가 사건번호 검색 키다. `query=` 는 **사건명** 검색이라 사건번호를 넣으면 0건이 나온다
(기존 메모 [[answer-grounding-rule]] 의 `search=1` 용법과 구분).

수집기 `scripts/case-diagram/fetch-lower-court.mjs` — 멱등·재시도·요청 간 120ms 대기, 결과를
`source/하급심 판결문/.cache/<대법원사건번호>.json` 에 캐시(재요청 방지). 리포트로
`확보 / 요지만(사실관계 없음) / 원심 미수록·불일치 / 원심 표기 없음` 4분류 목록을 출력한다.

**★자동 경로의 두 가지 안전장치**

1. **법원 검증.** 사건번호만으로는 판례가 유일하지 않다 — `허` 는 특허법원 전용이라 안전하지만
   `나`·`가합`·`라` 는 법원마다 같은 번호가 있다(서울고법 2008나68717 ≠ 부산고법 2008나68717).
   `【원심판결】` 에서 파싱한 법원명·선고일자를 API 응답과 대조해 불일치하면 **채택하지 않는다.**
   법원명은 `서울고등법원↔서울고법`, `대구지방법원↔대구지법` 을 같게 보도록 정규화(`normalizeCourt`).
   엉뚱한 사건의 사실관계에 그럴듯한 출처 캡션을 달아 주는 게 이 기능의 최악 실패다.
2. **"수록됨 ≠ 사실관계 있음".** law.go.kr 은 같은 사건이라도 판시사항·판결요지만 실린 레코드를
   주는 일이 있다(전문 3천 자 내외). 그건 도식의 사실관계 소스가 못 된다 → `hasFacts` 플래그로
   갈라 **보강 대상**으로 분류하고, 생성기는 `hasFacts` 인 캐시만 쓴다. 캐시 파일 자체는 남겨
   재요청을 막는다.

### 4.2 수기 투입 경로 (2순위 — 자동 실패분만)

자동 실패 목록만 원장이 채운다. 폴더·파일명 규약:

```
source/하급심 판결문/특허/
    2022후10814 특허법원 2021허4232.pdf
    2022다265123 특허법원 2022나1234.pdf
    2022다265123 서울중앙지법 2021가합5678.pdf     ← 심급 여러 개면 파일 여러 개(같은 접두어)
```

- **매칭 키 = 파일명의 첫 공백 앞 토큰 = 대법원 사건번호.** DB 의 유일한 안정 키라 이걸 쓴다.
  뒤 문구(법원·하급심 사건번호)가 그대로 `facts_source_ref` 가 된다.
- 같은 접두어 파일이 여러 개면 전부 읽어 합친다(1심+2심). 순서는 파일명 정렬.
- 허용 확장자 `.pdf`(텍스트 레이어 있는 것) · `.txt` · `.md`. 스캔 이미지 PDF 는 추출 결과가 빈 문자열이 되므로
  실패 목록에 남기고 넘어간다(OCR 은 범위 밖).
- `source/` 는 이미 운영 원본 자료 관례 폴더 → 이 폴더도 **.gitignore 등록**(저작물·대용량).
- **하위 폴더도 훑는다**(2026-08-21) — 원장이 "업로드 불가 모음" 처럼 묶어 두는 걸 그대로 받는다.
  파일명 규약만 맞으면 위치는 자유. 이 경로는 **4MB 상한이 없다** — 화면 업로드가 막히는 대용량은 여기로 온다.

#### ★PDF 추출 — 글자 좌표로 줄을 다시 세운다 (2026-08-21)

법원 판결문 PDF 는 본문·괄호·숫자를 **별도 텍스트 런**으로 그려 두는 경우가 많다. mupdf 의 기본 읽기
순서(`asText()`)를 그대로 쓰면 문장이 조각나고 숫자가 줄 끝으로 밀린다.

```
[전] 갑 제호증 5(9) … 2005. 9. 경 인터넷 에 게재된 에 관한 디자인으 로그 도면은 별지 의 사와 같다, 3‘’.
[후] 갑 제9호증   … 2005. 9.경 인터넷(https://…)에 게재된 ‘candle warmer’에 관한 디자인으로, 그 도면은 별지 3의 ‘사’와 같다.
```

★**사실관계는 날짜·등록번호가 그대로 남아야 하는 자료**다(2차가 이걸 각색해 출제한다). 조각난 텍스트를
AI 입력으로 쓰면 사실을 잘못 옮긴 채 승인 큐를 통과한다. `pdf-extract.server.ts` 가 글자별 좌표를
`baseline y → x` 로 정렬해 원래 줄을 복원한다 — **화면 업로드와 배치가 같은 SSOT 를 쓴다**(배치에 사본을
두면 배치만 조각난 텍스트를 캐시에 남긴다).

> **~~이미 조각난 채 적재된 8건은 재추출이 불가능하다~~** — 2026-08-26 해소. 원본 86개를 일괄

오분류되는 사고(2026-08-20)가 반복된다.

**★업로드 경로**(`/api/admin/lower-court-upload`)는 별도 리소스 라우트다 — mupdf(PDF 텍스트 추출)를
화면 모듈 그래프에 끌어들이지 않기 위함. 파일명 규약은 폴더 투입과 같고(`<대법원번호> <법원> <하급심번호>.pdf`),
앞 토큰을 떼어 출처 표기로 쓴다. 제약: **합계 4MB**(Vercel 서버리스 요청 본문 상한 4.5MB — 넘으면
액션에 닿기도 전에 잘린다), 스캔 PDF 는 추출 0자로 거부, `.txt`·`.md` 는 UTF-8 로 읽고 깨지면
**CP949 로 재시도**(한글 Windows 메모장 기본 인코딩 — 조용히 깨진 채 적재하면 소스가 통째로 못 쓰게 된다).
**★원본 파일 보관**(2026-08-24 추가). 예전에는 텍스트만 뽑고 원본 바이트를 버렸다("쓰는 쪽은
`body_text` 뿐"). 그래서 나중에 원본 PDF 가 필요해졌을 때 되찾을 방법이 전혀 없었다 —
2026다202753 원심 2023나11436 이 실사례다. 지금은 private 버킷 `case-lower-courts` 에 함께 보관하고
`case_lower_courts.files`(`[{name,path,size,mime}]`)로 가리킨다.

- Storage 키는 **ASCII 만**(`<case_id>/<stamp>-<n>.pdf`) — 한글 키는 서명 URL 단계에서 깨진다.
  한글 원본명은 `files[].name` 에만 두고 다운로드할 때 그 이름으로 내려 준다.
- 다운로드는 `/api/admin/cases/lower-court/:caseId/file?i=<n>` — staff 확인 후 **60초 서명 URL** 로 리다이렉트.
  버킷에 사용자 정책을 두지 않아 이 경로가 유일한 출구다.
- ★**본문을 갈아끼우면 원본을 지운다** — 전문 붙여넣기·자동 재수집은 `files` 를 비우고 Storage 객체도
  제거한다(`upsertLower` 한 곳에서). 본문과 어긋난 "원본"은 없느니만 못하다.
- **2026-08-24 이전 적재분에는 원본이 없었다**(수기 86건). 2026-08-26 에 원장이 원본 폴더를
  다시 확보해 일괄 보관 완료 — 84건 · 파일 86개(`source/판례데이터/특허_하급심판례`).
  ```bash
  npx tsx scripts/case-diagram/upload-lower-court-originals.ts          # 예행
  npx tsx scripts/case-diagram/upload-lower-court-originals.ts --apply
  ```
  파일명 stem 을 `source_ref` → 정규화 표기 → 하급심 사건번호 순으로 맞춘다(업로드 당시
  파일명이 그대로 `source_ref` 에 남아 있어 84/86 이 1차에서 붙는다). 경로는 case 당 고정
  `<case_id>/original-<n>.pdf` 라 재실행해도 파일이 쌓이지 않는다.
  - 검증: 텍스트 레이어가 있으면 추출 길이와 `char_count` 비를 본다(0.5~2 밖이면 경고).
    ★86개 전부 이 범위 안 — 다른 판결문이 섞여 들어오지 않았다는 뜻.
  - 스캔본 2개(`서울고등법원_2008나17757` · `서울중앙지방법원_98노8499`)는 추출 0자지만
    **원본으로는 보관한다**(업로드 화면과 다른 점 — 화면은 적재용이라 0자를 거부한다).
    같은 사건에 텍스트본이 따로 있어 본문은 그쪽에서 왔다.
  - **아직 원본이 없는 수기 적재분 2건**: `특허법원_2020허2758` · `수원지방법원_2018나1381`.

**★자동 수집분 PDF 생성**(2026-08-24). 자동 수집(`lower_auto` 111건)은 국가법령정보센터 API
텍스트라 내려받을 파일이 애초에 없다. **판례 전문 PDF 와 같은 규칙**으로 조판해 같은 버킷에
넣고 `files` 에 `kind:"generated"` 로 등록한다.

```bash
npx tsx scripts/case-diagram/build-lower-court-pdfs.ts            # 생성본 없는 것만
npx tsx scripts/case-diagram/build-lower-court-pdfs.ts --force    # 전체 재생성
npx tsx scripts/case-diagram/build-lower-court-pdfs.ts --all-kinds # lower_self 까지
```

- ★**조판 규칙은 `renderOfficialTextPdf` 하나뿐이다**(pdf-lib + NotoSerifKR TTF · A4 · 글자 단위
  wrap · 원문자 평문 대체). 사본을 만들지 않는다 — 판례 전문 PDF 와 다른 모양이 나오면
  그때부터 두 벌을 관리해야 한다.
- ★**미커버 정책도 그대로** — 폰트가 못 그리는 글자가 1자라도 있으면 그 건은 skip + 보고한다
  ("□ 로 조용히 내보내지 말 것").
- 자동 수집 본문은 문단이 이미 살아 있다(API 텍스트) — `reflowJudgmentText` 를 태우지 않는다.
  그건 **PDF 추출본**의 줄바꿈 깨짐을 되돌리는 용도이고, 문단 신호(들여쓰기)가 없는 API
  텍스트에 걸면 전체가 한 문단으로 뭉친다.
- 경로는 `<case_id>/generated.pdf` 고정 — 재생성해도 파일이 쌓이지 않는다.
- ★**재수집·붙여넣기 뒤에는 다시 돌려야 한다** — 본문이 바뀌면 `upsertLower` 가 생성본까지 지운다.

**★생성기의 2차 소스.** 화면에서 적재한 판결문은 로컬 캐시에 없으므로,
`draft-diagrams.mjs` 는 캐시가 없으면 `case_lower_courts`(status=`loaded`)를 읽는다.
이 연결이 없으면 화면에서 구해 넣은 판결문이 도식 생성에 반영되지 않는다.

### 4.3 귀속 규칙

| 상황 | `facts_source_kind` | 처리 |
|---|---|---|
| 판례 자체가 하급심(`cases.court <> 'supreme'`, 예: `2023나11078` 특허법원 판결) | `lower_self` | 자기 원문이 곧 하급심 — 원심을 찾지 않는다. **최우선 분기.** |
| API 자동 확보 | `lower_auto` | 하급심 전문에서 사실관계 정리. **기본 경로.** |
| 폴더 수기 투입 | `lower_manual` | 동일. 자동보다 우선(원장이 일부러 넣은 것) |
| 모두 실패 + 대법원 원문에 원심 인정사실이 실질적으로 있음 | `supreme_only` | 그 범위에서만 정리 + staff 목록에 **"하급심 보강 필요"** 표시 |
| 그 외 | `none` | 사실관계 비움. 도식은 쟁점~결론만으로 승인 가능 |

**사실관계는 지어내지 않는다.** 근거가 없으면 `none` 으로 비우고 도식을 반쪽으로 내보내는 편이,
그럴듯한 사실관계를 창작하는 것보다 안전하다(Non-negotiable 11).

학생 Sheet 의 사실관계 블록 하단에 **출처 캡션**(`특허법원 2022허4635`)을 단다. `supreme_only` 는
"대법원 판결문 기재 범위" 라고 밝힌다 — 사실관계가 얇은 이유를 학생이 알게.

### 5.0 ★인앱 초안과 배치 초안의 경계 (S2 에서 확정)

| | 만드는 것 | 근거 | 실행 위치 |

Vercel 서버리스에는 `source/하급심 판결문/.cache/` 가 없다(파일시스템은 `/tmp` 외 읽기 전용이고
`source/` 는 배포 대상도 아니다). 그래서 **인앱 초안은 사실관계를 만들지 않는다** — 대신 편집 화면에서
직접 쓰거나 배치가 채운다. 이 경계는 설계 §2 소스 이원화(사실관계=하급심 / 쟁점~결론=대법원)와 정확히
일치하므로, 제약을 우회한 게 아니라 원래 구조를 따른 것이다.

**근거 제한 — 이것이 이 기능의 안전장치다.**
1. 입력은 **그 판례의** 하급심 전문(§4) + `official_text_md` · `summary_body_md` · `summary_items` ·
   `comment_body_md` **뿐**. 일반 지식으로 메우지 않는다.
2. **사실관계는 하급심 전문에서만**, **쟁점·법조문·법리·포섭·결론은 대법원 원문에서만** 뽑는다(소스 이원화).
3. 근거를 못 찾은 해석 축은 **빈 채로 둔다**(모델에게 명시). 4축을 다 채우라고 요구하지 않는다.
4. 입력 텍스트에 없는 **사건번호를 인용하지 않는다**.
5. 생성물은 전부 `draft` — **원장 승인 전에는 학생에게 보이지 않는다**.

배치는 사실관계 소스를 넣기 전에 **조각 비율**을 잰다 — 구두점·숫자만 남은 3자 이하 줄의 비율.

```
실측 분포(loaded 261건): 0.00 에 240건 · 0.05 에 1건 ─── 빈 구간 ─── 0.20~0.39 에 20건
```

뚜렷한 이봉형이라 그 사이인 **0.15** 를 자른다(`SCRAMBLE_MAX`). 넘으면 그 건의 사실관계 소스를 버리고
`--with-facts` 로 제외한다. 쟁점~결론은 대법원 원문에서 오므로 영향이 없다.

★**조용히 넘기지 않는다** — 제외 건은 사건번호·출처·비율을 찍는다. 원본을 다시 받아 재추출하면 그대로
통과하므로, 무엇을 다시 받아야 하는지가 목록으로 남아야 한다.

## 10. 답안 쓰기 연습 (S6 — 계획, 2026-08-27 원장 요청)

> 요청: "쟁점별로 클릭하여 접었다 폈다 할 수 있게 하고, 쟁점별 **법리·사안의 포섭을 빈칸**으로 만들어
> 수험생이 작성하게 하라. 법리는 **축이 어긋나더라도 내용이 들어가 있으면 답으로 인정**하라.
> 결국 수험생이 주관식 답안을 쓸 수 있게 도와 달라."

### 10.1 Layer 1 판단 — 왜 새 러너를 만들지 않는가

도식은 이미 **답안 작성 순서 그대로**(사실관계 → 쟁점 → 법조문 → 법리 → 포섭 → 결론) 배열돼 있다.
답안 쓰기 훈련에 필요한 건 그중 **두 칸을 가리고 학생이 채우게 하는 것**뿐이다.
별도 러너(`/study/…`)를 새로 만들면 판례 뷰어와 도식이 두 벌이 되고, 학생은 같은 판례를 두 화면에서 봐야 한다.
→ **기존 도식 패널 안의 모드 전환**으로 붙인다(KISS · 기존 메커니즘 통합).

`case_training`(feat-2-028)과의 경계: 그쪽은 **쟁점을 스스로 찾는** 훈련이고, 이건 쟁점이 주어진 상태에서
**법리를 쓰는** 훈련이다. 사다리의 다음 칸이지 중복이 아니다.

### 10.2 화면

도식 패널 머리에 모드 전환 — **읽기 / 연습**. 선택은 `localStorage` 에 남는다(표시 방식 선택과 같은 관례).

```
[읽기] [연습]        ← 패널 상단

사실관계 · 경과 · 쟁점 · 법조문        ← 연습 모드에서도 그대로 보인다(문제지에 해당)
  ├ 2. 법리      [ 빈 칸 — 학생이 쓴다 ]
  └ 3. 사안의 포섭 [ 빈 칸 — 학생이 쓴다 ]
     결론                              ← 가린다(법리·포섭을 쓰기 전에 답을 보게 된다)
                    [ 맞춰보기 ]
```

- **법리는 축별 칸이 아니라 한 칸**이다. 4축으로 나눠 받으면 "축이 어긋나도 인정"이 성립할 수 없고,
  실제 답안도 축을 나눠 쓰지 않는다. 축은 채점할 때 **모범답안 쪽에서만** 쓴다.
- 「맞춰보기」를 누르면 그 자리에서 모범답안이 펼쳐지고 **아래에 나란히** 놓인다. 되돌리기 가능.
- 쟁점 접기/펴기(2026-08-27 반영 완료)와 맞물린다 — 쟁점 3개짜리 판례에서 한 쟁점씩 연습한다.

### 10.3 채점 — 핵심어 커버리지 (AI 없음)

**★Levenshtein(암기 모드)은 쓸 수 없다.** 조문 암기는 글자를 맞히는 일이지만 법리는 **바꿔 쓰는** 일이라,
정답을 제대로 쓴 답안도 편집거리로는 0.3 언저리가 나온다.

채택: **모범답안의 핵심어가 학생 답에 몇 % 담겼는가**(재현율형 — 학생이 더 길게 써도 감점 없음).
- 형태소 분석기 없이 조사·어미를 벗기고(`stem`), 불용어를 뺀 2자 이상 토큰을 핵심어로 본다.
- **축이 어긋나도 인정**: 채워진 축 각각을 **학생 답 전체**에 대고 맞춘다. 어느 축의 내용을 어디에 썼든
  글이 들어 있으면 그 축은 맞은 것이 된다. 축을 왜 나눠 두었는지는 모범답안을 펼칠 때 보인다.

**실측(2026-08-27, 승인 도식 2건으로 검증)** — UI 를 짓기 전에 지표부터 확인했다:

| 학생 답 | 침해금지·우려 | 손해액·한계이익 |
|---|---|---|
| 제대로 바꿔 쓴 답 | **0.73** | **0.74** |
| 일부만 쓴 답 | 0.20 | 0.17 |
| 엉뚱한 법리 | 0.07 | 0.04 |

성격이 전혀 다른 두 법리에서 값이 같은 자리에 떨어졌다 → 임계값을 고정으로 둘 수 있다.
**0.65 이상 인정 · 0.35~0.65 부분 · 미만 미흡.**

- 되돌려주는 것은 **모범답안 자신의 말**뿐이다 — 맞은 축 / 놓친 축 / **놓친 핵심어 목록**.
  AI 가 쓴 평은 넣지 않는다(Non-negotiable 11 · 응시마다 비용·지연).
- 놓친 핵심어는 그대로 뿌리면 "있고·때에·입은" 같은 찌꺼기가 섞인다 → 표시용 필터를 따로 두고 최대 8개.

| 일부만 | 0.10 | 0.11 | 0.09 |

**임계값을 따로 잡을 필요가 없었다 — 법리보다 오히려 높게 나온다.** 포섭은 사건 고유의
사실을 다루는 칸이라, 제대로 쓴 답이면 같은 고유명사·구성요소 번호를 쓸 수밖에 없기 때문이다.
법리와 같은 0.65/0.35 를 쓴다.

★다만 `dropFigures` 를 "숫자가 든 토큰 전부"로 잡았더니 **"제1항"·"제128조"까지 사라졌다**.
조문·청구항 번호는 제대로 쓴 답안이라면 당연히 들어가는 말이라, 빼면 채점이 헐거워진다.
