## 1. 무엇을 만드는가

도해특허법 유닛(94개)의 **표·본문 글자에 빈칸을 뚫어 낱말을 채우게 한다.**
빈칸이 되는 낱말은 **그 단원의 기출문제·정오문제에서 실제로 논의된 말**만 고른다.

**용도는 1차 객관식 대비다.** 2차 대비 학습모드(판례 도식 연습 feat-2-035 S6, 모범답안 연습
feat-2-036)와는 목적이 다르므로 채점 방식도 같지 않다 — 저쪽은 서술을 핵심어 커버리지로
재고, 이쪽은 **낱말 하나가 맞았는지 틀렸는지**를 본다(조문 빈칸과 같은 정오 판정).

### 유형의 뜻 (★확인 필요)

원장 지시문에 "유형 1, 유형 2, 유형 3(유형 1+유형 2)" 이라고만 있어 아래로 읽었다.
같은 문장이 근거로 드는 원천이 **기출문제**와 **정오문제** 둘뿐이고, 유형 3 을 "1+2" 로
정의한 것은 두 원천의 **합집합**을 뜻한다고 보았다(난이도 계층이라면 상위가 하위를 포함하므로
"1+2" 라는 표기 자체가 필요 없다).

| | 화면 이름 | 빈칸이 되는 말 |
|---|---|---|
| 유형 1 | **기출 유래** | 그 단원의 **기출문제**(past_exam·past_exam_variant) 본문·선지에 나온 말 |
| 유형 2 | **정오 유래** | 그 단원의 **정오문제(OX 지문)** 에 나온 말 |
| 유형 3 | **통합** | 유형 1 ∪ 유형 2 |

다르게 뜻하신 것이면 이 표만 고치면 되고, 아래 설계는 그대로 쓴다.

## 2. 먼저 재 보았다 — 말이 실제로 쓸 만한가

이 기능의 성패는 화면이 아니라 **뽑히는 낱말의 질**이다. 그래서 구현 전에
`scripts/dohae/probe-blank-terms.ts` 로 94유닛 전수를 돌렸다(저장 없음, 출력만).

### 원천 규모

| 항목 | 값 |
|---|---|
| 도해 유닛 | 94 (블록 633) |
| 특허 문제(승인·미삭제) | 1,173 — 기출 581 · 예상 592 |
| 선지 47,687 · 박스지문 1,583 | |
| 유닛당 기출 글 | 평균 10건 |
| 유닛당 OX 지문 | 평균 67건 · 중앙값 40 |
| 연결 문제가 아예 없는 유닛 | 4 |

문제는 **체계도 노드**로 붙는다 — `dohae_unit_nodes` → 그 노드의 **서브트리** →
`problems.primary_node_id`. 조문·판례·문제가 쓰는 규칙과 같다(정확일치로 두면 부모 노드에서
늘 0 이 된다).

★1차 대비 기능이라 **2차 주관식이 섞이지 않았는지 따로 확인했다** — `primary_node_id` 가
붙은 특허 문제는 전부 `mc_short`·`mc_case`·`mc_box`(객관식)다. 2차 주관식은 노드에
`problem_systematic_links` 로 복수 배치되므로([[subjective-node-mapping]]) 이 경로에
들어오지 않는다.

### 뽑는 방법과 그 이유

**말은 문제 쪽에서 모으고, 유닛 본문에서 찾는다.** 반대로 하면 안 된다 —
도해 표 칸은 「신규성」처럼 **조사 없이 낱말만** 들어 있어, 조사 기반 명사 추출
(`nounStem`, feat-2-030 S3c)이 유닛 본문에서는 거의 아무것도 못 잡는다. 문제 지문에는
조사가 붙으므로 거기서 어휘를 모으면 표 칸의 낱말도 그대로 걸린다.

거른 규칙 세 가지 — **전부 실측하다 나온 문제를 막은 것이다.**

1. **조사가 실제로 벗겨진 체언만.** 조사 없이 끝난 어절까지 담았더니 「공지된」·「반하여」·
   「받을」 같은 용언이 상위권에 올라오고, 같은 말이 「진보성 / 진보성이 / 진보성을」
   세 항목으로 갈라졌다.
2. **코퍼스 어딘가에 홀로 쓰인 적 있는 말만.** 조사를 벗기다 말이 잘린다 —
   「선출원주의」에서 `의` 를 떼면 **「선출원주」**. 같은 규칙이 「적용받」·「소급되」·
   「보정하」 같은 용언 토막도 함께 걸러 냈다.
3. **과목 전체에 두루 쓰이는 말은 뺀다.** 문서빈도 8%(두 글자 말은 2%) 상한.
   「발명」·「특허」·「경우」·「판단」은 빈칸이 되어도 답이 뻔하다.

점수 = (기출 등장 수 + OX 등장 수) × idf.

운영자가 화면에서 빼는 것으로 처리한다(§5).

### 유닛별 후보 수

| 후보 수 | 유닛 |
|---|---|
| 0 개 | **6** — 본문 글자가 없거나(전부 도해 이미지) 연결 문제가 없다 |
| 1~4 개 | 5 |
| 5~11 개 | 15 |
| 12~29 개 | 31 |
| 30 개 이상 | 37 |

평균 30개. **88/94 유닛에서 빈칸이 만들어진다.**

### ★유형 1 과 유형 2 는 많이 겹친다 (원장 판단 필요)

전 유닛 합계 — **기출만 127 · 정오만 1,016 · 둘 다 1,749**.

OX 지문이 기출 문제의 선지에서도 나오기 때문이다. 그래서 **어휘만 놓고 보면**
유형 1(1,876) ⊂ 대체로 유형 2(2,765) 이고, 유형 3(2,892)은 유형 2 보다 127개 많을 뿐이다.

그럼에도 **세 유형은 서로 다른 연습이 된다.** 한 번에 다 뚫지 않고 유닛당 상한을 두어
**유형 1 은 기출 등장 수로, 유형 2 는 OX 등장 수로 순위를 매기기** 때문이다 — 같은 어휘
풀에서도 뽑히는 12개가 달라진다. 유형 3 은 그 둘의 합집합(12~24칸)이다.

이 겹침이 뜻에 어긋난다면 유형의 정의를 바꿔야 하므로 §1 표와 함께 확인 부탁드린다.

## 3. 무엇을 빈칸으로 두지 않는가

- **조문 원문 박스** — 원장 지시("도해에서 조문은 이미 빈칸 모드가 있으니 만들 필요 없다").
  ★블록 JSON 에는 그대로 들어 있다(1칸짜리 표 + 본문이 `제N조`로 시작). 팝업이 렌더 때
  플랫폼 조문으로 갈아끼울 뿐이고, **그것도 유닛의 첫 박스 하나뿐**이다. 그러니
  "렌더에서 바뀌니까 괜찮다"고 두면 「조약의 효력」처럼 갈아끼움이 안 걸리는 유닛에서
  교재 조문 원문이 빈칸이 된다. **판정은 블록에서 직접 한다.**
- **소제목(`h`)** — `<summary>` 안에 그려진다(접기 머리). 입력 칸을 넣을 자리가 아니다.
- **도해 이미지**(`diagram` 블록, `diagram: true` 칸) — 글자가 없다.

## 4. 데이터 모델

### `dohae_blank_terms` (신규)

| 컬럼 | 뜻 |
|---|---|
| `term_id` uuid pk | |
| `unit_id` uuid → `dohae_units` on delete cascade | |
| `term` text | 빈칸이 될 말 |
| `from_exam` bool · `from_ox` bool | 유형 1 / 유형 2 소속 |
| `exam_count` int · `ox_count` int | 근거 건수(화면에 "기출 5 · 정오 23" 으로 보여 준다) |
| `score` numeric | 순위 |
| `excluded_at` timestamptz · `excluded_by` uuid | 운영자가 뺀 말 (지우지 않고 표시만) |
| unique `(unit_id, term)` | |

**좌표를 저장하지 않는다.** 어디에 놓일지는 렌더 때 본문에서 찾는다.

> ★조문 빈칸은 좌표(`block_index`/`cum_offset`)를 저장했다가 재직렬화 한 번에 96세트가
> 통째로 유실됐다(`blank-tiers-feat2030`). 도해는 본문이 운영자 편집으로도 바뀌고
> (`dohae-unit-editing`) 재파싱으로도 바뀐다 — 좌표를 들고 있으면 같은 사고가 난다.
> 말만 저장하면 본문이 바뀌어도 못 찾는 말이 조용히 빠질 뿐 다른 칸을 망가뜨리지 않는다.

재생성은 스크립트 `scripts/dohae/gen-blank-terms.ts`(멱등, dry-run 기본). 재시드로
`dohae_units` 가 지워지면 cascade 로 함께 날아가지만 **스크립트로 되만들 수 있으므로**
콘텐츠 손실이 아니다(유닛 편집분과 달리 사람이 쓴 것이 아니다).

RLS — **처음에는 읽기까지 staff 전용**으로 연다. 화면만 staff 로 막고 테이블을 전원에게
열면 검수 전 낱말이 PostgREST 로 그대로 나간다(★`problems` 가 RLS 로 draft 를 안 가려
같은 일을 겪었다 — `ox-panel-rls-and-fixes`). 학생 공개(§8 S5)와 **같은 단계에서**
SELECT 를 로그인 사용자 전원으로 넓힌다. 쓰기는 계속 staff.

**푸는 기록은 v1 에서 DB 에 넣지 않는다.** localStorage 초안만 둔다.
`user_blank_srs` 는 `article_blank_sets.set_id` 에 매인 구조라 그대로 못 쓰고,
`user_problem_attempts` 는 문제 풀이 신호라 여기에 섞으면 학습현황 지표가 오염된다
([[action-study-linkage]]). 기록·SRS 합류는 별건으로 남긴다(§8).

## 5. 화면

### 진입

도해 팝업(`DohaePopup`) 머리에 **「읽기 / 빈칸」** 전환을 둔다. 판례 도식 S6 과 같은 자리·같은 말.
빈칸을 켜면 **유형 1 · 유형 2 · 유형 3** 칩이 뜬다.

### 푸는 화면

- 본문·표 칸의 해당 낱말 자리에 입력 칸. **글자 수만큼 폭**(조문·판례 빈칸과 같다).
- **한 말은 유닛에서 처음 2회까지만 빈칸**, 나머지 출현은 글자 그대로 둔다.
  ★상한 12는 *말* 의 수이지 *칸* 의 수가 아니다 — t25 에서 「거절이유통지」는 23칸,
  「최후거절이유」는 20칸에 나온다. 출현마다 뚫으면 한 유닛에 입력 칸이 100개를 넘고,
  같은 답을 스무 번 치는 연습이 된다.
- **「맞춰보기」** 로 일괄 채점 — 맞으면 초록, 틀리면 빨강 + 정답 표시.
- 비워 둔 칸은 **채점에서 뺀다**(feat-2-036 과 같은 규칙 — 한두 칸만 연습한 학생이 손해 보지 않게).
- 채점은 `normalizeAnswer`(+`stripHanjaParen`) — 한자 병기 「고안(考案)」은 한글만 써도 정답.
- 초안은 `localStorage`(`dohaeBlank.<유형>.<unitId>`).
- **후보가 없는 유닛(6개)**: "이 항목은 연결된 기출·정오문제가 없어 빈칸을 만들 수 없습니다"
  — 빈칸 전환 자체를 비활성으로 둔다.

### 운영자

빈칸 모드에서 staff 에게만 각 칸 옆 **빼기** 버튼 — `excluded_at` 기록. 잡티(「일반적」·
「유무」)를 본문에서 보면서 바로 정리하는 것이 목록 화면을 따로 만드는 것보다 싸다.

### 손대지 않는 것

- **하이라이트·포스트잇 오버레이는 빈칸 모드에서 그리지 않는다.** 저장된 오프셋은
  컨테이너 전체 글자 기준이라(그래서 접기도 `<details>` 로 한다) 입력 칸이 글 흐름에
  들어가면 어긋난 자리에 그어진다. **저장값은 건드리지 않고 렌더만 멈춘다** — 읽기로
  돌아가면 그대로다.
- **유출방지 4겹**(워터마크·복사차단·인쇄숨김·고지)은 빈칸 모드에서도 그대로. 복사차단이
  선택을 막지 않으므로 입력에 지장 없다.

### 입력 방식 — 새로 만들지 않는다

`case-blank-fill-view.tsx` 의 `CaseBlankInput` 을 그대로 따른다: 칸마다 `<input>`,
`compositionStart/End` 가드, `pointerdown` 선행 flush, Enter 로만 다음 칸, 자동완성 차단 속성.

★V2(조문 빈칸의 단일 `contenteditable`)는 **가져오지 않는다.** 그것은 조문 본문 구조에
맞춰 명령형 DOM 으로 짠 것이고, 도해는 중첩 표까지 있어 다시 짜는 일이 된다. 대신
**iPad 실기 확인을 착수 조건이 아니라 완료 조건으로 명시한다**(§8 체크리스트) —
한글 IME 이월은 이 프로젝트에서 반복해 재발한 축이다([[blank-v2-ios-ime-carryover]]).

## 6. 공개 범위

**staff 전용으로 먼저 낸다.** 뽑히는 말의 질을 원장·강사가 실제 화면에서 보고 잡티를
빼신 뒤 학생에게 여는 것이 안전하다 — 자동 추출물이고, 잘못 뚫린 빈칸은 학생에게
"이게 중요한 말"이라는 잘못된 신호가 된다.

도해 본문 자체는 이미 학생 공개이므로(2026-08-23) 여는 것은 배선 한 줄이다.
판례 빈칸도 같은 순서를 밟았다(운영자 승인 데이터가 쌓인 뒤 특허법만 개방).

## 7. 3계층 게이트

**Layer 1 — 만들 것인가.** 원장 지시. 기존 것으로 대체 불가 — 조문 빈칸은 조문 원문에만
붙고, 도해의 비교표·요건 정리는 조문에 없는 편집물이다. 1차 객관식 대비 축에서 현재
빈칸이 걸리지 않는 유일한 콘텐츠다.

**Layer 2 — 어디에 두는가.**
- 말(persisted) / 위치(derived, 렌더 시 계산) / 입력(interaction, localStorage)을 섞지 않는다.
- 추출 규칙은 스크립트와 화면이 나눠 갖지 않는다 — **말은 스크립트가 정하고 화면은 찾기만** 한다.
- 유닛 텍스트 수집은 `dohae-edit.ts` 의 경로 규칙(`b3` / `b5.r0.c1`)을 그대로 쓴다.

**Layer 3 — 어떻게 쓰는가.** 순수 로직은 `app/features/dohae/lib/dohae-blanks.ts`
(말 찾기·겹침 해소·채점), 화면은 표시와 이벤트만. `any` 없음, 상수는 한곳.

## 8. 단계 (각 단계 끝에서 멈춘다)

| | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| **S1** | 순수 로직 `dohae-blanks.ts` + 단위 테스트 | 어절 경계 매칭·긴 말 우선·겹침 금지·**말당 2회 상한**·유닛당 말 상한이 테스트로 고정 |
| **S2** | DDL(`dohae_blank_terms` + RLS **staff 전용** + 인덱스) → `db:typegen` | 운영 적용, 타입 반영 |
| **S3** | 추출 스크립트 `gen-blank-terms.ts` (dry-run → `--commit`) | 94유닛 적재, 유닛별 후보 수 §2 와 일치 |
| **S4** | 팝업 빈칸 모드(읽기/빈칸 전환 · 유형 칩 · 채점 · 운영자 빼기) | staff 화면 동작 |
| **S5** | 원장 검수 → 잡티 정리 → **학생 공개 판단**(승인 시 RLS SELECT 확대) | 원장 결정 |

- [ ] 하이라이트·포스트잇: 빈칸 모드 진입·이탈 후 그어진 자리가 그대로인지

## 9. 안 하는 것 (지금은)

- **기록·SRS 합류** — `/study/srs` 큐에 도해 빈칸을 넣는 것. 저장 모델을 먼저 정해야 한다.
- **난이도 계층(하/중/상)** — feat-2-030 의 축과 유형 축을 겹치면 조합이 9가지가 된다.
- **다른 과목** — 도해는 특허법 단행본 하나뿐이다(`DOHAE_LAW_CODE`).
- **AI 로 말 고르기** — 규칙 추출로 §2 수준이 나온다. 운영자 빼기로 충분한지 먼저 본다.
