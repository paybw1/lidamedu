## 1. 무엇을 만드는가

도해특허법 유닛(94개)의 **표·본문 글자에 빈칸을 뚫어 낱말을 채우게 한다.**
빈칸이 되는 낱말은 **그 단원의 기출문제·정오문제에서 실제로 논의된 말**만 고른다.

**용도는 1차 객관식 대비다.** 2차 대비 학습모드(판례 도식 연습 feat-2-035 S6, 모범답안 연습
feat-2-036)와는 목적이 다르므로 채점 방식도 같지 않다 — 저쪽은 서술을 핵심어 커버리지로
재고, 이쪽은 **낱말 하나가 맞았는지 틀렸는지**를 본다(조문 빈칸과 같은 정오 판정).

### 유형의 뜻 (원장 확인 2026-09-04)

원장 지시문에 "유형 1, 유형 2, 유형 3(유형 1+유형 2)" 이라고만 있어 아래로 읽었다.
같은 문장이 근거로 드는 원천이 **기출문제**와 **정오문제** 둘뿐이고, 유형 3 을 "1+2" 로
정의한 것은 두 원천의 **합집합**을 뜻한다고 보았다(난이도 계층이라면 상위가 하위를 포함하므로
"1+2" 라는 표기 자체가 필요 없다).

| | 화면 이름 | 빈칸이 되는 말 |
|---|---|---|
| 유형 1 | **기출 유래** | 그 단원의 **기출문제**(past_exam·past_exam_variant) 본문·선지에 나온 말 |
| 유형 2 | **정오 유래** | 그 단원의 **정오문제(OX 지문)** 에 나온 말 |
| 유형 3 | **통합** | 유형 1 ∪ 유형 2 |

원장이 이 읽기가 맞다고 확인했다(2026-09-04).

## 2. 먼저 재 보았다 — 말이 실제로 쓸 만한가

이 기능의 성패는 화면이 아니라 **뽑히는 낱말의 질**이다. 그래서 구현 전에
`scripts/dohae/probe-blank-terms.ts` 로 94유닛 전수를 돌렸다(저장 없음, 출력만).

### 원천 규모

| 항목 | 값 |
|---|---|
| 도해 유닛 | 94 (블록 633) |
| 특허 문제(승인·미삭제) | 1,173 — 기출 581 · 예상 592 |
| 선지 47,687 · 박스지문 1,583 | |
| 유닛당 기출 글 | 평균 10건 |
| 유닛당 OX 지문 | 평균 67건 · 중앙값 40 |
| 연결 문제가 아예 없는 유닛 | 4 |

문제는 **체계도 노드**로 붙는다 — `dohae_unit_nodes` → 그 노드의 **서브트리** →
`problems.primary_node_id`. 조문·판례·문제가 쓰는 규칙과 같다(정확일치로 두면 부모 노드에서
늘 0 이 된다).

★1차 대비 기능이라 **2차 주관식이 섞이지 않았는지 따로 확인했다** — `primary_node_id` 가
붙은 특허 문제는 전부 `mc_short`·`mc_case`·`mc_box`(객관식)다. 2차 주관식은 노드에
`problem_systematic_links` 로 복수 배치되므로([[subjective-node-mapping]]) 이 경로에
들어오지 않는다.

### 뽑는 방법과 그 이유

**말은 문제 쪽에서 모으고, 유닛 본문에서 찾는다.** 반대로 하면 안 된다 —
도해 표 칸은 「신규성」처럼 **조사 없이 낱말만** 들어 있어, 조사 기반 명사 추출
(`nounStem`, feat-2-030 S3c)이 유닛 본문에서는 거의 아무것도 못 잡는다. 문제 지문에는
조사가 붙으므로 거기서 어휘를 모으면 표 칸의 낱말도 그대로 걸린다.

거른 규칙 세 가지 — **전부 실측하다 나온 문제를 막은 것이다.**

1. **조사가 실제로 벗겨진 체언만.** 조사 없이 끝난 어절까지 담았더니 「공지된」·「반하여」·
   「받을」 같은 용언이 상위권에 올라오고, 같은 말이 「진보성 / 진보성이 / 진보성을」
   세 항목으로 갈라졌다.
2. **코퍼스 어딘가에 홀로 쓰인 적 있는 말만.** 조사를 벗기다 말이 잘린다 —
   「선출원주의」에서 `의` 를 떼면 **「선출원주」**. 같은 규칙이 「적용받」·「소급되」·
   「보정하」 같은 용언 토막도 함께 걸러 냈다.
3. **과목 전체에 두루 쓰이는 말은 뺀다.** 문서빈도 8%(두 글자 말은 2%) 상한.
   「발명」·「특허」·「경우」·「판단」은 빈칸이 되어도 답이 뻔하다.

점수 = (기출 등장 수 + OX 등장 수) × idf.

### ★유형 1 과 유형 2 는 많이 겹친다 (원장 판단 필요)

전 유닛 합계 — **기출만 127 · 정오만 1,016 · 둘 다 1,749**.

유형 1(1,876) ⊂ 대체로 유형 2(2,765) 이고, 유형 3(2,892)은 유형 2 보다 127개 많을 뿐이다.

그럼에도 **세 유형은 서로 다른 연습이 된다** — 유형 1 은 기출에서 온 말만, 유형 2 는 OX 에서
온 말만 뚫기 때문이다. S6 이후 실측으로도 40.0 / 54.5 / 56.0칸으로 갈린다.

이 겹침이 뜻에 어긋난다면 유형의 정의를 바꿔야 하므로 §1 표와 함께 확인 부탁드린다.

## 3. 무엇을 빈칸으로 두지 않는가

- **조문 원문 박스** — 원장 지시("도해에서 조문은 이미 빈칸 모드가 있으니 만들 필요 없다").
  ★블록 JSON 에는 그대로 들어 있다(1칸짜리 표 + 본문이 `제N조`로 시작). 팝업이 렌더 때
  플랫폼 조문으로 갈아끼울 뿐이고, **그것도 유닛의 첫 박스 하나뿐**이다. 그러니
  "렌더에서 바뀌니까 괜찮다"고 두면 「조약의 효력」처럼 갈아끼움이 안 걸리는 유닛에서
  교재 조문 원문이 빈칸이 된다. **판정은 블록에서 직접 한다.**
- **소제목(`h`)** — `<summary>` 안에 그려진다(접기 머리). 입력 칸을 넣을 자리가 아니다.
- **도해 이미지**(`diagram` 블록, `diagram: true` 칸) — 글자가 없다.

## 4. 데이터 모델

### `dohae_blank_terms` (신규)

| 컬럼 | 뜻 |
|---|---|
| `term_id` uuid pk | |
| `unit_id` uuid → `dohae_units` on delete cascade | |
| `term` text | 빈칸이 될 말 |
| `from_exam` bool · `from_ox` bool | 유형 1 / 유형 2 소속 |
| `exam_count` int · `ox_count` int | 근거 건수(화면에 "기출 5 · 정오 23" 으로 보여 준다) |
| `score` numeric | 순위 |
| `excluded_at` timestamptz · `excluded_by` uuid | 운영자가 뺀 말 (지우지 않고 표시만) |
| unique `(unit_id, term)` | |

**좌표를 저장하지 않는다.** 어디에 놓일지는 렌더 때 본문에서 찾는다.

> ★조문 빈칸은 좌표(`block_index`/`cum_offset`)를 저장했다가 재직렬화 한 번에 96세트가
> 통째로 유실됐다(`blank-tiers-feat2030`). 도해는 본문이 운영자 편집으로도 바뀌고
> (`dohae-unit-editing`) 재파싱으로도 바뀐다 — 좌표를 들고 있으면 같은 사고가 난다.
> 말만 저장하면 본문이 바뀌어도 못 찾는 말이 조용히 빠질 뿐 다른 칸을 망가뜨리지 않는다.

재생성은 스크립트 `scripts/dohae/gen-blank-terms.ts`(멱등, dry-run 기본). 재시드로
`dohae_units` 가 지워지면 cascade 로 함께 날아가지만 **스크립트로 되만들 수 있으므로**
콘텐츠 손실이 아니다(유닛 편집분과 달리 사람이 쓴 것이 아니다).

RLS — **처음에는 읽기까지 staff 전용**으로 연다. 화면만 staff 로 막고 테이블을 전원에게
열면 검수 전 낱말이 PostgREST 로 그대로 나간다(★`problems` 가 RLS 로 draft 를 안 가려
같은 일을 겪었다 — `ox-panel-rls-and-fixes`). 학생 공개(§8 S5)와 **같은 단계에서**
SELECT 를 로그인 사용자 전원으로 넓힌다.

쓰기는 **UPDATE 만** staff 에게 연다 — 말을 만드는 것은 추출 스크립트(service_role)의 몫이고,
운영자가 화면에서 하는 일은 `excluded_at` 을 켜고 끄는 것뿐이다. INSERT/DELETE 정책은 없다.

★재생성 시 **`excluded_at` 은 보존해야 한다.** 나머지 컬럼은 스크립트 산출물이라 지웠다
다시 넣어도 되지만, 뺀 말은 사람의 판단이라 지우면 운영자가 같은 잡티를 또 빼야 한다.

**푸는 기록은 v1 에서 DB 에 넣지 않는다.** localStorage 초안만 둔다.
`user_blank_srs` 는 `article_blank_sets.set_id` 에 매인 구조라 그대로 못 쓰고,
`user_problem_attempts` 는 문제 풀이 신호라 여기에 섞으면 학습현황 지표가 오염된다
([[action-study-linkage]]). 기록·SRS 합류는 별건으로 남긴다(§8).

## 5. 화면

### 진입

도해 팝업(`DohaePopup`) 머리에 **「읽기 / 빈칸」** 전환을 둔다. 판례 도식 S6 과 같은 자리·같은 말.
빈칸을 켜면 **유형 1 · 유형 2 · 유형 3** 칩이 뜬다.

### 푸는 화면

- 본문·표 칸의 해당 낱말 자리에 입력 칸. **글자 수만큼 폭**(조문·판례 빈칸과 같다).
- **밀도는 「한 줄에 하나」**(40자 = 한 줄). 글조각(표 칸·문단)은 제 줄 수만큼 빈칸을 받는다.
- **한 말은 유닛에서 5회까지만** 빈칸, 나머지 출현은 글자 그대로 둔다.
  ★상한을 아주 풀면 t20 에서 「종업원」을 67번 치게 된다(실측). 연습이 아니라 노동이다.
- **말의 수에는 상한이 없다.** 예전엔 유형당 12개만 썼는데, 글조각이 유닛당 55개인데
  말 12개로 채우니 18칸에서 멈췄다(§12).
- **「맞춰보기」** 로 일괄 채점 — 맞으면 초록, 틀리면 빨강 + 정답 표시.
- 비워 둔 칸은 **채점에서 뺀다**(feat-2-036 과 같은 규칙 — 한두 칸만 연습한 학생이 손해 보지 않게).
- 채점은 `normalizeAnswer`(+`stripHanjaParen`) — 한자 병기 「고안(考案)」은 한글만 써도 정답.
- 초안은 `localStorage`(`dohaeBlank.<유형>.<unitId>`).
- **후보가 없는 유닛(6개)**: "이 항목은 연결된 기출·정오문제가 없어 빈칸을 만들 수 없습니다"
  — 빈칸 전환 자체를 비활성으로 둔다.

### 운영자

빈칸 모드 머리 띠 안에 staff 전용 **「말 관리」** — 지금 뚫린 말이 칩으로 나오고 `×` 로
뺀다(뺀 말은 점선 칩으로 남아 `↺` 로 되돌린다). 잡티를 본문에서 보면서 바로 정리하는
것이 목록 화면을 따로 만드는 것보다 싸다.

★칸마다 버튼을 붙이는 안은 접었다 — 입력 칸 옆이 어수선해지고, 지금 안 뚫린 말(뺐다가
되돌릴 말)은 본문에 나타나지 않아 어차피 한곳에 모아야 한다.

### 구현하며 붙은 규칙 (S4)

- **음영 라벨 칸은 빈칸이 걸리면 `KoreanLabel` 을 쓰지 않는다.** 그 컴포넌트는 글자를
  통째로 다시 조립해 입력 칸을 삼킨다.
- **속표가 끼어드는 자리를 가로지르는 말은 뚫지 않는다.** 화면이 글을 그 자리에서 쪼개
  그리므로 입력 칸을 놓을 데가 없고, 놓아 봐야 "안 쓴 칸"으로만 남는다(조문 빈칸에서
  미렌더 빈칸이 모수에 남던 것과 같은 함정). ★실데이터에서 이 규칙에 걸린 말은 **0개**
  였다 — 지금 있는 표에서 실제로 생긴 문제가 아니라 앞으로를 막는 빗장이다.
- **경로 규칙은 `dohae-edit.ts` 와 같다**(`b3` · `b5.r0.c1` · `b5.r0.c1.t0.r1.c0`).
  운영자 편집과 빈칸이 같은 좌표계를 쓴다.
- **빈칸 모드로 들어오면 접힌 절을 모두 편다.** 유닛은 로마숫자 소제목 단위로 처음에
  전부 접혀 있다(원장 지시 2026-08-22) — 그대로 두면 머리 띠만 보이고 입력 칸은 하나도
  없는데 「맞춰보기」가 "0/0 정답 (안 쓴 칸 19)" 를 내놓는다. **모드가 바뀔 때 한 번**만
  연다(`open` 속성으로 고정하면 사용자가 닫은 절이 다시 그릴 때마다 열린다).
- **값은 지금 배치에 있는 칸만 읽는다.** 유형을 바꾸면 빈칸 번호의 뜻이 달라지므로,
  ref 맵에 남은 앞 배치의 번호를 그대로 읽으면 엉뚱한 값이 초안·채점에 섞인다.

### 손대지 않는 것

- **하이라이트·포스트잇 오버레이는 빈칸 모드에서 그리지 않는다.** 저장된 오프셋은
  컨테이너 전체 글자 기준이라(그래서 접기도 `<details>` 로 한다) 입력 칸이 글 흐름에
  들어가면 어긋난 자리에 그어진다. **저장값은 건드리지 않고 렌더만 멈춘다** — 읽기로
  돌아가면 그대로다.
- **유출방지 4겹**(워터마크·복사차단·인쇄숨김·고지)은 빈칸 모드에서도 그대로. 복사차단이
  선택을 막지 않으므로 입력에 지장 없다.

### 입력 방식 — 새로 만들지 않는다

칸마다 `<input>` — 판례 빈칸(`CaseBlankInput`)과 같은 골격이되 **비제어**다.
채점이 「맞춰보기」 한 번이라 키 입력마다 판정할 일이 없고, 값을 state 로 되쓰면 타이핑마다
표 전체가 다시 그려진다.

| 붙인 것 | 왜 |
|---|---|
| `pointerdown` 선행 flush | 터치로 다른 칸을 바로 찍으면 iOS 가 조합 중인 글자를 그 칸으로 옮긴다. 이전 칸을 먼저 blur 해 조합을 거기서 끝낸다 |
| Enter = 다음 칸 (**blur → rAF focus**) | 한글 IME 가 확정한 마지막 음절을 조합 버퍼에 남겼다 새 칸으로 흘린다. 이전 칸에서 소진시킨 뒤 옮긴다 |
| `compositionStart/End` 가드 | 조합 확정 Enter 로 칸이 넘어가지 않게 |
| 입력 칸 key = `termId:start` | ★번호로 주면 유형을 바꿔 말이 달라져도 React 가 같은 자리의 칸을 재사용해 **앞 유형에서 친 답이 다른 말의 칸에 남는다**(비제어라 DOM 값이 그대로 산다) |
| 자동완성 차단 속성 | 조문·판례 빈칸과 동일 |

★V2(조문 빈칸의 단일 `contenteditable`)는 **가져오지 않는다.** 그것은 조문 본문 구조에
맞춰 명령형 DOM 으로 짠 것이고, 도해는 중첩 표까지 있어 다시 짜는 일이 된다. 대신
**iPad 실기 확인을 착수 조건이 아니라 완료 조건으로 명시한다**(§8 체크리스트) —
한글 IME 이월은 이 프로젝트에서 반복해 재발한 축이다([[blank-v2-ios-ime-carryover]]).

## 7. 3계층 게이트

**Layer 1 — 만들 것인가.** 원장 지시. 기존 것으로 대체 불가 — 조문 빈칸은 조문 원문에만
붙고, 도해의 비교표·요건 정리는 조문에 없는 편집물이다. 1차 객관식 대비 축에서 현재
빈칸이 걸리지 않는 유일한 콘텐츠다.

**Layer 2 — 어디에 두는가.**
- 말(persisted) / 위치(derived, 렌더 시 계산) / 입력(interaction, localStorage)을 섞지 않는다.
- 추출 규칙은 스크립트와 화면이 나눠 갖지 않는다 — **말은 스크립트가 정하고 화면은 찾기만** 한다.
- 유닛 텍스트 수집은 `dohae-edit.ts` 의 경로 규칙(`b3` / `b5.r0.c1`)을 그대로 쓴다.

**Layer 3 — 어떻게 쓰는가.** 순수 로직은 `app/features/dohae/lib/dohae-blanks.ts`
(말 찾기·겹침 해소·채점), 화면은 표시와 이벤트만. `any` 없음, 상수는 한곳.

## 11. S5 — 검수

검수는 `scripts/dohae/audit-blank-terms.ts` 가 돕는다. **사람이 판단할 것(법리·중요도)은
건드리지 않고**, 기계가 확실히 말할 수 있는 세 가지만 짚는다.

### 이미 고친 것 (기계 판정)

| | 전 | 후 |
|---|---|---|
| **③ 한 칸에 같은 말이 두 번** | 256건 | **0** |
| **문법 토막이 낱말로 섞임** | 「아니」·「하지」·「하여」·「본다」·「있기」 | 추출에서 제외(8종) |

- ③ 은 배치 규칙으로 고쳤다 — 유닛 상한 2 는 그대로 두되 **한 칸에는 한 번만**.
  같은 문장 안에서 같은 답을 두 번 치는 것은 연습이 아니다.
- 문법 토막은 `blank-term-extract.ts` 의 `FRAGMENTS` — 코퍼스에 홀로 쓰인 적이 있어
  ("…하여", "…본다") 기존 검사를 통과해 버렸다. **일반명사는 여기 넣지 않는다** —
  뺄지 말지가 사람 판단이라 `excluded_at` 으로 다룬다(추출을 다시 돌려도 보존).

이 둘을 반영한 뒤 실측: 유닛당 **유형1 13.7칸 · 유형2 16.2칸 · 유형3 18.1칸**
(한 칸 중복을 걷어낸 만큼 줄었다), 적재 **1,802행**.

### 원장 판단이 필요한 것 2건

**① 답이 화면에 그대로 있는 말 — 99건**
빈칸이 속한 절의 이름이나 유닛 제목에 같은 말이 있다. 예: t14 「신규성」(절 이름이
「신규성(法 29①각호)」) · t26 「분할출원」(유닛 제목) · t20 「직무발명」.
빼면 슬롯 하나를 다른 말에 쓸 수 있고, 두면 그 단원의 대표 개념이 남는다.

**② 두 글자 일반어 — 133종**
법률 용어(질권·기피·제척·항변·자백·송달·구술·불복·소급·취하·포기·승계…)와
일반어(의미·이하·견해·결론·관련·기타·단계·문제·분야·본문·원문·실체·성질·작성·
전부·조건·준비·차례·형식·형태·유무·각자·오전·복수)가 섞여 있다. 일반어만 골라
빼는 것은 사람이 정한다. **정해지면 추출 쪽 상수로 넣는다** — 유닛마다 하나씩 빼는
것보다 싸고, 다음 재생성에도 남는다.

### 학생 공개 (원장 승인 후)

두 줄이면 된다.

1. `dohae_blank_terms` 의 SELECT 정책을 `auth.uid() is not null` 로 (도해 본문과 같은 등급).
2. 팝업의 「빈칸」 전환 게이트에서 `viewerIsStaff` 조건을 뺀다

「말 관리」는 계속 `viewerIsStaff` 전용이다.

## 12. S6 — 「한 줄에 하나」로 밀도 재조정 (2026-09-05)

원장 지적: **양이 너무 적다.** 실측해 보니 상한을 잡고 있던 것은 배치 규칙이 아니라
**말의 수**였다.

- 유닛당 글조각(표 칸·문단) **54.7개** · 40자를 한 줄로 치면 **132줄**
- 후보로 뽑히는 말은 유닛당 **30.1개**인데 적재 상한 24 에 잘려 **19.2개**만 들어가 있었고,
- 화면은 거기서 다시 **유형당 12개**만 쓰고 **말당 2회**까지만 뚫었다 → **18.1칸**

즉 글조각이 55개인데 말 12개로 채우고 있었다.

### 규칙을 바꿔 재 본 것 (전 유닛 실측)

| 규칙 | 유닛당 칸 | 같은 답 최다 반복 |
|---|---|---|
| 지금(S5) | 18.1 | 2회 |
| 글조각당 1칸 · 말당 2회 | 19.4 | 2회 |
| 글조각당 1칸 · 말당 무제한 | 23.9 | **25회**(특허취소신청) |
| **줄당 1칸 · 말당 5회** | **64.5** | 5회 |
| 줄당 1칸 · 말당 8회 | 72.9 | 8회 |
| 줄당 1칸 · 말당 무제한 | 84.9 | **67회**(종업원 t20) |

**글조각 단위로는 안 된다** — 긴 문단이 한 칸만 받아 19.4칸에 그친다. 줄 단위여야 세 배가 넘는다.
반대로 반복 상한을 완전히 풀면 같은 답을 67번 치게 된다.

### 확정된 규칙

- **밀도 = 한 줄에 하나** (`LINE_CHARS = 40`, 글조각의 몫 = `ceil(글자수 / 40)`, 최소 1)
- **같은 말은 유닛에서 5회까지** (`MAX_HITS_PER_TERM`)
- **한 글조각에 같은 답은 한 번만** (S5 규칙 유지 — 감사 ③ 은 계속 0건)
- **말 수 상한 폐지** (`MAX_TERMS_PER_TYPE` 삭제) + **적재도 자르지 않음**(`headroom = Infinity`)
- ★상한에 걸린 말은 **건너뛰고 자리를 다음 말에게 넘긴다.** 멈추면 흔한 말이 앞에서 몫을
  다 쓴 글조각이 통째로 빈칸 없이 지나간다.

### 결과

적재 1,802 → **2,830행**(삭제 0 · 원장이 빼 둔 말 보존) · 배치 **유형1 40.0 · 유형2 54.5 · 유형3 56.0칸**.

감사(`audit-blank-terms.ts`)는 ③「한 칸에 두 번」 **0건**을 유지한다. 다만 뚫리는 말이 늘어
①답이 화면에 있다 99 → **154건**, ②두 글자 일반어 234 → **727건**으로 함께 늘었다 —
**원장 판단 대기 중인 두 항목이 그만큼 커졌다**(§11).
