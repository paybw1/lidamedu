# feat-14 — 운영 통합 고도화: 강의 · 학습 · 평가 · 컨설팅

> 작성 2026-09-01 · 상태 **제안(승인 대기)** · 코드 0 · DB 0
> 선행 자산: [[feat-7-040~049]] · [[feat-11-001~008]] · [[feat-8-028~030]] · `admin-ops-advancement` 로드맵

## 0. 한 줄 결론

**기능은 이미 다 있다. 병목은 가동(adoption)과 축 사이 연결이다.**

운영관리 화면은 26 클러스터 111 화면이고, LMS·커머스·컨설팅 파이프라인은 M4까지 완성돼 있다.
그런데 운영 DB 를 열어 보면 **학습 축만 살아 있고 나머지 축은 완성된 채 잠들어 있다.**
따라서 이 문서는 **새 기능을 늘리지 않는다.** 잠긴 것을 열고, 열린 것들을 하나의 사슬로 잇고,
사슬에 피가 돈 뒤에 관제 계기판을 다는 순서를 제안한다.

## 1. 진단 — 축별 스코어카드

측정 시점 2026-09-01, 운영 DB(mcgdoplo). 학생 지표는 전부 `role='student'` 로 걸러 staff 오염을 뺐다.

| 축 | 구축도 | 가동도 | 근거 숫자 |
|---|---|---|---|
| **학습** | ●●●●● | ●●●○○ | 문제 시도 **14,280** · Q&A 스레드 **6,454** · 학습 세션 578 · 즐겨찾기 615 |
| **평가** | ●●●●● | ●●○○○ | 플랫폼 모의 세션 **57** · **오프라인 시험 44건이 전부 draft, 응시 0** · GS 제출 4 |
| **강의** | ●●●●● | ●○○○○ | 코스 6 · **활성 수강권 2** · 시청 이벤트 **85** |
| **커머스** | ●●●●● | ●○○○○ | **결제 완료 주문 1** · 미결제 17 · 취소 11 · 활성 구독 5 |
| **컨설팅** | ●●●●○ | ●○○○○ | 월간 계획 **4** · 학습 기록 **14** · 상담 노트 **5** · 종합반 2반 11명 |

### 1.1 유입은 되는데 학습으로 안 넘어간다

| 구간 | 30일 | 전환 |
|---|---|---|
| 신규 가입(학생) | 85명 | — |
| 접속(학생) | 110명 | — |
| **문제 풀이(학생)** | **33명** | 접속 대비 **30%** |
| 주간 문제 풀이 | 12명 | |

접속자 110명 중 77명이 **들어와서 아무것도 풀지 않고 나간다.** 콘텐츠·기능 부족이 아니다
(문제·조문·판례·도해·Q&A 전부 있다). 들어온 사람을 첫 행동까지 데려가는 길이 약하다.

### 1.2 만들어 놓고 한 번도 안 쓴 것 — 오프라인 시험

**44건 전부 `draft`, 응시 결과 0건.** 배포 게이트(draft→published→closed)와 채점 그리드,
지필 결과의 학습 신호 합류(feat-7-042)까지 다 있는데 **published 로 넘어간 시험지가 하나도 없다.**
이건 기능 결함이 아니라 운영 루틴이 안 붙은 것이다. 이 문서의 문제의식을 가장 선명하게 보여 준다.

### 1.3 컨설팅 축은 파일럿에서 멈춤

종합반 2반 11명(등업 승인 8건). 진단·월간 계획·승인 RPC·일일 기록·타이머·격주 체크포인트가
feat-7-047/048 로 완성됐는데 **계획 4건 · 기록 14건**. 11명 중 실제로 루프를 도는 학생이 소수다.

### 1.4 권한 위생 — staff 계정 36개 중 실사용 6

| 항목 | 수 |
|---|---|
| staff 계정(admin 16 · manager 11 · instructor 9) | 36 |
| 최근 90일 로그인한 staff | **6** |
| 이메일에 test/example/e2e 포함 | **26** |

**운영자 권한 계정 30개가 90일간 로그인 없이 살아 있다.** 대부분 E2E·테스트 잔재로 보이지만,
`admin` 16개는 결제·회원 PII·hard delete 권한이다. 감사 알림(P1)을 붙여 놓고 문은 열어 둔 상태.

## 2. 이미 있는 것 — 다시 제안하면 안 되는 자산

아래는 **완료·배포됐다.** 고도화 방안에 이것들을 다시 넣지 않는다.

**운영관리 기반**
- 허브 경영 KPI 밴드 · 워크큐 8종 타일 · 감사 로그(파괴적 작업 전수) · 커머스 CSV 내보내기 (P0)
- IA 5섹션 재설계 · 역할 맞춤 사이드바 · 운영자 화면 검색 팔레트 (IA P0)
- 중앙 RBAC 방어선(`/admin/*` 레이아웃 가드 + `admin-guard.server` SSOT) · duty 기반 담당자 라우팅
- 결제 실패 dunning(백오프·유예·lapse) · 세그먼트 대량 메시징 · 체험→유료 전환 추적
- 회원 CRM 10탭(`/admin/students/:id`) · 발송 로그(`message_send_logs` 372건) · 운영자 '내 활동' 발신함

**축별 엔진**
- 학습: 문제·조문·판례·도해·SRS·빈칸 3단계·게임화. 신호 backbone = `user_problem_attempts` 단일 테이블
- 평가: 플랫폼 모의 · 오프라인 시험(배포 게이트·채점 그리드·SRS 합류) · GS · 2차 논술 3단계 훈련
- 강의: LMS M1~M4 전부(콘텐츠 라이브러리·콜러스 동기화·재생 횟수 제한·강의실·주문/부분환불/무통장/도서몰)
- 컨설팅: 진단 → 월간 계획 → 승인 RPC → 일일 기록 → 타이머 → 체크포인트 → 공부 통계
- 연계: 약점→과제(개인·조망·반공통 3곳) · 과제 이행 표시 · 신호→상담 루프 · 모의 구분 뷰·점수 스냅샷

## 3. 고도화 방안 — 가동 → 연결 → 관제

순서가 핵심이다. **매출이 0인 상태에서 MRR 대시보드를 만들면 0을 예쁘게 보여 주는 화면이 생길 뿐이다.**

```
 1단계 가동            2단계 연결              3단계 관제
 (잠긴 것을 연다)      (축을 사슬로 잇는다)    (사슬에 계기판을 단다)
      │                      │                       │
 강의 오픈 게이트       여정 상태 SSOT          매출·이연·마진
 학습 첫 행동           시청→파악 합류          PG 대사 · 정산 지급
 시험 배포 루틴         평가→컨설팅 표준화      4-eyes 승인
 컨설팅 확대 조건       등급 단일화             크로스반 헬스
```

---

### 1단계 — 가동 (지금 해야 하는 것)

#### G1. 강의 플랫폼 오픈 게이트 닫기

막고 있는 것은 **코드가 아니라 다섯 개의 외부 의존**이다. 전부 이미 식별돼 있다.

| # | 항목 | 성격 | 담당 |
|---|---|---|---|
| 1 | `ENFORCE_DEVICE = ON` | 벤더 fingerprint 규격 확정 대기 | 콜러스 |
| 2 | `watch_events` 영구보존 법적 근거 | 개인정보 처리방침 반영 | 법무 |
| 3 | T-PASS ↔ 신판 코스 연결 절차 | 운영 절차 확정 | 원장 |
| 4 | 토스·카카오 **라이브 키** 교체 | 테스트 검증은 완료 | 원장 |
| 5 | dunning 라이브 청구 실동작 | 결제 가동 후 1회 검증 | 개발 |

**규모: 개발 소(小).** 대부분 스위치·키 교체다. 1~3은 개발이 할 수 없다.
→ **원장 결정이 필요한 첫 항목.** 이게 안 열리면 커머스·강의 축의 나머지 제안은 전부 공회전이다.

#### G2. 학습 첫 행동까지 데려가기 (접속 110 → 풀이 33 개선)

이미 있는 것: 다음 행동 카드 · 이용 가이드 허브 · 조문 연결 배지.
**빠진 것: 처음 들어온 사람에게 "지금 이거 하세요" 가 한 개로 좁혀지지 않는다.**

- **첫 7일 온보딩 트랙** — 가입 직후 7일간 대시보드 최상단을 "오늘의 한 가지"로 고정
  (1일 과목 고르기 → 2일 조문 10개 → 3일 문제 10개 → …). 완료 시 다음 단계 해금.
  재사용: 다음 행동 카드 · 가이드 허브 · 게임화 스트릭. **신규 테이블 없음**(진척은 기존 신호에서 파생).
- **이탈 복귀 훅** — 가입 후 3일 무행동 학생에게 인앱+이메일 1회.
  재사용: 세그먼트 대량 메시징(`/admin/broadcasts`) 에 세그먼트 1종 추가. **규모 소.**

**측정 지표: 접속→첫 풀이 전환율 30% → 50%.** 이 숫자 하나로 성패를 판정한다.

#### G3. 오프라인 시험 배포 루틴 붙이기

44건이 draft 로 잠들어 있는 게 가장 값싼 개선 기회다. 기능은 다 있다.

- 반 상세에 **"이번 주 시험" 카드** — draft 시험지 목록 + [배포] 원클릭. 워크큐에도 타일 1개.
- 배포 시 학생에게 알림(기존 kinds 재사용), 마감 후 채점 그리드로 직행.

재사용: `offline_tests` 배포 게이트 · 워크큐 타일 패턴 · 알림 kinds. **규모 소.**

#### G4. 컨설팅 파일럿 확대 조건 확정

11명 중 계획 4건. 확대 전에 **왜 안 도는지**를 먼저 봐야 한다.

- 반 상세에 **컨설팅 루프 이행판** — 학생별 (진단 / 이번달 계획 / 이번주 기록 / 마지막 상담) 4칸 신호등.
  빈칸이 곧 할 일이고, 그 자리에서 대신 제출·상담 코멘트로 넘어간다.
- 재사용: 상담자 계획 직접 편집(feat-7-048 B) · 신호→상담 인라인 코멘트(연계 P2) · `getLastConsultedDates`.
  **규모 중(中).** 새 데이터 없음, 기존 조회의 재배열.

#### G5. staff 계정 정리 (권한 위생)

- 90일 무로그인 staff 계정 감사 → 테스트 계정 회수, 실사용자만 남긴다.
- `admin` 16 → 실제 필요한 수로. **역할 enum 은 건드리지 않는다**(duty 패턴 유지).
- 재사용: 감사 로그 · `alertSecurityEvent`. **규모 소.**

### 2단계 — 연결 (사슬 만들기)

여기가 **강의-학습-평가-컨설팅을 하나의 제품으로 만드는** 지점이다.

#### C1. ★ 학생 여정 상태 — 단 하나의 구조 제안

지금은 학생의 상태가 다섯 군데에 흩어져 있다:
`getMembershipAccess`(등급) · `cohort_members`(반) · `enrollments`(강의) · `user_subscriptions`(구독) ·
`user_problem_attempts`(활동). 화면마다 "이 학생이 지금 어느 단계인가" 를 제각기 다시 계산한다.

**제안: 여정 상태를 파생 SSOT 하나로 정의한다.**

```
가입 → 체험 → 수강(강의 구매) → 반(종합반 배정) → 응시 → 합격
```

- **새 테이블을 만들지 않는다.** 기존 신호에서 파생하는 함수 하나(`getStudentJourney`)로 시작한다.
  — 캐싱이 필요해지면 그때 materialized view 를 얹는다(성급한 테이블 신설 금지).
- 각 단계에 **머문 기간**과 **다음 단계로 넘어가는 조건**을 함께 반환한다.
- 이 함수 하나가 다음을 동시에 먹여 살린다:
  - 학생 CRM 헤더(지금은 탭마다 흩어져 있음)
  - 체험→유료 전환 추적(이미 있음 — 같은 정의를 쓰게 통일)
  - 세그먼트 메시징(세그먼트 = 여정 단계 + 체류 기간)
  - 이탈 경보(단계별 정체 = at-risk 의 상위 개념)

**이것이 네 축을 하나로 묶는 핵심이다.** 강의는 '수강' 단계, 평가는 '응시' 단계, 컨설팅은 '반' 단계의
개입 수단이 되고, 지금처럼 각자 다른 화면에 사는 별개 제품이 아니게 된다.

재사용: `getMembershipAccess` · `trial-conversion.server` · `cohort_members` · `getAtRiskStudents`.
**규모 중.** 파생 함수 1개 + 기존 화면 3곳 배선.

#### C2. 시청 데이터 → 파악 레이어 합류

지금 파악 레이어(학습현황·at-risk·반 통계)의 신호는 `user_problem_attempts` 뿐이다.
**강의를 틀어 놓고 문제를 안 푸는 학생은 "미활동" 으로 보인다.** 강의가 가동되면 즉시 문제가 된다.

- `watch_events`/`lesson_completions` 를 학습현황의 활동 신호에 합류(문제 시도와 **별도 축**으로 병기).
- 진도 = 강의 진도 + 문제 진도 두 줄로. 하나로 합치지 않는다(의미가 다르다).

재사용: `getLessonProgressForUser` · `admin-cohort-monitoring` 조회. **규모 중.** G1 이후에만 의미 있음.

#### C3. 평가 결과 → 컨설팅 재료 표준화

지금도 시험 결과는 `user_problem_attempts` 로 합류한다(backbone 견고). 빠진 건 **상담 재료로서의 형태**다.

- 상담 화면에서 "이 학생 최근 평가 3건 요약"(모의·오프라인·GS 를 한 축에) 카드.
- 약점 단원 → 이미 있는 약점→과제 CTA 로 직결(3곳 완비 — 상담 화면에만 없다).

재사용: `listStudentMockSessions` · `getNodeMastery` · `selectProblemsForWeakNodes`. **규모 소.**

#### C4. 회원 등급 단일화

`getMembershipAccess`(체험/무료/자기학습/종합반) 와 강의 `enrollments`·`user_subscriptions` 가 별개 축이다.
강의를 산 학생의 등급이 무엇인지 한 곳에서 답할 수 있어야 한다. C1 의 여정 상태에 흡수시킨다.

**규모 중.** C1 의 하위 작업.

### 3단계 — 관제 (매출이 흐른 뒤)

**전제: 1단계 G1 이 열려 실제 결제가 발생한 뒤.** 그 전에 착수하면 0 위의 대시보드다.

- **MRR · 이연매출 · 마진** — 구독/강의/도서 혼합 인식 기준 확정 필요(회계 판단).
- **PG 대사 큐** — 토스 정산 내역 ↔ `payments`/`orders` 대사, 불일치만 큐로.
- **정산 지급 실행 · 명세 · 분쟁** — 현재는 계산까지만. 지급 실행은 별도.
- **4-eyes 승인** — 환불·수강권 회수·hard delete 등 파괴적 작업에 2인 승인.
- **크로스반 헬스 · 360 타임라인 · 재참여 자동화** — C1 여정 상태가 선행돼야 의미가 생긴다.

**규모 대(大).** 이 단계는 별도 승인 대상으로 남긴다.
