# feat-14 — 운영 고도화: 사슬의 한 토막만 열린 상태에서 무엇에 투자할 것인가

> 작성 2026-09-01 · **2차 개정**(전제 두 번 정정) · 상태 **제안(승인 대기)** · 코드 0 · DB 0
> 선행 자산: feat-7-040~049 · feat-11-001~008 · feat-8-028~030 · `admin-ops-advancement` 로드맵

## 0. 전제 — 이 문서가 두 번 고쳐 쓴 이유

초판에서 두 가지를 틀리게 봤다. 기록으로 남긴다.

| 초판의 오독 | 실제 |
|---|---|
| 강의·커머스 지표가 낮다 → **병목** | 내년을 준비하며 **의도적으로 잠근 것**. 낮은 게 계획대로다 |
| 학습 플랫폼 활성도 30% → **개선해야 할 결함** | 학습 플랫폼도 **사슬의 한 토막**일 뿐. 부분만 열린 상태에서 원활한 운영은 구조적으로 어렵다 |

**목표 그림은 강의 → 학습 → 평가 → 컨설팅의 사슬이고, 지금은 가운데 한 토막만 열려 있다.**

사슬이 붙으면 학생은 *강의를 사서* 들어오고, *배운 것을 학습 플랫폼에서* 굳히고,
*평가로* 확인하고, *컨설팅으로* 교정한다. 지금은 그 앞뒤가 없으니
"들어와서 왜 문제를 풀어야 하는지" 를 학생 스스로 만들어야 한다. 활성도가 낮은 건 그 결과다.

**그래서 이 문서의 질문은 "지금 지표를 어떻게 올릴까" 가 아니다.**

> **사슬이 다 붙었을 때 버려지지 않을 것은 무엇이고, 그중 지금 해야만 하는 것은 무엇인가.**

---

## 1. 실태 — 숫자를 지표가 아니라 배경으로 읽는다

### 1.1 처리 큐는 깨끗하다

| 큐 | 미처리 |
|---|---|
| Q&A 미답변 | 4 |
| 오류신고 미처리 | 3 |
| 고객문의 미처리 | 2 |
| 회원 승인 대기 | 2 |
| 등업 대기 | 0 |

운영관리 워크큐(P0·P1)가 제 몫을 하고 있다. **"할 일이 쌓인다" 는 문제는 없다** —
운영관리를 이 방향으로 더 밀 이유가 없다.

### 1.2 지금 실제로 소모되는 자원은 콘텐츠 쪽이다

| 부하 | 규모 |
|---|---|
| 판례 도식 | draft **40** / 승인 219 |
| 문제 | draft 12 / 승인 **3,199** |
| 오류신고 유입 | **월 35건**(Q&A 25건보다 많다) |

지난 한 달의 실제 작업(판례해설 권호 정정 103건 · 도식 생성 14건 · 심급 배지 254건 ·
빈칸 Enter 버그 · O/X 표시 교정 500건)이 **전부 여기에 속한다.**

### 1.3 활성도는 지금 판정할 지표가 아니다

30일, `role='student'` 한정: 신규 85 · 접속 110 · **문제 풀이 33(30%)** · 주간 12.

이 숫자를 **성과로 읽지 않는다.** 학생이 지금 여기에 오는 이유는 학원이 만든 게 아니라
학생이 스스로 만든 것이고(강의 수강 관계가 없다), 그 상태의 30% 는 오히려 자연스럽다.
**참고선으로만 남기고, 사슬이 붙은 뒤 다시 잰다.**

### 1.4 위생 하나 — staff 계정

staff 36개 중 최근 90일 로그인 **6개**, test/e2e 이메일 **26개**, 그중 `admin` 16개
(결제·PII·hard delete 권한). 내년 커머스가 열리기 전에 정리돼야 한다.

## 2. 판단 기준 — 버려지는 것 / 남는 것

지금 무엇에 손대야 하는지는 **사슬이 붙었을 때 그것이 살아남는가**로 가른다.

| 지금 만들면 | 사슬이 붙은 뒤 |
|---|---|
| 학습 플랫폼 단독 온보딩·리텐션 장치 | ❌ **다시 설계해야 한다** — 유입 동기가 강의로 바뀌면 첫 화면의 전제가 통째로 달라진다 |
| 활성도 캠페인·복귀 훅 | ❌ 대상 정의(누가·언제)가 수강 관계 기준으로 바뀐다 |
| **콘텐츠 자산과 그 제작·검수 처리량** | ✅ **네 축 모두의 원재료다.** 강의도 평가도 컨설팅도 같은 문제·조문·판례·도식을 쓴다 |
| **콘텐츠 품질을 지키는 루프**(신고→수정→회신) | ✅ 학생이 늘수록 값이 커진다 |
| **학생 여정 상태 정의** | ✅ '수강' 단계를 한 칸 끼우면 그대로 확장된다 |
| **외부 의존 리드타임**(벤더·법무·절차) | ✅ 지금 시작해야 내년에 열린다 |

**결론: 지금은 활성화가 아니라 원재료와 뼈대에 투자한다.**

## 3. 이미 있는 것 — 다시 제안하지 않는다

**운영관리 기반(완료·배포)**: 허브 KPI 밴드 · 워크큐 8종 · 감사 로그 전수 · 커머스 CSV ·
IA 5섹션 재설계 · 역할 맞춤 사이드바 · 운영자 화면 검색 · 중앙 RBAC 방어선 · duty 라우팅 ·
dunning · 세그먼트 메시징 · 체험전환 추적 · 회원 CRM 10탭 · 발송 로그 · 운영자 '내 활동' 발신함.

**축별 엔진(완료·배포)**: 학습 · 평가(모의·오프라인 시험·GS·2차 논술 3단계) ·
강의(LMS M1~M4 전부) · 컨설팅(진단→계획→승인→기록→타이머) · 연계(약점→과제 3곳·상담 루프).

## 4. 방안 — 지금 할 세 가지 + 내년 준비

### N1. 콘텐츠 제작·검수 처리량 ★ 최우선

**이유: 네 축 전부의 원재료이고, 사슬이 붙어도 버려지지 않는 유일한 대규모 투자처다.**
지금 도식 40건이 draft 로 쌓인 건 검수가 화면 왕복이라서다.

- **검수 큐 화면** — 도식·문제·해설을 한 줄씩 훑으며 승인/반려(키보드 이동, 한 화면에서 판정).
  지금은 목록 → 개별 편집 화면 왕복.
- **감사 결과를 큐의 정렬 키로** — `audit-diagrams` WARN(법리 축 0개 등)·`audit-essay-answers` FAIL 을
  위로 올린다. 사람이 볼 것만 사람이 본다.
- **정정 도구의 일상화** — `/admin/tools/find-replace` 는 이미 있다. 감사 스크립트 결과를
  화면에서 바로 볼 수 있게 이어 붙인다(지금은 개발자가 터미널에서 돌린다).
- 재사용: 감사 스크립트 · `review_status` 전이 · 패널 인라인 편집 · find-replace.
- **규모 중.** **판정 지표: 도식 draft 40 → 10 이하 유지.**

### N2. 오류신고 루프 (월 35건 — 유입 1위)

콘텐츠 품질을 지키는 장치다. 학생이 늘수록 값이 커진다.

- **신고 ↔ 처리 연결** — 담당자·처리 메모·관련 화면을 기록에 남긴다.
  지금은 `resolution_note` 하나뿐이고 **답변자 귀속 필드가 없다**(운영자 '내 활동'에서도 상태만 보인다).
- **같은 신고 묶기** — 월 35건 중 상당수가 같은 화면·같은 원인. 화면 URL 기준 묶어 보기.
- **처리 기간 측정 시작** — 지금은 재지 않는다.
- 재사용: `bug_reports` · '내 활동' · duty 알림. **규모 소~중.**

### N3. 학생 여정 상태 — 사슬의 뼈대 (유일한 구조 제안)

학생 상태가 다섯 군데에 흩어져 있다 — `getMembershipAccess`(등급) · `cohort_members`(반) ·
`enrollments`(강의) · `user_subscriptions`(구독) · `user_problem_attempts`(활동).
화면마다 "이 학생이 어느 단계인가" 를 제각기 다시 계산한다.

```
지금:   가입 → 활성 → 학습 지속 → 반 → 응시 → 합격
내년:   가입 → 활성 → [수강] → 학습 지속 → 반 → 응시 → 합격
                       └ 한 칸 끼우면 강의·평가·컨설팅이 같은 축 위에 올라온다
```

- **새 테이블을 만들지 않는다.** 파생 함수 `getStudentJourney` 하나로 시작(캐싱은 필요해질 때 뷰).
- 각 단계의 **체류 기간**과 **다음 단계 조건**을 함께 반환.
- 지금 먹여 살리는 것: 회원 CRM 헤더(탭마다 흩어짐) · 세그먼트 정의 · at-risk 의 상위 개념.
- 내년에 얻는 것: **네 축 통합이 새 설계가 아니라 확장이 된다.**
- 재사용: `getMembershipAccess` · `trial-conversion.server` · `cohort_members` · `getAtRiskStudents`.
- **규모 중.**

### N4. 내년 준비 — 리드타임만 확정 (개발 없음)

내년 오픈을 막는 것은 코드가 아니라 **외부 의존의 리드타임**이다.

| # | 항목 | 담당 | 왜 지금 시작해야 하나 |
|---|---|---|---|
| 1 | 콜러스 기기 fingerprint → `ENFORCE_DEVICE` ON | 벤더 | 벤더 응답 주기가 길다. 없으면 계정 공유를 못 막는다 |
| 2 | `watch_events` 보존 근거 → 처리방침 개정 | 법무 | 개정·고지에 기간이 필요하다 |
| 3 | T-PASS ↔ 신판 코스 연결 절차 | 원장 | 에디션 규칙이라 **강의 콘텐츠 제작 전에** 정해져야 한다 |
| 4 | 토스·카카오 라이브 키 | 원장 | 테스트 검증 완료. 교체 후 dunning 라이브 1회 검증 |
| 5 | staff 계정 위생(무로그인 30개) | 원장 | 결제가 열리기 전에 |

**개발 규모 전부 소(小)**, 1~3은 개발이 할 수 없다.
→ **내년 오픈 시점을 역산해 "언제까지 무엇을 받아야 하는지" 만 정하면 된다.** 지금 코드 작업 없음.

### 보류 — 지금 하지 않기로 하는 것

| 항목 | 왜 미루나 |
|---|---|
| 학생 온보딩 트랙·복귀 훅 | 유입 동기가 강의로 바뀌면 첫 화면 전제가 달라져 **다시 만들게 된다** |
| 활성도 캠페인 | 위와 같음. 대상 정의가 수강 관계 기준으로 바뀐다 |
| 종합반 이행판 확대 | 파일럿 11명. 확대 결정이 먼저다(기능은 이미 있다) |
| 관제(MRR·PG 대사·정산 지급·4-eyes) | 실매출 후. 지금은 0 위의 계기판 |

## 5. 하지 않을 것 (명시)

- **새 운영자 화면을 기본값으로 만들지 않는다** — 이미 26 클러스터 111 화면.
  N1 검수 큐처럼 **왕복을 없애는 화면**만 만들고 조회용 타일은 늘리지 않는다.
- **IA 재설계 안 한다**(2026-07 완료) · **새 role enum 안 만든다**(duty 패턴).
- **잠긴 축의 지표를 성과로 읽지 않는다** — 계획대로 잠긴 것이다.
- **부분 가동 상태의 활성도를 결함으로 취급하지 않는다** — 구조의 결과다.
