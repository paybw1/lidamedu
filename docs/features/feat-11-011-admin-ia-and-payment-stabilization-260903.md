## 1. 현황 감사 (2026-09-03, 운영 DB `mcgdoplo` 실측)

### 1.1 ★§2 접근불가 6화면 — 원인 규명 완료

**6화면 모두 서버 코드·데이터에 이상이 없다.** 주 쿼리를 운영 DB 에 직접 실행해 9/9 정상 응답을 확인했다(`tmp/probe-p0.mjs`). 원인은 **권한 차단이며, 차단 화면이 일반 오류 화면과 구분되지 않는 것**이 신고로 이어졌다.

| 번호 | 화면 | 서버 가드 | 운영 실태 | 결과 |
|---|---|---|---|---|
| P0-01 | `/admin/lms/enrollments` | manager+ **AND** duty `lms_cs` | `lms_cs` 배정 **0명** | manager 전원 403 |
| P0-03 | `/admin/lms/devices` | manager+ **AND** duty `lms_cs` | 〃 | 403 |
| P0-02 | `/admin/orders` | manager+ **AND** duty `lms_orders_admin` | `lms_orders_admin` 배정 **0명** | 403 |
| P0-06 | `/admin/shipments` | manager+ **AND** duty `lms_orders_admin` | 〃 | 403 |
| P0-04 | `/admin/access-logs` | `role === 'admin'` (원장 전용) | manager 11명 | 403 |
| P0-05 | `/admin/instructors` | `role === 'admin'` (원장 전용) | manager 11명 | 403 |

근거:

- `staff_duty_assignments` 실측 — 배정된 duty 는 `ai_usage_alert` / `bug_report` / `lecture_abuse_alert` / `lms_video_admin`(CHO·김민정) / `qna_question` / `student_admin_access` / `upgrade_request` **뿐**. `lms_cs` · `lms_orders_admin` · `lms_stats_view` 는 **아무에게도 배정돼 있지 않다.**
- `hasDutyAccess()`(`app/features/admin/lib/duties.server.ts`)는 `role === 'admin'` 만 우회 — **원장 계정으로는 6화면이 전부 열린다.** 신고자는 manager 계정이다.
- `app/root.tsx` `ErrorBoundary` 는 404 와 국가차단만 전용 화면을 주고, **그 밖의 4xx·5xx 를 모두 "문제가 발생했습니다 / 일시적인 오류일 수 있습니다"** 로 렌더한다 → 403 과 실제 장애가 화면상 동일.
- `admin-shell.tsx` `visibleAdminNav()` 는 `minRole` 만 필터하고 **duty 는 보지 않는다** → 열 수 없는 메뉴가 사이드바에 그대로 노출. 요청서 §1.4 "권한 없는 메뉴는 숨긴다" 위반이 이 신고의 직접 원인.

> **결론** — §2 는 "6개 화면을 고치는 일"이 아니라 **①권한 정책 결정(D2) ②차단 화면 분리(P0) ③메뉴 duty 필터(P0)** 세 가지다.
> 다만 열린 뒤 §2 공통 완료기준(검색·목록·상세·저장·취소·권한차단·변경이력)은 별도로 실사한다(P1).

### 1.2 ★§10 보안 — 이번 감사에서 나온 별건

요청서와 무관하나 원장이 알아야 한다.

1. **운영 DB 에 `role='admin'`(원장) 계정이 16개**, 그중 **15개가 `e2e-*` 테스트 계정**이다(`e2e-d-*` 11개, `e2e-tm-place-*` 5개). 실제 원장은 임병웅 1명.
2. **`테스트학생01~05` 가 `role='manager'`(관리자)** 로 올라가 있다. 실계정 manager 는 하지원·리담관리자·김민엽·김민정·CHO·joon.
3. E2E 가 `auth.users` 를 지우지 못해([[e2e-deleteuser-noop]]) 실행마다 계정이 쌓이는 구조다 — 방치하면 계속 증가한다.

→ P0 에 **테스트 계정 강등·정리 + E2E 계정 role 승격 금지**를 포함한다. 삭제가 아니라 `role='student'` 강등 + 접근 차단(감사 로그 남김)을 기본안으로 한다.

### 1.3 §3 결제 — 실측 수치

```
orders.status   pending_payment  24건   2026-07-08 ~ 2026-09-03   ← 적체
                paid              2건
                cancelled        12건
                refunded          1건
order_items.item_type   plan 25 · book 7 · course_extension 6
```

- **원인**: `createOrder` / `createCartOrder`(`orders.server.ts:26,78`)가 **PG 호출 전에** `status='pending_payment'` 로 주문을 만든다. 사용자가 결제창을 닫으면 그대로 남고, 정리 주체가 없다. 만료 루틴은 **무통장 전용**(`expireOverdueBankTransfers`)뿐이다.
- `pending_payment` 는 소유 판정에도 쓰인다(`orders.server.ts:342` — `.in("status", [paid, partially_refunded, pending_deposit, pending_payment])`). **결제하지 않은 주문이 "보유"로 계산될 수 있다** — 요청서에 없지만 같은 뿌리의 결함이다.
- `course_extension` 은 한글 라벨 매핑이 없다(`extension.server.ts:181`에서 저장, 표시 계층에 매핑 부재) → 학생 화면에 내부코드 그대로.
- 도서 항목은 `order_items.book_id` 만 있고 제목 스냅샷이 없다 → 표시 로직이 도서명을 못 붙이면 "도서 × 2" 로 떨어진다.
- **연장 메타는 이미 저장돼 있다** — `enrollment_extensions`(feat-11-010 §6)에 기존 종료일·연장일수·금액·회차(=`count(status='applied')`)가 전부 있다. **관리자 결제내역 화면이 이 테이블을 조인하지 않을 뿐이다.**
- 중복 연장 방지도 이미 있다 — `enrollment_extensions.order_item_id UNIQUE`(feat-11-010 §5).

## 2. 설계 결정 — D1~D10

> 각 항목은 **기본안 1개 + 대안**이다. 이견 없으면 기본안으로 간다.
> **[원장 결정 필요]** 표시된 것만 답을 주시면 된다. 나머지는 확인 후 진행한다.

### D1. 관리자 메뉴 재편 범위 **[원장 결정 필요]**

요청서 §1.2 의 10개 군(대시보드·강의상품·영상자료·수강운영·회원CRM·주문결제·교재배송·쿠폰포인트·정산통계·사이트관리·시스템보안)은 **동영상 서비스 기준**이다. 그런데 현재 `/admin` 은 학습 플랫폼(법령·판례·문제·빈칸·2차 논술·종합반·Q&A — 클러스터 20여 개)과 강의·판매를 **한 사이드바에 담고 있다.** 10개 군을 `/admin` 전체에 적용하면 학습 플랫폼 IA 가 갈 곳이 없다.

- **기본안 — 관리자 화면을 2모드로 나눈다.** 사이드바 최상단에 `[학습 관리 | 강의·판매 관리]` 전환(학생 화면의 플랫폼 스위처와 같은 어법). **강의·판매 모드**가 요청서 10개 군을 그대로 구현하고, **학습 관리 모드**는 현행 IA 를 유지한다. 양쪽에 걸치는 화면(회원·CRM, 시스템·보안, 정산·통계)은 **한 벌만 두고 양쪽에서 같은 URL 로 진입**한다(§1.4 "동일 기능의 대표 URL 하나" 충족). 마지막 모드는 기억한다.
  - 장점: 요청서를 100% 만족하면서 학습 플랫폼 운영을 안 깨뜨린다. 학생 표면에서 이미 검증된 어법이다.
  - 비용: 사이드바 컴포넌트 1개 개조 + 클러스터 재배치. 화면 이동은 없다(URL 유지).
- 대안 A: `/admin` 전체를 10개 군으로 재단 → 학습 플랫폼 30여 화면이 "기타"로 몰린다. **비권장.**
- 대안 B: 강의·판매 관리를 `/lecture-admin` 등 **별도 경로**로 분리 → URL 이 갈라져 §1.4 "대표 URL 하나" 와 충돌하고 기존 북마크가 깨진다. **비권장.**

### D2. 권한 정책 — duty 배정 vs 완화 **[원장 결정 필요]**

`lms_cs`·`lms_orders_admin` 이 0명 배정이라 manager 가 수강권·주문·배송·기기 화면을 못 연다. 두 갈래다.

- **기본안 — 배정으로 푼다.** `/admin/staff-duties` 에서 담당자를 지정한다(원장이 실제 담당자를 정해야 하므로 결정 필요). 코드는 그대로, **메뉴에서 duty 를 반영해 숨기고**(P0), 직접 URL 접근은 전용 차단 화면을 준다. 요청서 §1.4 와 정확히 일치한다.
  - 필요 입력: `lms_cs`(수강권·기기·CS) / `lms_orders_admin`(주문·결제·배송) / `lms_stats_view`(정산·통계) 각각의 담당자.
- 대안: **manager 는 기본 허용**으로 완화하고 duty 는 강사 한정으로만 쓴다. 운영은 편해지나 결제·환불 권한이 관리자 전원에게 열린다.

추가로 `/admin/access-logs`·`/admin/instructors` 는 **원장 전용**이 맞는지 확인이 필요하다. 기본안: **접속이력은 manager 허용**(회원 CS 에 필요), **강사 담당·권한은 원장 전용 유지**(권한 부여 화면이므로).

### D3. "결제시도" 상태 모델

- **기본안 — `orders.status` 에 `attempted` 추가.** PG 호출 **전**에는 `attempted` 로 만들고, 토스 결제창 진입 성공 시점에 `pending_payment` 로 승격한다. `attempted` 는 **주문 목록·매출 집계·소유 판정에서 전부 제외**한다. 결제창 종료(클라이언트 신호) 또는 **TTL 30분 경과** 시 `expired` 로 자동 전환한다(cron + lazy 이중, 무통장 만료와 같은 패턴).
  - `orders.status` CHECK 제약에 `attempted`·`expired` 추가 + 부분 인덱스.
  - **기존 24건 백필**: `pending_payment` 이면서 결제 레코드가 없고 30분 이상 지난 것 → `expired`. dry-run 목록을 원장 확인 후 적용, 원복용 백업 JSON 저장.
- 대안: 기존 `draft`(장바구니) 재사용 → 장바구니와 결제시도가 섞여 §3.2 "같은 목록에 섞임" 문제를 다시 만든다. **비권장.**

### D4. 주문 표시명 — 스냅샷 vs 조인

- **기본안 — `order_items.title_snapshot`(text) 신설.** 주문 생성 시점의 상품명·도서명·연장 문구를 **저장**한다. 표시 SSOT 는 `app/features/orders/lib/order-item-label.ts` 단일 함수(비-server, 관리자·학생 공용):
  - `plan` → 상품명 · `book` → 도서명 (수량 별도 열) · `course_extension` → **"수강기간 연장 — {강의명} {N}일"**
  - 내부코드(`course_extension` 등)는 어떤 화면에도 노출하지 않는다.
  - 기존 38건은 현재 조인 가능한 값으로 백필한다.
  - 이유: 상품명이 바뀌거나 상품이 내려가도 **영수증·결제내역은 그때 산 이름을 보여야 한다.**
- 대안: 조회 시 매번 조인 → 상품 삭제·개명에 영수증이 흔들린다.

### D5. 연장 주문 메타 — 신규 저장 안 함

요청서 §3.2 "연장 주문에 주문유형·상품명·수강권 ID·기존 종료일·연장일수·연장 회차·금액을 저장" 은 **`enrollment_extensions` 에 이미 전부 있다.** 컬럼을 또 만들면 두 곳이 어긋난다(feat-11-010 이 "연장횟수는 컬럼이 아니라 count 로 센다"를 명시).

- **기본안**: 저장은 그대로, **관리자 결제내역·주문 상세가 `enrollment_extensions` 를 조인해 표시**한다. `title_snapshot`(D4)만 추가 저장. 요청서 의도(=화면에서 식별 가능)는 이걸로 충족된다.

### D6. 중복 방지키

- 연장 이중 적용: `enrollment_extensions.order_item_id UNIQUE` — **이미 있음.**
- **추가 기본안**: `payments.toss_payment_key` 에 UNIQUE 인덱스(부분, not null). confirm 응답과 웹훅이 동시에 도착해도 결제 레코드가 두 벌 생기지 않게 한다. 적용 전 중복 존재 여부를 먼저 조회한다.

### D7. 만료 후 연장의 기산일 **[확인 필요]**

요청서 §3.2: "만료 후 연장이면 결제승인 즉시 수강 가능하게 하되 **다음 날부터** 연장일수를 계산."
feat-11-010 §4 의 현행 계산식과 대조가 필요하다. 기본안: **현행이 `now + N일`이면 `KST 익일 0시 + N일`로 바꾸고**, 승인~익일 사이는 접근을 허용한다(= 실제 부여일수가 하루 늘어난다). 원장이 의도한 게 "손해 없이 온전한 N일"이면 이 해석이 맞다.

### D8. 목록 상태 유지 메커니즘

§1.4·§5 의 "목록 필터·정렬·페이지·검색어를 상세 갔다 와도 유지".

- **기본안 — URL 쿼리스트링이 SSOT**(현행과 동일), 목록 → 상세 이동 시 **`sessionStorage` 에 마지막 쿼리를 화면별로 저장**하고, 상세의 "목록으로" 버튼과 사이드바 재진입이 그 쿼리를 복원한다. 공용 훅 1개(`use-list-return.ts`) + 공용 `<BackToList>` 컴포넌트로 전 목록 화면에 적용.
  - URL 이 SSOT 이므로 **링크 공유·새로고침이 그대로 동작**한다. sessionStorage 는 복원 힌트일 뿐이다.
- 대안: localStorage 전역 저장 → 며칠 전 필터가 되살아나 "왜 목록이 비었지" 를 만든다. **비권장.**

### D9. 포인트 정책 범위 **[원장 결정 필요]**

- **기본안 — 최소 구성.** `app_settings` 키로 ①적립률(구매금액 %) ②최소 사용 포인트 ③1회 최대 사용한도 ④유효기간(개월)만 둔다. 화면 = `/admin/points`(정책 + 이용내역 조회·수동 지급/회수). 소멸은 유효기간 경과분을 cron 이 `expired` 트랜잭션으로 상계.
- 대안: 조건별 정책 테이블(가입·상품별·이벤트별 적립률) — 운영 규칙이 아직 없으면 YAGNI. **필요하면 말씀 주세요.**
- "포인트쿠폰"(포인트 지급용 쿠폰)은 **`coupons.benefit_type='point'` 확장**으로 처리한다(테이블 신설 금지).

### D10. 쿠폰 두 시스템 통합 여부

현재 **구독 할인 = `discounts`**, **강의·도서 쿠폰 = `coupons`/`user_coupons`** 로 분리돼 있다([[coupon-two-systems-feat13]]).

- **기본안 — 통합하지 않는다.** 결제 파이프가 다르고(구독 정기결제 vs 주문 1회성) 합치면 양쪽 회귀 위험이 크다. 대신 **메뉴에서 "쿠폰·포인트관리" 한 군으로 묶고**, 각 화면 상단에 적용 대상(구독 / 강의·교재)을 명시한다.
- 대안: 단일 쿠폰 엔진으로 통합 — 별도 프로젝트 규모. **비권장.**

## 6. 구현 완료 — 운영자 결제 환불 (2026-09-03)

원장 지시(§4 별건 1)로 Phase 순서보다 먼저 넣었다.

**화면** `/admin/pricing` 아님 — **운영관리 > 매출·정산 관리 > 주문·결제 관리(`/admin/payments`)** 결제내역 탭.
결제 완료 행 오른쪽 「처리」 열에 **환불** 버튼이 생긴다.

**동작**
1. 대상 확인 창 — 학생·상품·환불액을 다시 보여 준다. **사유 필수**(2~500자, 감사 기록에 남음).
2. 토스 결제건이면 **전액 취소 API 호출** → 성공한 뒤에만 환불로 기록한다.
   ★순서가 중요하다. 반대로 하면 DB 는 환불인데 돈은 그대로인 상태가 남는다.
3. 무통장·무료·수동 지급처럼 **결제키가 없는 건**은 자동 취소가 불가능하므로 안내 문구가 바뀌고
   기록만 남는다(실제 송금은 사람이 한다). 수강권·주문 회수는 동일하게 수행한다.
4. 이 결제로 지급된 **구독(`user_subscriptions`) 회수** + 연결 **주문(`orders`) 회수**(강의 수강권·도서 배송).
5. `subscription_admin_logs` 에 `action='refund'` 로 남는다 — 누가·언제·얼마·사유.
6. 환불 후에는 「환불내역」 탭과 CSV 에 그대로 잡힌다(기존 화면 재사용).

**정책**
- **전액 환불만.** 부분 환불은 강의·도서의 항목별 부분환불(`/admin/orders`)이 이미 담당하고,
  구독은 부분 금액을 표현할 상태값이 없다. 굳이 만들면 매출·환불 집계가 어긋난다.
- **기간 제한 없음.** 학생 셀프 해지의 3일 제한(`REFUND_WINDOW_DAYS`)은 그대로 두고,
  그 창이 지난 건을 운영자가 처리한다.
- **권한 = manager 이상**(주문·결제 관리 화면과 동일). 원장 전용으로 좁히려면
  `admin-payments.tsx` action 의 `roleAtLeast(prof?.role, "manager")` 를 `"admin"` 으로 바꾸면 된다.

**파일**
- `app/features/subscriptions/refund-admin.server.ts` (신규) — `refundPaymentAdmin`
- `app/features/subscriptions/screens/admin-payments.tsx` — `action` + `RefundDialog`
- `scripts/sql/20260903_payment_refund_admin.sql` — 감사 로그 action 에 `'refund'` 추가 (운영 적용 완료)
- 원복: `scripts/sql/20260903_payment_refund_admin_rollback.sql`

**검증**
- `npm run typecheck` 통과 · `npx react-router build` 통과
- 가드 실검증(운영 DB, 변경 없는 경로만): 없는 결제 / 실패 결제 / 대기중 결제 / 사유 미입력 → **4/4 차단**

도서후기 500P(1일 1회). 나머지 9종은 중지 상태로 등록만 해 두었다.

**적립 시점이 코드에 연결된 것은 5종**(가입·차시완료·수강후기·도서후기·결제완료).
나머지 8종은 화면에 **「연결 대기」**로 표시되고, 켜도 적립되지 않는다. 현재 활성 4종은
전부 연결돼 있어 운영에는 지장이 없다.

### 설계에서 정한 것

- **적립량을 코드에 박지 않는다.** `awardPoints({ policyKey, userId, refType, refId })` 만
  부르면 켜짐 여부·금액·한도·중복을 전부 정책이 판단한다.
- **중복 방지는 DB 가 한다** — `point_transactions (user, policy, ref_type, ref_id)` 부분 UNIQUE.
  훅이 두 번 불려도 두 번 적립되지 않는다. 애플리케이션 카운트로 막지 않는다.
- **하루 한도는 KST 달력일 기준**으로 센다(서버 시간이 아니다).
- ★**가입 포인트는 소급 지급하지 않는다.** 로그인 완주 시점에 부르되 **가입 후 24시간 이내**
  계정만 대상. UNIQUE 인덱스만 믿으면 1인 1회는 지켜지지만, 정책을 켜는 순간 **기존 회원
  279명이 다음 로그인에 5,000P씩** 받게 된다. 그건 지급이 아니라 사고다.
- **교환은 DB 함수 하나**(`exchange_points_for_coupon`, SECURITY DEFINER)로 처리한다.
  포인트 차감과 쿠폰 발급을 애플리케이션에서 나눠 부르면 중간에 끊겼을 때 포인트만
  사라지거나 쿠폰만 생긴다.
- 한 쿠폰은 **회원당 1회** 교환된다 — `coupon_grants` 의 UNIQUE(coupon_id, user_id) 가
  이미 그렇게 강제하고 있어 별도 횟수 제한을 두지 않았다.
- 기존 후기 보상(app_settings `review_reward_points` 2,000P 단일 값)은 **정책 엔진으로 흡수**했다.
  값이 두 곳에 있으면 운영자가 화면에서 고친 값이 안 먹는다.

## 8. 구현 완료 — 관리자 메뉴 2모드 (2026-09-03, D1)

사이드바 최상단에 **`[학습 관리 | 강의·판매 관리]`** 전환을 두고, 강의·판매 모드가
요청서 §1.2 의 **열 개 업무군을 번호 순서 그대로** 구현한다.

```
0 대시보드      1개      6 교재·배송관리   3개
1 강의·상품관리  6개      7 쿠폰·포인트관리  2개
2 영상자료관리   2개      8 정산·통계      7개
3 수강운영관리   4개      9 사이트관리     11개
4 회원·CRM     5개     10 시스템·보안     6개
5 주문·결제관리  2개
```

- **URL 은 하나도 바뀌지 않는다.** 배치와 이름만 옮겼다 — 기존 북마크가 그대로 산다.
  커머스 모드의 49개 경로가 전부 실제 화면·라우트로 해석되는지 확인했다(미등록 0).
- **화면 메타(라벨·minRole·duty)의 단일 출처는 `ADMIN_NAV`.** 커머스 모드는 **경로만**
  나열하고 메타는 찾아 쓴다. 두 벌로 두면 권한 표기가 조용히 갈라진다.
- **공용 화면은 한 벌만.** 회원·CRM / 공지 / 시스템·보안 / 강사 / 사이트는 양쪽 모드에
  **같은 URL** 로 나타난다(요청서 §1.4).
- 학습 관리 모드에서는 커머스가 가져간 클러스터(`lms`·`products`·`sales`)를 뺀다.
  양쪽에 다 보이면 어디가 정본인지 알 수 없다.
- **모드 판정** — 화면이 속한 클러스터가 모드를 정하고, 양쪽에 걸친 공용 화면은
  마지막에 고른 모드(localStorage)를 따른다. SSR 결정성을 위해 저장값은 mount 뒤 적용.
- ★**검색(⌘K)과 허브는 두 모드를 모두 훑는다.** 지금 보는 모드에 없다고 못 찾으면
  "화면 찾기"가 아니고, 허브에서 반대편 화면이 사라지면 안 된다.
