# 복습 전용 화면 — 현황 점검 (읽기 전용 조사)

> 목적: 학습관리 "오늘의 할일·복습"에서 항목을 누르면 **그 문제의 원래 위치로 흩어지는** 현상을 확인하고, 대신 **복습 전용 화면**(복습 문제들을 모아 이전/다음으로 이동)을 설계하기 위한 재료.

## 0. 한눈에 (TL;DR)

- **"오늘의 할일·복습"의 정체** = `/study/today` 화면(`today.tsx`)의 **3개 카드**(① 복습 / ② 추천 학습 / ③ 과제). 단일 정렬 목록이 아니라 영역 분리.
- **사용자 주장("누르면 원래 위치로 흩어진다")은 맞다.** ② 추천 7종은 거의 전부 `/subjects/{과목}/...`(과목 학습 허브의 문제·조문·판례 뷰어)로 직행한다. ① 복습 카드는 `/study/srs` 허브로 가지만, **그 허브도 "러너"가 아니라 표(table) 목록**이라 행을 누르면 **다시** `/subjects/...`로 흩어진다(OX만 예외).
- **풀기/보기는 실제로 혼재한다.** 풀기(채점·스케줄 갱신) = 객관식·빈칸·**OX** SRS. 보기(읽기만) = **조문 정독 복습 단 하나**(코드·UI 모두 "채점 없음, 정독"이라 명시).
- **이미 "전용 러너"인 예외가 둘** = OX 복습(`/study/srs/ox`, 다과목 카드 모음 + 이전/다음 없는 세로 나열) · 암기 카드(`/srs`, 별개 시스템).
- **기존 러너 재사용성**: OX는 공용 카드 `QuestionCard`가 **풀기/보기 양용**(주석에 명시) — 그대로 재사용 가능. **MCQ는 보기 모드가 없어** `problem-viewer`에 보기 게이트 한 줄을 더해야 한다(단일 지점). 임의 묶음 주입은 `quiz_sessions.problem_ids` 통로가 이미 표준(오답노트가 사용 중).

### 1-4. ★ 네비게이션 검증 결론

**사용자 주장은 ② 추천 카드에 대해 정확히 맞다.** 종류마다 목적지가 다 다르고, 모두 **자신의 원래 콘텐츠 위치(과목별 학습 허브)로 점프**한다 → 오늘 화면으로 돌아오는 흐름이 끊긴다. 특히 `gap_problems`는 5문항 중 **첫 문제만** 링크되고 나머지는 뷰어 내 next/prev에 의존(`daily-menu.server.ts:416` 주석).

**예외(이미 전용 러너/허브로 가는 것):**
- **① 복습 카드** → `/study/srs`(허브) 또는 `/srs`(암기 카드). 개별 문제로 안 흩어짐.
- **OX SRS 복습** → `/study/srs/ox`(`srs-ox-review.tsx`, 다과목 혼재 카드 모음 — 단 이전/다음 없는 세로 나열).
- **③ 과제** → `/assignments/{id}`.

**★ 두 번째 단절(중요):** ① 복습 카드가 가는 **`/study/srs` 허브 자체도 "러너"가 아니라 표(table) 목록**(`srs.tsx`)이다. 그 표의 각 행 "풀기"가 **다시** `/subjects/{law}/problems/{id}`(`srs.tsx:288`), `/subjects/{law}/articles/{num}`(`srs.tsx:716,864`)로 흩어진다. **OX 섹션만** `/study/srs/ox` 통합 러너로 모인다(`srs.tsx:419,790`). 즉 복습은 **2겹으로 흩어진다**: ② 추천에서 한 번, ①→`/study/srs` 표 행에서 또 한 번.

> **설계 함의**: "복습 전용 화면"이 직접 대체해야 할 대상은 **`/study/srs` 허브의 표→과목 허브 흩어짐**이다(= 1차 타깃). ② 추천 카드의 흩어짐은 그다음(추천을 전용 러너로 보낼지는 별도 판단).

## 2. 풀기 / 보기 혼재 지도

### 2-1. 먼저: SRS 시스템은 2종 (혼동 주의)

| 구분 | `/study/srs` (복습 큐, 자동) | `/srs` (암기 카드, 플래시카드) |
|---|---|---|
| 모듈 | `app/features/study/` | `app/features/srs/` (별도) |
| 정의 | 평소 풀이/방문에서 **자동 파생**된 due(틀린 문제·빈칸·OX·조문)를 다시 풀게/읽게 | 조문·판례를 **앞/뒤 카드**로 능동 회상(Anki식 self-grade) |
| 채점 모델 | 정답 여부 이진 → SM-2 simplified | 4단계 self-grade(다시/어려움/보통/쉬움) |
| 스케줄 알고리즘 | `study/lib/srs.ts` `computeNextSrsState` | `srs/lib/scheduler.ts` `scheduleNext` (별개 파일·별개 알고리즘) |
| 스케줄 테이블 | `user_problem_srs`·`user_ox_ref_srs`·`user_blank_srs` (조문은 테이블 없음) | `srs_review_states`+`srs_review_logs`+`srs_items` |
| 진입 | `screens/srs.tsx`, nav "복습" | `srs/screens/srs-review.tsx`, nav "암기 카드"(베타) |

`/study/srs/ox`(`srs-ox-review.tsx`)는 별개 시스템이 아니라 **`/study/srs`의 OX 전용 풀이 러너**다.
(★ `study/lib/srs.ts`와 `srs/lib/scheduler.ts`는 이름만 비슷한 다른 파일.)

### 2-2. 복습 종류별 풀기/보기 판정

| 복습 종류 | 풀기 / 보기 | 근거 (파일:line) | 답 제출 API |
|---|---|---|---|
| **객관식 SRS due** | **풀기** | 행→문제 뷰어(`srs.tsx:288`). due=`getDueProblems`(`srs.server.ts:80`, `user_problem_srs.next_due_at<=now`) | `/api/problems/attempt` |
| **빈칸 SRS due** | **풀기** | 행→조문 뷰어 빈칸 모드(`srs.tsx:864`, `?blank=`). due=`getDueBlankSets`(`blanks/srs.server.ts:82`) | 빈칸 attempt→`applyBlankSrsUpdate` |
| **정오문제(OX) SRS due** | **풀기 (가장 전형적)** | `/study/srs/ox` 러너. O/X 클릭→`handleAnswer`(`srs-ox-review.tsx:80-98`)가 `isCorrect` 계산 후 `fetch("/api/problems/attempt")`. due=`getDueOxRefs`(`ox-srs.server.ts:85`) | `/api/problems/attempt` (`:92`) |

| 기능 | 풀기 / 보기 | 근거 |
|---|---|---|
| **암기 카드 `/srs`** | 풀기(능동 회상, **채점 아닌 self-grade**) | 앞면→"정답 보기" 뒤집기→4단계 자가평가(`srs-review.tsx:184-195`). `/api/srs/review`→`submitReview`→RPC `srs_record_review` |

### 2-3. 답 제출 흐름 (풀기형 수렴점)

객관식·OX·OX-SRS 러너·OX 시험·약점/오답 세션이 **한 엔드포인트로 수렴**:

```
[문제뷰어 / OX패널 / OX시험 / /study/srs/ox 러너]
   └─ POST /api/problems/attempt   (problems/api/attempt.tsx)
        └─ recordProblemAttempt()  (study/queries.server.ts:334)
             1) user_problem_attempts INSERT (1행=1채점)
             2) SRS hook (best-effort, 실패해도 attempt 성공):
                - oxAnswer==null  → applyProblemSrsUpdate()  → user_problem_srs
                - oxAnswer 있음+ref → applyOxRefSrsUpdate()   → user_ox_ref_srs
```

- `apply*SrsUpdate`는 이전 상태→`computeNextSrsState`→해당 테이블 upsert. **풀면 그 자리서 `next_due_at` 재계산.**
- 빈칸은 별도 attempt API에서 `applyBlankSrsUpdate`. 암기 카드만 `/api/srs/review` 경로. 주관식은 스케줄 갱신 없음.

### 2-4. due 계산 (요지)

- `/study/srs`(문제·빈칸·OX): `next_due_at <= now()`. 다음 복습일 = `computeNextSrsState`(`study/lib/srs.ts:27`) — **틀림=1일**, **맞음=1→3→7→14→30→60일(×ease), 최대 90일**. 세 종류 동일 함수, 테이블만 분리.
- 조문 복습: 테이블 없이 `study_sessions` 방문 + `INTERVAL_DAYS=[7,14,30,60]` 파생(`article-review.server.ts:29-35`). 정답 신호 없음.
- 암기 카드: `srs_review_states.due_date<=오늘(KST)`, `scheduleNext` state machine(별개).

### 2-5. 결론 — 혼재 양상

**한 화면(`/study/srs`) 안에 풀기 3 + 보기 1이 공존한다:**
- **풀기**(채점·attempt·스케줄 갱신): 객관식 / 빈칸 / **OX** SRS.
- **보기**(읽기만, 채점 없음): **조문 정독 단 하나**. 버튼도 "풀기"가 아니라 "정독".

즉 혼재의 실체는 "절반은 풀기, 절반은 보기"가 아니라 **"대부분 풀기 + 조문 정독 1종만 보기"**다. (오답을 "보기"로 다시 보고 싶은 수요는 별개 — 현재 오답은 `session-from-attempts`로 **풀기**만 제공.)

### 3-2. 핵심 사실

1. **"답 없이 정답·해설 즉시"인 순수 보기 모드는 두 곳뿐** — (OX) `QuestionCard`를 `submitted+onAnswer=noop`(레퍼런스 `my-ox-session-result.tsx`), (MCQ) `wrong-note-print`의 `McqBlock`(단 인쇄 레이아웃).
2. **나머지 풀이 화면의 "보기"는 풀기 게이트 뒤에 숨어 있다** — `mcq-pack-sheet.tsx:557` `const showAnswers = graded && !isExam`(해설은 `:682`), `problem-viewer.tsx:1280` `{revealed && !isExam ? ### 3-3. 재사용성 평가

**OX 복습 → 공용 `QuestionCard` 직접 재사용이 정답.**
props = `{ item, index, answer, submitted, onAnswer }` — 출처 개념 0, loader 의존 0. **머리주석에 풀기/보기 양용 의도가 명시**(`ox-question-card.tsx:1-3` "결과 뷰는 onAnswer=noop 로 읽기 전용 렌더에 재사용"). `submitted=false`+실제 `onAnswer`=풀기, `submitted=true`+noop=보기. 복습 화면이 `OxQuestionItem[]`을 `.map()`하고 풀기/보기 토글 하나만 얹으면 됨. (덤으로 `srs-ox-review`의 자체 카드를 공용 카드로 통일하면 드리프트 해소.)

**MCQ 복습 → 보기 모드를 추가해야 한다.**
풀기·prev/next·묶음 주입이 다 되는 `problem-viewer`가 토대로 가장 적합하나 **답 없이 보기 모드가 없다.** 두 가지가 필요:
1. **보기 게이트 우회** — 정답·해설 노출이 `revealed && !isExam` 한 군데(`problem-viewer.tsx:1280`)로 모여 있어 `revealed || viewMode` 식 **렌더 분기 한 곳** 수정이면 충분(해설 블록은 `problem` 데이터만 사용 — 채점/세션에 안 엮임).
2. **묶음 주입** — 복습 큐를 `createQuizSession(scopeType, problemIds)`로 만들어 `?session=&mode=` 진입(오답노트 패턴 그대로, 새 통로 불필요).

**순수 보기 렌더 자산**(`wrong-note-print`의 `McqBlock`/`OxBlock`)은 배열→정답·해설 펼침이 이미 되지만 **인쇄 레이아웃 + 오답 전용 loader + 네비 부재**라 화면 복습용 변환 비용이 더 크다.

## 4. 복습 항목 수집 방식

- 현재 `/study/today` loader는 `getTodaySummary` 하나를 호출(`today.tsx:65`), 내부에서 8개 쿼리를 `Promise.all` 병렬(`today-summary.server.ts:141-159`) → 결과를 `{ review, recommendations, assignments, progress, cardBacklog, … }`로 **영역별 필드 분리**. **한 정렬 목록 아님.**
- `/study/srs` loader는 종류별 섹션(문제/빈칸/OX/조문)을 각각 `getDue*`로 조회해 **섹션별 표**로 렌더(`srs.tsx`).
- **복습 전용 화면이 "한 정렬된 목록"으로 모을 수 있는가? → 가능하다.** 모든 풀기형 due는 결국 **`{ refType, problemId/refId, lawCode, … }`로 환원**되고, 임의 묶음을 푸는 표준 통로(`quiz_sessions.problem_ids`)가 이미 존재한다. 즉 **due 항목들을 한 배열로 모아 세션으로 만들면** `problem-viewer`/`QuestionCard`가 prev/next로 순회할 수 있다.
- **단, 콘텐츠 타입이 이종(異種)** — MCQ(문제 뷰어)·OX(QuestionCard)·빈칸(조문 뷰어 빈칸 모드)·조문 정독(읽기). prev/next "한 줄"에 섞으려면 **타입별 렌더러 전환**이 필요(아래 §5의 비용 핵심).

## 5. 설계 선택지 + tradeoff

> 혼재의 실체(§2-5) = **대부분 풀기 + 조문 정독 1종만 보기**, 그리고 콘텐츠 타입이 이종(MCQ·OX·빈칸·조문).
> 비용의 핵심은 "풀기↔보기 모드 전환"이 아니라 **"이종 콘텐츠 렌더러를 한 prev/next 줄에 모으는 것"**이다(모드 전환 자체는 OX는 공짜, MCQ는 게이트 한 줄).

### (a) 한 러너 + 항목별 모드 자동 전환
복습 전용 화면 하나가 due 항목을 한 목록으로 들고, 항목 타입에 따라 카드 렌더러와 풀기/보기 모드를 자동 전환(MCQ·OX·빈칸=풀기, 조문=보기 카드), prev/next는 공통.

- **장점**: 사용자가 원한 "모아서 이전/다음" 그대로. 흐름 안 끊김. OX는 `QuestionCard` `submitted` 토글로 모드 전환이 **이미** 됨.
- **단점/비용**: **이종 렌더러 통합이 큼** — OX 카드 ≠ MCQ 문제 뷰어(5지선다+박스+해설) ≠ 빈칸(조문 뷰어 빈칸 모드) ≠ 조문 정독. MCQ를 카드화하거나 `problem-viewer`를 임베드해야 하고, 빈칸은 조문 뷰어 의존이라 카드 안에 넣기 가장 어렵다.
- **러너 적합성**: OX=`QuestionCard` 그대로. MCQ=`problem-viewer`에 보기 게이트+세션 묶음(중간). 빈칸=난항(별도 취급 권장). 조문=보기 카드 신규(경량).

### (b) 종류(갈래)별 묶음 — 풀기 갈래 / 보기 갈래 분리
풀기 갈래(문제 SRS: MCQ·OX, 각각 세션 러너) / 보기 갈래(조문 정독: 읽기 목록)로 나눠 각자 러너.

- **장점**: 이종 통합 회피 — 각 갈래가 동질이라 기존 러너에 잘 맞음. 현재 구조(`/study/srs`의 섹션 분리)와 연속적이라 점진 적용 쉬움. **OX는 `/study/srs/ox`가 이미 갈래 러너**(이전/다음만 보강).
- **단점**: "한 줄로 모아서 이전/다음"이라는 사용자 멘탈모델과 살짝 어긋남(갈래 전환은 사용자가 인지). 화면이 2개로 나뉨.
- **러너 적합성**: 풀기 갈래 MCQ=세션+`problem-viewer`, 풀기 갈래 OX=`/study/srs/ox`(또는 `QuestionCard` 모음). 보기 갈래=경량 읽기 목록. **가장 기존 자산에 잘 맞음.**

### (c) 통일 — 전부 "풀고 → 해설 보기"
풀기/보기 구분을 없애고 모든 복습을 푼 뒤 해설로(보기 모드 제거).

- **장점**: UX·코드 단순(모드 분기 없음). 어차피 풀어보는 게 복습 효과가 큼.
- **단점/치명적**: **조문 정독은 "풀" 문제가 없다**(읽기지 채점 대상 아님 — `article-review.server.ts`가 명시). (c)는 조문 정독 종류에 **적용 불가** → 조문을 복습에서 빼거나 억지로 OX화해야 함. 오답 "다시 보기" 수요도 무시.
- **러너 적합성**: 풀기형엔 잘 맞지만(세션+뷰어), 보기 전용 항목을 못 담아 **부분해**.

### 권고 (다음 설계 단계용 — 이번엔 구현 안 함)

**(b)를 토대로 하되 (a)의 "한 입구" 감각을 얹은 하이브리드**가 현실적이다:

1. **풀기형(MCQ·OX·빈칸)은 due를 한 배열로 모아 세션(`quiz_sessions`)으로 만들고 prev/next 러너로 순회.** OX는 `QuestionCard` 재사용(+`/study/srs/ox` 통합), MCQ는 `problem-viewer`에 **보기 게이트 한 줄** 추가 후 세션 주입(오답노트 패턴). 빈칸은 조문 뷰어 의존이 강하니 1차 범위에서 별도/후순위.
2. **조문 정독(보기)은 같은 화면의 "읽기 카드"로 in-flow 배치하거나(=(a) 맛), 경량 읽기 목록으로 분리(=(b) 맛).** 어느 쪽이든 "푸는 것"으로 강제하지 않는다.
3. **풀기/보기 토글**은 OX에선 공짜(`submitted`), MCQ에선 게이트 한 줄 — 그래서 "오답을 답 없이 다시 보기"도 저비용으로 제공 가능(부가 가치).

이 방향이면 **1차 타깃(§1-4의 `/study/srs` 표→과목 허브 흩어짐)을 전용 러너로 대체**하면서, 기존 자산(QuestionCard 양용·problem-viewer 세션 nav·quiz_sessions 통로)을 최대 재사용하고, 조문 정독이라는 유일한 순수 보기 종류를 억지로 풀기로 만들지 않는다.
