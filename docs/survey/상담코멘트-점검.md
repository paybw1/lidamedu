# 상담 코멘트 점검 (`/me/consult` + 강사 작성 경로) — 읽기 전용 진단

> 범위: `student_notes`(feat-7-025 작성/CRUD, feat-7-028 공유·알림). 코드 변경 0.
> 핵심 질문: **소통 품질**과 **단방향이 의도인가 빈틈인가**.
> 결론 먼저: ① 흐름은 깔끔하나 ② **사실상 단방향(노트형)인데 "상담"+인박스 알림이 양방향 기대를 만든다 — 답글·읽음 둘 다 없음**. ③ 마크다운은 **약속만 하고 렌더 안 됨**(평문). ④ **작성 게이트에 cohort 검사 누락 = 타 반 학생에게 코멘트를 쓰는 Critical 권한 구멍**(과제 feat-7-021b ①과 동일 계열, 여기선 미수정). 학생→타학생 누수는 없음.

## ① 코멘트 흐름 (강사 → 학생)

**강사 작성** — 학생 상세 페이지(`/admin/students/:profileId`) 안의 `상담 코멘트` 카드(`NotesSection`).
- `신규` 버튼 → `NewNoteForm`: 본문 textarea(최대 4000자) + 노출 라디오(`강사만`/`학생도 보기`) + `핀` 체크박스. `POST /api/admin/student-note` `intent=create`.
- **특정 학생 1:1 지정 = `studentId`(현재 보고 있는 학생 profileId)를 hidden input 으로 박아 전송.** 즉 "이 학생 상세에서 쓴다"가 곧 대상 지정. (대상 선택 UI 없음 — 화면 컨텍스트가 대상.)
- 작성 후 노출이 `share_with_student` 면 학생 인박스에 `student_note_shared` 알림 + `href=/me/consult?note=<id>` (`queries.server.ts:76-91`).

**학생 수신** — `/me/consult`(`student-consult.tsx`).
- 알림 클릭 → 이 화면, `?note=<id>` 로 해당 카드 스크롤·하이라이트(`:42-47`).
- 본인에게 **공유된**(`onlyShared:true`) 코멘트만 카드 리스트. 핀 우선·최신순. 핀 배지·작성자명·작성일 표시.

**read-only 모델** — 학생은 **보기만**. `/me/consult` 라우트엔 **loader 만 있고 action 없음** → 학생이 쓰는 경로가 코드상 부재. 강사↔학생 매핑은 `student_notes.author_id`(강사) ↔ `student_id`(학생) 단일 행, 스레드/부모 없음.

흐름 자체는 군더더기 없이 명료하다. 문제는 흐름이 아니라 **소통 모델의 얕음**(②)과 **게이트 기준 불일치**(④).

## ② ★ 소통 모델 — 단방향이 의도인가 빈틈인가

### 답글 가능? — **불가**
- 학생 화면은 순수 리스트. textarea·답글 버튼·action 전무.
- 스키마에 **답글 구조가 없음**(`parent_id`/`thread_id` 없음, `author_id` 는 항상 1명). 작성 API(`/api/admin/student-note`)는 `getStaffRole` 게이트 → **학생은 애초에 작성 주체가 될 수 없음**.

### 읽음 표시? — **없음**
- `student_notes` 에 `read_at`/`seen_at` 컬럼 없음. `/me/consult` loader 는 조회만 하고 아무것도 마킹하지 않음.
- 강사 `NoteRow`(`:990-1064`)에 "읽음/안읽음" 표시 없음 → **강사는 자기 코멘트가 학생에게 닿았는지 전혀 모른다.**
- 알림(`user_notifications.read_at`)에는 읽음 상태가 있으나 (a) 그것은 *알림 클릭* 여부지 *코멘트 열람*이 아니고, (b) **강사에게 노출되지 않는다**(학생 인박스 전용).

### 의도인가 빈틈인가 — **"단방향 노트"가 본래 설계, 그러나 포장이 양방향 기대를 만든 빈틈**
구조적 근거는 일관되게 **단방향 설계**를 가리킨다:
- 단일 `author_id`(강사), 스레드 스키마 없음, 학생 작성 API 부재, 네이밍이 "코멘트/노트"(대화가 아니라 기록).
- → 강사가 학생 기록에 남기는 **일방적 피드백 메모**로 만든 것이 맞다.

그러나 **포장은 양방향(메시지)처럼 보인다**:
- 기능명 "**상담** 코멘트" — "상담"은 본래 양방향 함의.
- 인박스 알림 "**강사의 새 코멘트가 도착했습니다**" — 메시지 도착처럼 읽힘. 학생은 자연히 "되묻고 싶다"가 생기는데 답할 곳이 없음.
- 강사는 "전달/이해됐나"를 알 수단이 없어 **상담의 피드백 루프가 끊김**.

**판정:** 단방향은 *버그가 아니라 MVP 스코프 선택*이다. 다만 "상담"+인박스라는 포장과 read-only 실체 사이에 **기대 격차(latent gap)**가 있고, **읽음 표시 부재**는 단방향 모델 안에서도 분명한 결함(강사가 깜깜이).

→ 보완 방향을 가른다(⑤): **양방향(답글)=스키마부터 새로 까는 큰 작업** / **단방향 유지 + 읽음·마크다운=작은 다듬기**. 구조 근거상 **후자가 비례적**이며, 진짜 "상담 대화"가 제품적으로 필요해질 때 전자를 별도 feat 로.

## ③ 마크다운 렌더 — 약속 불이행(평문)

- 작성 폼 placeholder: **"…남길 코멘트… (마크다운 가능)"** (`admin-student-detail.tsx:949`) — 강사에게 마크다운을 *약속*.
- 컬럼명도 `body_md`(마크다운 의도).
- 그러나 **렌더는 양쪽 다 평문**:
  - 강사 `NoteRow`: `<p className="… whitespace-pre-line">{note.bodyMd}</p>` (`:1061`)
  - 학생 `/me/consult`: `<div className="… whitespace-pre-line">{n.bodyMd}</div>` (`student-consult.tsx:93-95`)
- 결과: `**굵게**`·`- 목록`·`[링크](…)`·표가 **별표·하이픈·대괄호 그대로 노출**. 줄바꿈만 보존(`whitespace-pre-line`).
- 앱에 재사용 렌더러 `app/features/problems/components/markdown-view.tsx`(`<MarkdownView>`, react-markdown+gfm+katex)가 이미 있어 **교체는 경량**.
- ★**단, 그대로 쓰면 안 됨**: `MarkdownView` 는 `rehype-raw` + `allowDangerousHtml:true`(`:9,144-147`)로 **원시 HTML 을 실행**한다. 신뢰 콘텐츠(운영자 해설·hwpx 적재)용 설정. 상담 코멘트는 **강사(준신뢰)가 써서 학생·타 강사에게 보이는** 글이라, 그대로 쓰면 `<script>`/`<img onerror>` **저장형 XSS**(강사→학생) 경로가 생긴다. 현재 평문 렌더는 React 이스케이프로 XSS 안전 — 마크다운 보완 시 **rehype-raw 비활성 또는 rehype-sanitize 적용**이 전제.

## ④ ★ 게이트 / 보안

### RLS 실태 (운영 mcgdoplo 조회)
`student_notes` RLS **enabled**. 정책 2개:
- `student_notes_author_all` (ALL): `author_id = auth.uid() OR private.is_manager(auth.uid())` (qual+check 동일).
- `student_notes_student_read` (SELECT): `student_id = auth.uid() AND visibility='share_with_student' AND deleted_at IS NULL`.

그러나 **앱 코드는 전 작성·조회를 `adminClient`(service_role, RLS 우회)로 수행**(`queries.server.ts` 전 함수). 즉 RLS 는 앱 경로에선 작동하지 않고 **코드 게이트가 유일 방어**.

### 누가 누구 코멘트를 보나 — 읽기 누수 없음
- **학생 측**: `/me/consult` 는 `listNotesForStudent(user.id, {onlyShared:true})` — `studentId` 를 **세션 본인으로 고정** + 공유분만. RLS `student_notes_student_read` 도 동일 강제. → **타 학생 코멘트·강사전용 코멘트 절대 못 봄. 누수 0.**
- **강사 측**: 학생 상세 loader 가 instructor 면 `cohort_members` 조인으로 **본인 소유 cohort 멤버인지 확인**(`admin-student-detail.tsx:96-107`) 후에만 그 학생의 전체 코멘트(강사전용 포함) 노출. (강사전용 노트가 같은 학생을 보는 다른 staff 에게도 보이는 건 "학생 기록 공유" 설계로 수용 가능 — 누수로 보지 않음.)

### ★ 쓰기 게이트 — cohort 검사 누락 (Critical 권한 구멍)
작성 API action(`student-note.tsx:45-46`)은 **`getStaffRole` 성공(=staff 여부)만 확인**하고 끝난다. `studentId` 는 폼에서 받아 **uuid 형식만 검증**(`createSchema`). 그 외 소유권 검사 0.

→ **강사 A 가 `/api/admin/student-note` 에 다른 반 학생의 `studentId` 로 직접 `intent=create` POST 하면, 자기 반이 아닌 학생에게 상담 코멘트를 작성**할 수 있고, `share_with_student` 면 **그 학생 인박스에 "강사의 새 코멘트가 도착했습니다" 알림까지 발송**된다. (화면 loader 의 cohort 게이트를 우회.) **강사↔강사 수평 권한 상승.**

- **RLS 도 이걸 못 막는다**: `student_notes_author_all` 의 check 는 `author_id = auth.uid()` 뿐 — 작성자가 자기 자신을 author 로 넣으면 통과. **cohort 소유권은 RLS 에 없음.** 즉 작성을 요청 클라이언트로 바꿔도(과제 feat-7-021b (나) 방식) **이 구멍은 안 닫힌다.** → **해법은 action 의 명시적 cohort 게이트**(아래).
- update/delete 는 `isAdmin(=manager+) || author===self` 게이트(`queries.server.ts:113,159` + RLS `author_all`)라 **타 강사 노트 편집·삭제는 차단**. 구멍은 **create(임의 studentId)** 한 곳.

### 게이트 기준이 과제와 왜 다른가 (첫 개요 지적에 답)
- **과제(feat-7-021b)**: 대상이 `cohort_id` 직결 → 수정 후 action 이 `cohort.ownerId===self || manager` 게이트 + 쓰기 요청 클라이언트(RLS `user_owns_cohort`)로 **이중 방어**.
- **상담 코멘트**: 대상이 `student_id`(반 아님). **학생 상세 loader 는 cohort 기준(`cohort_members` 조인)으로 옳게 게이트**하지만, **쓰기 action 은 그 기준을 빠뜨림**(staff 여부만). → 같은 클래스의 버그가 과제에선 고쳐졌고 여기선 **남아 있음**.
- **맞는 기준**: loader 와 동일하게 "이 강사가 *대상 학생이 속한* cohort 를 소유하는가"(= `cohort_members` 조인, manager+ 는 프리패스). loader 의 `ownsAnyCohort` 로직을 action 에서 **재사용**하면 됨.

### (부수) 죽은 경로
- `update` intent 는 API·`updateNote` 에 있으나 **강사 UI 에 편집 폼이 없음**(`NoteRow` 는 삭제 버튼만, `:1040-1059`). → 작성 후 본문 수정·노출 토글(강사만→학생공개) 불가. `updateNote` 의 "공유로 전환 시 알림" 분기(`:126-142`)도 UI 상 도달 불가. 기능 결손(보안 아님).

## ⑤ 보완 방향 (선택지)

### A. 보안 — 방향 무관 **필수** (Critical)
작성 action 에 cohort 소유권 게이트 추가. instructor 면 대상 `studentId` 가 본인 소유 cohort 멤버인지(`cohort_members` 조인, loader 의 `ownsAnyCohort` 재사용) 확인, 아니면 403. manager+ 프리패스. **(과제 feat-7-021b ① 가와 동형, update/delete 는 이미 author-게이트라 create 만 보강.)** 단독 소커밋 권장.

### B. 단방향 유지 + 다듬기 (작은 작업) — 구조상 비례적 **권고**
1. **읽음 표시**: `student_notes.read_at`(또는 `note_reads`) 추가 → `/me/consult` 진입 시 본인 공유 노트 read 마킹 → 강사 `NoteRow` 에 "읽음/안읽음·읽은 시각" 배지. 강사가 전달 여부를 앎(상담 피드백 루프 최소 복원).
2. **마크다운 렌더**: 평문 → `MarkdownView` 교체(강사·학생 양쪽). **단 ③의 XSS 전제** — 이 표면은 `rehype-raw` 끄거나 `rehype-sanitize` 적용한 변형으로. placeholder 약속 이행.
3. **(선택) 편집 UI**: `NoteRow` 에 편집(본문·노출·핀) — 이미 있는 `update` intent 활성화.

### C. 양방향(답글) — 큰 작업, **지금은 비권고**
스키마부터: 답글/스레드(`parent_id` 또는 messages 테이블) + 학생 작성·답글 API + RLS(학생은 *자기에게 공유된* 노트에만 답글) + 강사 알림(`note_reply`) + 강사 인박스 노출 + 스레드 뷰. "코멘트/노트" → "메시지 스레드" 로 모델 전환. **진짜 상담 대화가 제품 요구로 확정될 때 별도 feat 로.** (현 구조 근거상 선제 도입은 YAGNI.)

### 권고 요약
- **A(보안)는 즉시·필수**(방향과 무관, Critical).
- 소통 보완은 **B(읽음+마크다운)**가 구조·비용 대비 합리적. C(양방향)는 제품 결정이 선 뒤.
- 순서 제안: **A → B-1(읽음) → B-2(마크다운, 안전하게)**. C 는 보류.
