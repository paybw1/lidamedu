# 과제(assignments) 점검 — 기술 건강성 + 운영/사용 가치 (읽기 전용 · 코드 0)

> 작성 2026-06-18 · 방법: `assignments/queries.server.ts` 전문 정독 + admin 화면·action 권한 게이트(서브에이전트) + 학생 화면 UX(서브에이전트) + 운영 DB RLS 직접 조회. 라인 근거 표기.
> **헤드라인(★Critical)**: 모든 과제 서버 함수가 `adminClient`(RLS 우회)로 동작하고 권한은 caller(loader/action)에 위임된다. **화면 loader는 cohort 소유권을 검증하지만, 쓰기 action(`/api/admin/assignment`)은 "staff인지"만 보고 소유권을 일절 검증하지 않는다** → 한 강사가 **다른 강사 반의 과제를 생성·수정·삭제**할 수 있다(action 직접 호출 시). RLS는 소유권을 강제하도록 올바로 설계돼 있으나 service-role 쓰기가 그것을 우회한다.

## ① A. 기술 건강성

### 1.1 ★ service-role 사용처 + 권한 구멍 (Critical)

**구조**: `assignments/queries.server.ts:8` 전 함수가 `adminClient`(service_role, RLS 우회). 파일 주석(`:1-3`): *"staff 권한 검사는 caller(loader/action) 선행. 함수 내부 admin client 우회."* → **보안은 전적으로 loader/action 게이트에 의존.**

| 경로 | 게이트 | 판정 |
|---|---|---|
| 학생 목록 `listStudentAssignments` | 본인 cohort 만 조회(`:686-691`) | ✅ 자기 것만 |
| 학생 상세 `getStudentAssignment` | **함수 내부**에 cohort 멤버십 검증(`:755-761`, 비소속→null) | ✅ 견고(드물게 함수 자체가 게이트) |
| 강사 화면 loader (`admin-cohort-assignments`·`admin-assignment-edit`) | `if (!roleAtLeast(role,"manager") && cohort.ownerId !== user.id) 403` (`:57-59`/`:73-75`) | ✅ 소유권 검증(원장/관리자는 전체, 강사는 본인 반만) |
| **쓰기 action `api/admin/assignment`** | `getStaffRole` 만(`:61-62`). 소유권/owner_id/roleAtLeast **0** | ❌ **구멍** |

**★ 구멍 상세**: action의 6개 intent(`create`/`update`/`delete`/`upsert_item`/`delete_item`/`convert_week`)가 폼에서 `cohortId`·`assignmentId`·`itemId`·`weekId`를 받아 **소유권 검증 없이** 바로 서버쿼리(adminClient)에 넘긴다.
- `update`/`delete`/`upsert_item`: `assignmentId`만 믿고 처리 — 그 과제가 어느 반인지 역추적조차 안 함.
- `delete_item`: **`itemId`만** 받음 — cohort로 거슬러 갈 단서도 없음(최악).
- `convert_week`: 입력 `cohortId`로 곧장 새 과제 insert.
- → **강사 A가 `/api/admin/assignment`에 다른 반 id로 POST하면 그 반 과제를 마음대로 조작.** 화면 loader 게이트는 그 화면 폼을 거칠 때만 적용되며 action 직접 호출로 우회된다. (student는 `getStaffRole`=null→403이라 차단 — 구멍은 **강사↔강사 수평 권한 상승**.)

**RLS는 올바른데 우회됨**(운영 mcgdoplo 조회): `assignments_owner_all`(ALL) = `user_owns_cohort(cohort_id, auth.uid()) OR is_manager(auth.uid())`, `assignment_items_owner_all`도 동일, `assignment_submissions_self_rw`(본인만). **즉 요청 클라이언트(RLS)로 썼다면 DB가 교차-반 쓰기를 막았을 것** — 그러나 쓰기 함수가 `adminClient`라 RLS가 발동 안 함. → 안전망이 있는데 service-role이 비활성화시킨 형태.

**학생이 남의 과제 데이터를 보나? → 아니오.** 학생 경로는 본인 cohort·본인 submission만 노출. 상세는 cohort 집계(`totalMembers`/`completedMembers`)만 보이고 타 학생 개별 진척은 안 보인다. `assignment_submissions` RLS도 `self_rw`+`staff_read`(소유 반만). **학생 측 누수 없음.** 위험은 staff 쓰기 경로 단 하나.

### 1.2 N+1 / 성능 (Warning, 규모 시 악화)

- `recomputeSubmission`(`:428`)이 (과제×학생)당 **~5쿼리** 실행: items + 정답 + **study_sessions 스캔(`.limit(5000)`)** + 빈칸 + 암송.
- `listStudentAssignments`(`:705-707`): 학생의 **모든 과제를 매 로드마다 recompute** → N개 과제 = N회 recompute = **N회의 5000행 study_sessions 스캔**(중복). 과제 수에 선형.
- `listAssignmentProgress`(`:622-624`): 한 과제 진척 보기에 **전 멤버 recompute** → M명 = M회 recompute(M회 세션 스캔). 강사가 cohort의 한 과제 진척을 열면 M×5쿼리.
- **캐시·throttle 없음**: `last_checked_at`가 있는데도 신선도 체크 없이 **매 로드 무조건 재계산·재upsert**. submission 테이블은 결과를 저장하나 recompute는 항상 다시 돈다.
- 비용 = 학생목록 O(과제수), 강사진척 O(멤버수), 각 recompute에 5000행 세션 스캔. 반 인원·과제 누적될수록 강사 진척 화면이 무거워진다.

### 1.3 ★ study_sessions `.limit(5000)` 무정렬 → 완수 오판 (Warning/정확성)

`recomputeSubmission`(`:481-485`)의 세션 스캔은 `.limit(5000)`에 **ORDER BY 없음**. 세션 5000건 초과 사용자는 임의의 5000건만 반환 → **실제 열람한 조문/판례가 그 5000건에 안 들면 "미완"으로 오판**("했는데 미완"). 헤비 유저에서 article_read/case_read 완수가 틀릴 수 있다.

### 1.4 마감 처리 (의도 확인 필요)

- `recomputeSubmission`은 **`due_at`를 전혀 안 본다**. 완수는 순수 활동 기반 — **마감 지나도 완수 판정 계속**, late/overdue 상태 없음.
- `completed_at`(`:557`)을 **recompute마다 `now()`로 덮어씀** → "완료 시각"이 실제 완료가 아니라 "마지막 재계산 시각"으로 표류(사실상 무의미).
- 마감은 **표시 전용**(목록/상세에 절대시각 + "(지남)" 텍스트). 잠금·late 마킹 없음. → 과제가 "강제"가 아니라 "권장"이면 OK지만, 강사가 "마감 내 완료 vs 지각 완료"를 구분할 방법이 없다.

### 1.5 에러 처리

- 쿼리 함수 일부 `throw`(목록/상세) → loader 전파 → **루트 ErrorBoundary**(`root.tsx:298`, 404→`<NotFound/>`). 화면별 ErrorBoundary는 **없음**(assignments 전체 0건).
- 학생 상세 null(없음 OR 비소속)은 **동일 404**로 수렴 — 정보 노출은 막지만 "없음 vs 권한없음" 구분 불가, loader가 넣은 한국어 메시지도 NotFound 화면에선 안 보일 공산.
- `upsertSubmission` 에러는 **삼킴**(로그+null 반환) → recompute가 조용히 저장 실패해도 화면엔 안 드러남.

## ② B. 운영/사용 가치

### 2.1 학생 경험

**자동 완수 판정 기준**(`recomputeSubmission:537-556`):
| 종류 | 완료 조건 | 정확성 평가 |
|---|---|---|
| 객관식(problem) | 한 번이라도 정답 | 합리적(체크 의미) |
| 조문(article_read) | study_sessions 열람 1회 | ⚠️ **열람=완료** → 실수로 잠깐 열어도 완료("안 했는데 완료"). 5000행 한계 시 반대로 오판도. |
| 판례(case_read) | 열람 1회 | 동일 |
| 빈칸(blank_set) | 전 칸 1회 이상 정답 | 엄격(좋음) |
| 암송(recitation) | is_complete 1회 | 합리적 |

**"제출 없이 자동 완수"를 이해하나? → 부분적·불투명.**
- 항목별 **종류 라벨**(조문 학습/판례 학습/객관식/빈칸/암기)과 **"학습하러 가기" 진입 링크**는 있다 → "어디로 가나"는 안내됨.
- 그러나 **"무엇을 하면 이 항목이 완료되나"(열람/정답/전칸정답/암송) 설명이 화면에 한 줄도 없다** → 자동 판정이 블랙박스. "재확인" 버튼(loader 재호출로 recompute)으로 갱신은 가능.
- `entryUrl=null` 항목(매핑 실패)은 **링크도 안내도 없는 회색 카드** = 막다른 길.

**남은 것 파악 → ★불가(가장 큰 UX 결함).** 상세의 모든 항목이 **항상 빈 원**(`CircleIcon`) — 완료 항목도 체크로 안 바뀐다. 근본 원인: **데이터에 항목별 done 플래그가 없음**(`labels.ts`의 `AssignmentItem`에 completed 필드 없음; recompute는 per-item done을 계산하지만 **집계 카운트만 저장하고 버림** `:539-553`). → 학생은 "5중 3 완료"는 알아도 **"어느 2개가 남았는지"를 화면에서 알 수 없다.**

**마감 표시**: 절대시각 + 경과 시 빨강 "(지남)"뿐. 남은 시간(D-N)·임박 경고·카드 강조 없음.

### 2.2 비종합반(cohort 미소속) 학생

- 라우트 가드(`study-management.layout`)는 **구독(feature)만 검사, cohort는 안 봄** → 반 미배정이어도 화면 진입.
- 데이터는 빈 배열 → **"진행 중인 과제가 없습니다."** 표시. → **"과제 0건"과 "반 미배정"을 구분 못 함.** 미배정 학생은 원인·연락 경로를 모른다(숨김은 정상이나 안내 부재).

### 2.3 강사 경험

- **생성/관리**: `admin-assignment-edit`에서 intent 기반 CRUD(생성/수정/삭제/항목 upsert·delete) + **커리큘럼 주차→과제 자동 변환(`convert_week`)** — 주차 항목을 그대로 과제로 떨구는 생산성 기능(lecture 종류는 자동채점 불가라 skip). 항목은 조문/판례/문제/빈칸/암송 5종을 붙인다.
- **진척 보기**: `admin-cohort-assignments`가 `listAssignmentProgress`로 **멤버별 이름·이메일·상태·완료 X/Y·완료시각**을 표로(이메일은 admin listUsers, throw 방어). 유용하나 (a) **열 때마다 전 멤버 recompute로 무겁고**(2.1.2), (b) `completed_at` 표류로 "언제 끝냈나"가 부정확, (c) "마감 내 vs 지각" 구분 없음.
- 쓰기 편의는 기능상 충분(주차 변환이 특히 강점)하나 **권한 게이트 누락(1.1)이 운영 신뢰성의 약점**.

## ③ 보완 방향 (렌즈별 · 선택지 · 코드 0)

### A. 기술 건강성
1. **★Critical — action 소유권 게이트(필수)**: `/api/admin/assignment`의 각 intent에서 화면 loader와 동일하게 `getCohortById` + `roleAtLeast(manager) || cohort.ownerId===user.id` 검증. `assignmentId`/`itemId`만 받는 intent는 cohort 역추적(또는 폼에 cohortId 동반). **대안**: 쓰기 함수를 요청 클라이언트(RLS)로 전환 → 이미 올바른 RLS(`*_owner_all`)가 자동 강제(adminClient 폐기). 둘 중 하나는 반드시.
2. **N+1/캐시(Warning)**: recompute에 신선도 가드(`last_checked_at` 최근이면 skip) 또는 활동 기록 시점에만 갱신(이벤트 기반). 강사 진척은 멤버 일괄 1쿼리화 검토.
3. **세션 스캔 정확성**: `.limit(5000)` 무정렬 제거 — 필요한 article/case id로 **타깃 조회**(`scope` 필터 또는 정렬+범위)로 바꿔 오판·중복스캔 동시 해소.
4. **마감 정책(의도 결정)**: (a) 현행 유지(권장형, 활동기반) / (b) `completed_at`을 최초 완료시 1회만 고정 + late 플래그(마감 후 완료 구분) / (c) 마감 후 잠금. → **결정 후** 진행.
5. 화면별 ErrorBoundary + "없음 vs 권한없음" 메시지 분기(선택).

### B. 운영/사용
6. **★항목별 완료 체크(최대 가치)**: recompute가 이미 아는 per-item done을 버리지 말고 노출 — `AssignmentDetail.items[].done` 추가 → 상세에서 완료 항목 체크/미완 강조. "어느 게 남았나"를 학생이 즉시 파악. (자동 완수 모델의 핵심.)
7. **완료 조건 안내**: 항목 종류별 "이렇게 하면 완료" 한 줄(열람/정답/전칸/암송). 블랙박스 해소.
8. **비종합반 안내**: cohort 미소속이면 목록에서 "아직 반에 배정되지 않았습니다 — 문의" 전용 빈 상태(현 "과제 없음"과 구분).
9. **마감 표시 강화**: D-N/남은시간 + 임박 강조(선택, 6·7 다음).
10. `entryUrl=null` 항목: 운영자 편집 시 경고 또는 학생 화면에서 "준비 중" 명시.
