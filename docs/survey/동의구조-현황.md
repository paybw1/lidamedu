# 동의 구조 현황 (조사) — 학습데이터·합격자 분석

> 읽기 전용 조사. **코드·DB 변경 0.** 실제 경로·컬럼·값 확인 기준 (운영 DB mcgdoplo, 조사 시점).
> 핵심: §4(동의를 쓰는 모든 지점)·§5-A(자동 동의 시 바뀔 곳)는 누락 시 합격자 분석이 조용히 틀어지므로 빠짐없이 정리.

## 0. 한 줄 요약

동의는 **`profiles` 의 두 컬럼**으로 분리돼 있다 — `service_data_consent_at`(**필수**, 서비스 이용 전제) / `analytics_consent_at`(**선택**, 합격자 분석·후기 포함). "응시결과" 노드 동의 = **선택(analytics)** 동의 하나. 합격자 분석 전체가 `analytics_consent_at IS NOT NULL` + `is_synthetic≠true` + `status='passed'` 의 교집합으로 게이트된다. 현재 오픈 전이라 **exam_results 0건, 실 합격 동의자 0명 → 합격자 비교 게이트 OFF**.

## 1. 동의 데이터 — 어디에 어떻게 기록되나

### 1.1 컬럼 (둘 다 `profiles`)

| 컬럼 | 타입 | 의미 | 값 |
|---|---|---|---|
| `profiles.service_data_consent_at` | `timestamptz \| null` | **필수** 동의(학습 데이터 처리 = 서비스 이용 전제, PIPA 15①4 계약 이행). 미동의 학생은 서비스 이용 불가 | 동의 시각 / `null`=미동의 |
| `profiles.analytics_consent_at` | `timestamptz \| null` | **선택** 동의(학습 로그+시험 결과 익명·집계 → 합격자 패턴 분석·진단·컨설팅·후기 공개). 거부해도 이용 제한 없음 | 동의 시각 / `null`=미동의·철회 |
| `profiles.is_synthetic` | `boolean` | 시드/합성 계정 표식 — 합격자 표본에서 제외 판정용(동의 컬럼은 아님) | — |

> 두 동의는 **완전 별개**다(코드 주석 `exam-results/queries.server.ts:176-179`). exam_results 테이블에는 동의/합성 컬럼이 **없고**, 분석은 항상 `exam_results → profiles` 조인으로 동의·합성을 본다.

### 1.2 기록 경로 (set 함수)

`app/features/exam-results/queries.server.ts`:
- **필수** — `setServiceDataConsent(client, userId)` (181-191): `service_data_consent_at = now()`. **grant 전용**(철회 set 없음 — 철회는 계정 해지/문의).
- **선택** — `setAnalyticsConsent(client, userId, consented)` (161-174): `analytics_consent_at = consented ? now() : null`. **on/off 토글**(철회 = `null` 세팅).

동의를 세팅하는 화면·액션:

| 동의 | 화면/경로 | 동작 | 비고 |
|---|---|---|---|
| 필수 | `/join` 가입 (`auth/screens/join.tsx`) | 가입 액션에서 `setServiceDataConsent` (64-66) | 이메일가입 체크박스 2개 모두 **[필수]**, 소셜은 푸터 고지로 묵시 동의 |
| 필수 | `/consent` 게이트 (`onboarding/screens/consent.tsx`) | POST → `setServiceDataConsent` (50) | 미동의 학생 강제 리다이렉트 대상(§1.4). 스킵 없음 |
| 선택 | `/me/exam-results` (`exam-results/screens/my-exam-results.tsx`) | 라우트 action `intent="consent"` → `setAnalyticsConsent` (139-145) | "동의하기/동의 철회" 토글 카드 |
| 선택 | `/onboarding/welcome` Step2 (`onboarding/screens/welcome.tsx`) | action `intent="consent"` → `setAnalyticsConsent` (124-131) | "(선택)" 단계, 스킵 가능 |

> 선택(analytics) 동의의 set 진입점은 **위 두 화면의 라우트 action** 둘뿐(별도 `api/` 없음). 시드 스크립트 `exam-results/seed.server.ts:123` 는 합성 합격자에 `analytics_consent_at` 을 채우지만 `is_synthetic=true` 라 실표본 게이트엔 안 잡힌다.

### 1.3 현재 동의자 수 (실측, 오픈 전)

`profiles` 38행(학생 26):
- **service_data_consent_at 보유 = 1** (게이트 적용 전 단계 / 거의 미수집)
- **analytics_consent_at 보유 = 7** (전부 실계정 — `is_synthetic` 7건 중 0건)
- `is_synthetic = true` 프로필 = **0** (현 운영DB엔 합성 계정 없음 → `excludeSynthetic` 필터는 현재 사실상 no-op)
- `exam_results` = **0행** (passed 0 / failed 0) → 시험 결과 자체가 아직 없음

### 1.4 미동의 게이트 / 철회 경로

- **필수 게이트**: `core/lib/require-consent.server.ts` `requireServiceDataConsent()` — `private.layout` / `dashboard.layout` loader 에서 호출. 미동의 **학생**을 `/consent` 로 redirect. staff(instructor↑) 면제, `/consent`·`/logout`·`/api` 접두는 통과.
- **선택 철회**: `setAnalyticsConsent(_, _, false)` → `analytics_consent_at=null`. 화면 문구상 "철회 시 다음 분석 배치부터 제외". UI: `/me/exam-results` "동의 철회" 버튼, onboarding Step2 "지금은 동의 안 함".
- **필수 철회**: UI 없음 — 계정 해지/문의로만(코드·문구 명시).

## 2. "응시결과" 노드 동의 — 문구·범위

화면: `/me/exam-results` → `exam-results/screens/my-exam-results.tsx` (라우트 `routes.ts:628-631`). 동의는 **선택(analytics) 단일 토글** — 항목별 체크박스 아님. 동의 안 해도 화면 사용 가능(동의는 합격자 표본 포함 여부만 좌우).

**헤더 안내** (192-201):
> 변리사 1·2차 시험 결과를 연도·차수별로 기록합니다. 인증된 데이터는 학습 패턴 분석에 익명·집계 형태로 활용됩니다. 상세 약관 → (`/legal/analytics-consent`)

**동의 카드 본문** (254-259, 제목 "학습 데이터 분석 활용 동의"):
> 본인의 학습 로그(문제 풀이, 조문 열람, 빈칸/암기, 강의 시청 등)와 시험 결과를 **익명화·집계**하여 합격자 학습 패턴 분석 및 다른 학생의 진단·컨설팅에 활용하는 데 동의합니다. 동의는 언제든 철회할 수 있으며, 철회 시 다음 분석 배치부터 본인 데이터는 제외됩니다.

→ **하나의 동의가 "학습 로그 + 시험 결과" 둘 다를 묶고 있다**(분리 안 됨). 이게 §5-B 분리의 핵심 지점.

### 2.1 가입/온보딩 동의 단계

- **가입(`/join`)**: 필수 체크박스 2개 — ① "[필수] 이용약관 및 개인정보처리방침 동의", ② "[필수] 학습 데이터 활용 동의 (서비스 제공·진단·가명처리 분석)". 가입 시 **`service_data_consent_at` 만** 세팅(필수). **선택 analytics 동의는 가입에서 안 받음.** 소셜 가입은 체크박스 없이 푸터 고지로 묵시.
- **온보딩(`/onboarding/welcome`) Step2 "합격자 비교 표본 포함 (선택)"**: 필수 동의는 "가입 시 완료" 안내 후, **선택 analytics 동의만** 받음("동의하고 계속"/"지금은 동의 안 함", 스킵 가능). 데이터 범위: 문제 풀이·조문/판례 열람·빈칸/암기·강의 시청·본인 시험 결과(입력 시).
- **`/consent` 게이트(필수)**: "학습 데이터 기반 진단·합격자 비교 컨설팅 ... 동의해 주셔야 이용". 데이터 항목 = 문제 풀이·열람 이력·빈칸/암기·강의 진행률·학습 메타데이터. "합격 결과 인증(합격증 제출)은 **별개의 선택 사항**". 스킵 없음.

> 필수/선택 구분은 UI상 명확("[필수]" 라벨, "(선택)" 단계, "거부해도 이용 제한 없음").

## 3. 합격 여부(exam_results) — 분석과 어떻게 연결되나

### 3.1 구조 (`exam_results`, 동의/합성 컬럼 없음)

`result_id`(uuid PK) · **`user_id`(uuid → profiles.profile_id)** · `exam_year`(int) · `exam_round`(enum `first`/`second`) · **`status`(enum `absent`/`pending`/`failed`/`passed`)** · `self_reported_total_score`(numeric) · `self_reported_subject_scores`(jsonb) · `verification_status`(enum `self_reported`(기본)/`document_submitted`/`verified`/`rejected`) · `certificate_url`·`certificate_path`·`verified_by`·`verified_at`·`rejection_reason` · `study_summary_md` · `created_at`·`updated_at`.

- **입력**: `upsertMyExamResult` (자기보고, `verification_status` 기본 `self_reported`). 합격증 제출 시 staff 검증 → `verified`. (입력 시점에 동의를 받지 않음 — 동의는 profiles 컬럼.)
- **합격 여부 = 누구 것**: `exam_results.user_id` 로 본인 연결.

### 3.2 분석에서 "합격자"를 가르는 기준

`status = 'passed'` 인 exam_results 행을, 조인된 `profiles.analytics_consent_at`·`is_synthetic` 로 추가 필터. **합격 여부 활용에 별도 동의 컬럼은 없다 — analytics_consent 하나에 포함**(§2 문구가 "시험 결과"까지 묶음). 즉 합격/불합격 활용 = analytics 동의 + status.

## 4. ★ 합격자 분석이 동의를 쓰는 지점 (영향 범위 — 빠짐없이)

핵심 파일 `app/features/exam-results/analytics.server.ts` (1432줄). **세 개의 독립 필터**가 항상 함께 작동:
1. **status** — 서버 `.eq("status","passed"|"failed")`.
2. **consent** — `analytics_consent_at !== null`. 두 층위: (a) `onlyConsented` 옵션 = 행 자체 제거 / (b) 옵션과 무관하게 **집계(aggregates)는 항상 동의자만**(비동의 행은 `aggregates=null`).
3. **synthetic** — `is_synthetic`. `excludeSynthetic` 옵션. **모든 함수의 기본값 = false(합성 포함)** — 학생 화면 caller 가 매번 `excludeSynthetic:true` 를 명시해서 막는다(빠뜨리면 합성 누수).

### 4.1 게이트 — `passer-benchmark-gate.server.ts` `isPasserBenchmarkEnabled(round?, year?)`

.eq("status", "passed")  // (+ round/year 옵션)
realSampleSize = rows.filter(r =>
  r.profiles?.analytics_consent_at !== null && r.profiles?.is_synthetic !== true).length
enabled = realSampleSize >= PASSER_BENCHMARK_MIN_SAMPLE   // = 10

- **현재 0/10 → OFF**(exam_results 0행). 에러 시 fail-closed(OFF).

## 5. 변경 설계 — A/B 대칭 동의 (합의안)

> 법적 문구·"필수 흡수" 적법성은 **placeholder**(전문가 확인 예정). 여기선 구조·코드 매핑만.

### 5.1 동의 3축

- **필수 `service_data_consent_at`(현행)** — 계정·서비스 운영(로그인·콘텐츠·결제). **분석 게이트 아님.** 학습로그를 여기 통째 흡수하지 않음(= 전원 강제 풀 / 타인활용 강제 쟁점 회피).
- **A `my_analysis_consent_at`(신규)** — 내 데이터로 **내** 분석만(학습통계·OX진단·복습·암기). 남 풀 불필요. **기본 ON**, 철회 시 "이 기능들 꺼짐" 명확 안내. 식별성 낮음 → 대부분 동의 예상.
- **B `pool_consent_at`(신규)** — 내 데이터 **풀 기여 ↔ 합격자·동료 대비 비교 열람**. **대칭**(철회 시 기여·열람 동시 중단). opt-in. 합격자 패턴·컨설팅·공개통계·후기 기여도 B.

### 5.2 A 게이트 대상 (own-data — `analytics.server.ts` 밖)

학습통계(`study/screens/stats`)·OX진단(`study/lib/ox-diagnosis.server.ts` `computeOxDiagnosis`)·복습 SRS 큐(`/study/srs`)·암기 플래시카드(`/srs`). **현재 무게이트(service로 덮임)** → A로 게이트. 기본 ON, 철회 시 off + 안내.

### 5.3 B 게이트 — 기여/열람 분리 (대칭의 핵심)

**기여**(누구 데이터가 풀에 들어가나) / **열람**(누가 결과를 보나)을 따로 건다.

| 함수 | 기여 게이트 | 열람 게이트 | 현재 → 변경 |
|---|---|---|---|
| `isPasserBenchmarkEnabled`(게이트) | **B** 합격자(`status=passed × B × ¬synthetic ≥ 10`) | — (전역) | `analytics_consent`→**B** |
| `listPasserCases`/`listFailerCases` | **B**(`onlyConsented`→onlyB) | 내부/admin | →B |
| `getPasserPoolStats` | **B** count | admin | →B |
| `computePasserAggregateStats` | **B** | admin | →B |
| **`getPasserBenchmarks`** | **B** 합격자 | **★ B(요청자)** | 기여 B + **열람 B 신설** |
| **`getPasserLawAverages`** | **B** | **★ B(요청자)** | 기여 B + **열람 B 신설** |
| **`getPasserTrendData`** | **B** | **★ B(요청자)** | 기여 B + **열람 B 신설** |
| **`getFailerBaseline`** | **B**(failer) | **★ B(요청자)** | 기여 B + **열람 B 신설** |
| **`passer-srs-benchmark`** | **B** | **★ B(요청자)** | 기여 B + **열람 B 신설** |
| `listPasserSummaries`(후기) | **B**(요지 공유) | 익명 공개읽기 | 기여만 B |
| `getPublicPlatformStats`(공개) | **B** | 비로그인 공개 | 기여만 B |
| `computeGroupComparison`(admin) | **B**(양측) | admin | →B |
| `computeAggregates`/`fetchPasserActivity`/`baselineFromCases`(내부) | 상위 상속 | — | 상속 |

### 5.4 ★ viewer-B 게이트 신설 (이 작업의 핵심 — 빠뜨리면 대칭 붕괴)

- **비교 열람** = `getPasserBenchmarks` · `getPasserLawAverages` · `getPasserTrendData` · `getFailerBaseline` · `passer-srs-benchmark` (화면: dashboard · goals · study/srs · passer-trend).
- **현재 코드엔 viewer 측 동의 체크가 없다** — 전역 `isPasserBenchmarkEnabled` 게이트만 있어, 게이트 ON이면 **비동의자도 비교를 봄** = 기여 안 하는데 열람 = 비대칭.
- **신설**: 위 화면 loader 에서 요청자의 `pool_consent_at` 확인 → 미동의면 benchmark/trend 호출 skip + 비교 카드 미노출(대신 "B 동의 시 비교 제공" 안내).
- **대칭 성립**: B 철회 → (1) **열람 차단**(viewer-B) + (2) **풀 제외**(기여 B 필터) 동시. 둘 다 같은 `pool_consent_at` 한 컬럼이 좌우.

### 5.5 후기·공개통계 — 기여만 B, 열람 개방 (확정된 비대칭)

`listPasserSummaries`(후기)·`getPublicPlatformStats`(공개)는 **익명·공개**라 열람엔 B 불요. 단 **내 데이터가 거기 들어가는 기여는 B**. ("비교"=상호적 → 기여자만 열람 / "공개 익명 통계"=누구나 열람.)

### 5.6 DB·기존자·철회

- `profiles`: `analytics_consent_at` → **`my_analysis_consent_at`(A) + `pool_consent_at`(B)** 2컬럼 신설. (전환기엔 병행 후 제거.)
- 기존 `analytics_consent_at` 동의 **7명**: 현 문구가 풀·후기·컨설팅을 포함하므로 **B로 매핑** + **A**(식별성 낮음)도 ON. (소급 매핑 적법성 = placeholder, 전문가 확인.)
- 신규 가입: **A 기본 ON / B opt-in**(가입·온보딩 Step2·응시결과 카드를 A/B 2항목으로).
- 철회 경로 유지: A·B 모두 토글(=null). 필수(service)는 계정 해지로만(현행).

### 5.7 단계별 구현 계획 (각 단계 멈춰 보고 → 승인 후 다음)

| 단계 | 내용 | 산출/검증 |
|---|---|---|
| 0 | 설계 확정 | ✅ (이 문서) |
| 1 | **컬럼 신설 + 마이그** — `my_analysis_consent_at`·`pool_consent_at` + 기존 7명 매핑 백필 + `set/get` 함수 + typegen | 마이그 적용·동의자 수 실측·typecheck |
| 2 | **기여 필터 B 교체** — §5.3 기여 게이트 전부(`analytics_consent_at`→`pool_consent_at`) + 게이트 + passer-srs (열람은 아직 손X) | 합격자 풀이 B 기준으로 좁혀지는지(현재 데이터로) |
| 3 | **★ viewer-B 게이트 신설** — 비교 화면 loader 에 요청자 B 체크 → 미동의면 비교 미노출 | B 철회자=비교 안 보임 + 풀 제외 (대칭 동작 확인) |
| 4 | **A 기능 게이트** — 학습통계·OX진단·복습·암기에 A 체크 + 철회 시 off 안내 | A 철회 시 해당 기능만 off, 나머지 정상 |
| 5 | **문구/UI/마이그 마무리** — 가입·온보딩·응시결과 2항목(A/B) + 법령 MDX(placeholder) | 동의 UI 일관·기존자 매핑 확정 |
