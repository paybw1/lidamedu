> 읽기 전용 점검(코드 변경 0). 고도화 방향 결정용 재료. 조사일 2026-06-22.
> 근거는 파일:라인. RLS는 운영 DB(`mcgdoplo`) `pg_policies` 라이브 확인. 사실/추측 구분 표기.

## 0. 한눈 요약 (TL;DR)

- **"1차 진도별 모의고사"는 `mcq_packs.kind = 'mock_progressive'` 라벨일 뿐**, 진도(progress)에 연동되거나 출제 범위를 단원으로 한정하는 구조가 **전혀 없다**. `mock_full`(전체)과 코드·데이터상 차이 0 — 표시 텍스트와 진입 쿼리(`?kind=`)만 다르다.
- **"+문제집 추가"는 2단 구조다.** ⓐ 버튼 → `PackForm`은 **팩 껍데기(메타데이터)만** 만든다(문제 선택 없음). ⓑ 팩 상세에서 `MockPackProblemPicker`로 **개별 문제를 수동 검색·다중선택**해 채운다.
- **전적으로 staff(강사/매니저/원장) 운영 도구.** 학생 셀프 구성 경로 없음. 자동 생성은 기출(past_exam)에 한해 메타 기반으로만.
- **출제 입력에 학습자 데이터(진도·약점·차수·오답·즐겨찾기)를 0건 참조한다.** 100% 수동 picker + 기출 자동(메타)뿐.
- 연동 가능한 진도·약점·차수·풀 통계 함수는 **이미 다 존재**한다(§4). 고도화는 "새로 만들기"보다 "기존 추출 함수를 출제 입력으로 연결"에 가깝다.

### 1.3 kind 분기 (`mcq.tsx`)

화면은 `?kind=` 쿼리로 종류를 나눈다. **kind enum 4값**(DB 컬럼, `app/features/mcq-packs/labels.ts:3-7`):

```
past_exam=기출문제 | mock_full=전체 모의고사 | mock_progressive=진도별 모의고사 | other=기타
```

제목 매핑(mcq.tsx:183-190): `mock_progressive`→"1차 진도별 모의고사", `mock_full`→"1차 전체 모의고사", `past_exam`→"1차 기출문제"(기본값). `?kind=mock`은 DB값이 아닌 **가상 묶음**으로 mock_full+mock_progressive union 조회(mcq.tsx:143-146). 메뉴 "모의고사▾"에서 종합=`?kind=mock_full`, 진도별=`?kind=mock_progressive`, 기출=`?kind=past_exam`로 진입(feat-10-003) — **라우트·DB 동일, 쿼리만 다름**.

### 1.4 데이터 모델 (검증함 · `database.types.ts:3964-4073`)

**`mcq_packs`** (1 row = 1 문제집/시험지): `pack_id`(PK), `kind`(plain text — 앱에서 4값 가드), `subject_scope`(patent/trademark/design/civil/civil_procedure/science/industrial), `title`, `description`, `year`, `exam_round_no`(회차 정수), `duration_min`(타이머), `video_url`, `result_doc_url`, `published_at`, `is_published`, `pass_score`(합격선%), `created_by`(FK→profiles), `created_at`/`updated_at`, `deleted_at`(soft-delete).

> ⚠️ **출제 범위/단원/진도 관련 컬럼은 없다.** 위 17개 컬럼이 전부(database.types.ts:4001-4019). scope=과목(subject_scope)이지 단원이 아님.

**`mcq_pack_problems`** (pack↔problem 다대다): `pack_id`(FK→mcq_packs), `problem_id`(FK→problems), `ord`(순서), `created_at`. **PK=(pack_id, problem_id)** 복합. soft-delete 없음(hard delete). FK 둘 다 `ON DELETE CASCADE`.

### 1.5 "진도별"의 의미 — 라벨뿐 (검증함 · 사실)

`mock_progressive`와 `mock_full`은 **데이터·코드상 구조적 차이가 없다**:
- 둘은 `kind` enum의 두 값일 뿐(labels.ts:3-7). 범위 한정 컬럼 부재(§1.4).
- `isMockKind()`가 둘을 **동일 취급**(labels.ts:24-26). 시작 모드도 둘 다 exam(타이머)(mcq.tsx:417-419). 톤·합격선 RPC 공통(SPEC.md:605).
- feat-10-003 문서: "종합/진도별은 `mcq_packs.kind`가 이미 구분, 코드 변경 없이 메뉴 쿼리로만 분리"(feat-10-003:25-30).

→ **"진도별"이라는 의미는 시스템 제약이 아니라 운영 관례다.** 운영자가 "특정 단원까지만 담은 팩"에 `mock_progressive` 라벨을 붙일 뿐, 시스템은 그 범위를 강제·검증·추천하지 않는다.

### 1.6 누가 만드나 — staff 전용 (사실)

- pack/문제 CRUD는 **`instructor`/`manager`/`admin`만**(아래 §2.2). 학생 셀프 생성 불가.
- 학생은 **응시 시작(`/api/mcq-pack/start`)·열람**만. exam(타이머) 모드는 mock 팩만 허용(start.tsx:54-61).
- 자동 생성은 **기출(past_exam)에 한정**: `regeneratePastExamPacks`(mcq-packs/queries.server.ts:554)가 기출 문제를 (과목, 연도)별로 묶어 팩 upsert. **모의(mock_*)에는 자동 생성 없음**(RegenPastExamButton은 `!isMock`일 때만, mcq.tsx:213).

## 2. "+문제집 추가" 동작 (누가·무엇·어떻게·권한)

### 2.1 2단 구조 (핵심 · 사실)

| 단계 | 진입 | 컴포넌트 | 하는 일 |
|---|---|---|---|
| **ⓐ 팩 생성** | `mcq.tsx:214` "+문제집 추가" 버튼 | `PackForm` (mcq.tsx:575-783) | **팩 껍데기(메타)만** INSERT. 인라인 카드 폼(모달 아님). |
| **ⓑ 문제 채우기** | 팩 상세 `/latest/mcq/:packId` | `MockPackProblemPicker` (mcq-packs/components/) | **개별 문제 검색·다중선택**해 일괄 추가 |

> **"+문제집 추가" 버튼 자체는 문제를 고르지 않는다.** `PackForm`의 필드는 구분(kind)·과목·명칭·연도·회차·제한시간·공개여부·합격선 등 메타데이터뿐(mcq.tsx:619-738) — 문제 선택 UI 없음. 문제는 팩을 만든 뒤 상세 화면에서 따로 채운다.

### 2.2 누가 쓰나 — staff 전용 3겹 방어 (사실)

1. **클라이언트 노출**(약): `canEdit = role !== null`(mcq.tsx:151, mcq-pack-detail.tsx:76). `getStaffRole`(laws/queries.server.ts:745)이 role∈{instructor,manager,admin}일 때만 값 반환 → 학생은 버튼·폼·picker 자체가 안 보임.
2. **서버 action 게이트**(주1): `admin/api/mcq-pack.tsx:106` — `if (!role) return 403`. 미인증 401.
3. **RLS**(주2, 운영 라이브 확인):
   - `mcq_packs`: public은 `deleted_at IS NULL AND is_published` SELECT만 / staff는 `is_staff()` INSERT·UPDATE·DELETE.
   - `mcq_pack_problems`: public SELECT `using(true)` / staff `ALL` (`is_staff()`).
   - `private.is_staff()` = `profiles.role ∈ {instructor, manager, admin}`.

→ 뮤테이션이 전부 **요청 컨텍스트 client(RLS 적용)** 이므로 **RLS가 최종 강제력**. action 게이트는 1차 필터/UX.

### 2.3 무엇을·어떻게 추가 (granularity·선택방식 · 사실)

- **단위**: 팩에 **개별 문제(`problems`)**. "문제집(다른 pack)을 통째로" 넣는 건 별개(mcq_exams 교시).
- **선택**: `MockPackProblemPicker` = **수동 검색 + 체크박스 다중선택**. 키워드 2자+ 또는 필터(출처 origin/형식 format/연도) 입력 시 250ms 디바운스 후 `GET /api/admin/search-content?kind=problem&examRound=first&...` 호출. 검색 백엔드(search-content.tsx)는 `adminClient`로 **`review_status='approved' & deleted_at is null`만**, limit 20.
- **진도 필터·랜덤·자동 단원배정 없음.** 단원(node) 기준 필터조차 없다(출처/형식/연도만).

### 2.4 action / 뮤테이션 (`admin/api/mcq-pack.tsx`, intent 분기 · 사실)

| intent | 동작 | 쿼리 |
|---|---|---|

### 2.5 중복 방지·검증 (사실)

- **PK=(pack_id, problem_id)** 가 곧 중복 방지(같은 문제 두 번 불가).
- 코드 멱등: `addPackProblems`가 기존 problem_id 선제외 → `skipped` 보고.
- 콘텐츠 게이트: 추가 시 `review_status='approved'`만(단건·일괄·검색 모두). 미승인 문제 응시풀 유입 차단.
- FK CASCADE: 팩/원본 문제 삭제 시 매핑 자동 정리.

## 3. 한계 / 거친 부분 (고도화 단서)

1. **학습자 데이터 0 연동**(가장 큰 단서). 출제 입력에 진도·약점·차수·오답·즐겨찾기 **어느 것도** 안 쓴다. 100% 수동 picker + 기출 메타 자동뿐(§4 검증).
2. **"진도별"이 이름뿐**(§1.5). 시스템이 진도/단원 범위를 강제·표시·추천하지 않아, 진도별 팩의 일관성이 운영자 기억·관례에 의존. 학생도 "이 팩이 내 진도에 맞나"를 알 길이 없다.
3. **picker가 거칠다**: 단건 키워드 검색 limit 20, 미리보기 = `bodySnippet`(짧은 발문)뿐, **단원/노드 기준 필터 없음**(출처·형식·연도만), 중요도·난이도·약점 필터 없음. 50~100문항 시험지를 수동으로 한 건씩 골라야 함(UX 마찰).
4. **학생 셀프 구성 경로 전무**. 오답/즐겨찾기 기반 풀이는 `quiz_sessions`(개인 복습 러너)로만 흐르고 `mcq_packs`와 단절(§4.5). 학생이 "내 약점 모의고사"를 스스로 만들 수단 없음.
5. **`regen_past_exam`이 수동 보강분을 날린다**: 기존 기출 팩 재생성 시 매핑 전체 삭제 후 재삽입(queries.server.ts:650) → 기출 팩에 수동으로 더한 문제 소실 위험(버튼 confirm에 경고 있음).
6. **`add_problem`(단건) dead code** — 정리 후보.
7. **중복 추가 방지는 같은 팩 내부뿐**. "이 문제가 다른 팩에 이미 있다"는 cross-pack 안내는 없음(수동 출제 시 과목 내 중복 출제 인지 어려움).

## 5. 고도화 후보 + tradeoff (결정용)

> 규모(S/M/L) · 기존 구조 적합성 표기. 현 구조(staff 수동 picker + 라벨뿐 진도별)를 출발점으로.

### 후보 A. picker UX 개선 — **검색·필터·미리보기 강화** (규모 S~M)
- 내용: picker에 **단원(node) 필터** 추가(이미 `getSystematicNodeProblemStats`로 노드별 문제수 보유), 중요도·난이도 필터, limit 상향/페이징, 발문 전체 미리보기, "다른 팩에 이미 포함" 배지.
- 적합성: **높음.** search-content + ListProblemsFilters에 축이 이미 있어 필터만 노출하면 됨. DB 변경 거의 없음.
- tradeoff: 가장 안전·저비용. 다만 "수동" 본질은 그대로 — 출제 효율만 개선.

### 후보 B. 소스 확장 — **오답/약점/단원에서 일괄 추가** (규모 M)
- 내용: 팩 상세에 "약점 단원에서 N문항", "글로벌 난이도 상위 N", "특정 노드 전체" 같은 **소스 버튼** 추가 → 후보를 picker에 채워줌(최종 확정은 운영자).
- 적합성: **높음.** `getWeakNodes`·`listProblemsBySubject`·노드 통계가 이미 있음. `addPackProblems`(배열 삽입)에 그대로 연결.
- tradeoff: 운영자 대상이면 "어느 학생 기준?" 모호(약점은 userId 필요). 학생별이 아닌 **전체 통계(글로벌 난이도·기출 빈도)** 기반 소스가 staff 출제와 자연스럽게 맞음.

### 후보 C. 자동 구성 — **원클릭 모의고사 생성** (규모 M~L)
- 내용: "내 진도까지 N문항", "약점 N문항", "차수(1차) 전과목 모의" 식 자동 편성. 약점·진도·차수·난이도 가중 샘플링.
- 적합성: **중.** 추출 함수는 다 있으나, "어떤 비율로 섞을지" 규칙(가중치)·중복/난이도 균형 로직을 **신규 설계**해야 함. 결과를 새 pack으로 굳힐지(staff) vs 일회성 quiz_session으로 줄지(학생) 결정 필요.
- tradeoff: 가치 큼(수동 → 자동). 출제 품질(난이도 균형·편향)·설명가능성 확보가 관건.

### 후보 D. 학생 셀프 모의고사 (규모 L · 구조 변경)
- 내용: 학생이 자기 약점/진도/오답으로 **자가 모의고사** 생성. 현재 오답/즐겨찾기 러너(quiz_sessions)와 합치거나 별 테이블.
- 적합성: **낮음~중.** 현재 pack은 staff 전용(RLS is_staff). 학생 생성은 RLS·소유권·가시성 **재설계** 필요. 다만 quiz_sessions(scope_type: wrong-note/bookmark/free)에 이미 개인 러너 인프라가 있어, "pack을 새로 안 만들고 세션으로" 가면 규모 축소 가능.
- tradeoff: 학생 가치 최상이나 권한 모델 변경 위험. **pack(영구·공유) vs session(일회·개인)** 중 어디에 둘지가 핵심 결정.

### 후보 E. "진도별"에 실제 의미 부여 (규모 M · 데이터 변경)
- 내용: `mcq_packs`에 **범위(단원/노드 상한 or progress 마일스톤) 컬럼** 추가 → 진도별 팩이 "어디까지"인지 시스템이 알고, 학생 진도와 매칭/추천.
- 적합성: **중.** 마이그레이션 + 출제·표시 로직 추가. 현재 "라벨뿐"의 근본 해소.
- tradeoff: 진도별의 의미를 진짜로 살림. 다만 기존 mock_progressive 팩들에 범위를 소급 입력해야 하고, 운영 부담 증가.

### 조합 권장(참고 · 추측)
- **저위험 빠른 효과**: A(picker 단원/난이도 필터) + B(약점·난이도 소스 버튼). 기존 함수 연결만으로 staff 출제 효율 즉시 개선, DB 변경 최소.
- **큰 그림**: C(자동 구성) 또는 D(학생 셀프)는 "pack에 굳힐까 / session으로 줄까"를 먼저 결정해야 규모가 갈린다. E는 진도별을 진짜로 쓸 거면 선행 필요.
