# 반(cohort)별 커뮤니티 게시판 — 설계용 현황 조사

> **목적**: "반별 게시판" 설계 전 기존 구조 사실 정리. **코드·DB 변경 없음(읽기 전용)**.
> **조사일**: 2026-06-15 · **대상**: 운영 DB `mcgdoplo`(read-only SQL: 스키마·RLS·규모) + 코드(`database.types.ts`·feature 소스).
> **표기**: 사실만. 미구현="미구현", 불명="확인 안 됨".

## 0. 결론 한 줄
**반 구조·소속 기반 RLS·게시판/댓글/첨부 인프라가 전부 이미 존재**한다. 단 ① 학생-반 소속은 스키마상 다대다 가능하나 **현재 데이터는 1반·1:1**, ② 기존 `community_posts` 게시판은 **반 스코프가 전혀 없는 전역** 구조, ③ **반별 타게팅 + 소속 RLS의 직접 선례는 `announcements`·`assignments`** 이며 거기서 쓰는 `user_is_in_cohort()`/`user_owns_cohort()`/`private.is_manager()` 헬퍼를 새 게시판에 그대로 재사용 가능. → "community에 얹기"보다 **assignments/announcements식 cohort 스코프 + community식 글/댓글/첨부 shape 조합**이 코드베이스 일관성에 맞음.

## 1. 반(cohort) 구조 — 접근 단위의 기반 ★

### 테이블 (운영 DB 실측 컬럼)
- **`cohorts`**: `cohort_id(uuid PK)`, `name`, `description`, **`owner_id(uuid NOT NULL)` = 담당 강사**, `starts_on`, `ends_on`, `is_archived(bool)`, `created_at`, `updated_at`, `deleted_at`.
- **`cohort_members`**: `cohort_id(uuid NOT NULL)`, `profile_id(uuid NOT NULL)`, `joined_at`, `added_by(uuid nullable)`. **멤버 역할 구분 컬럼 없음 → 멤버=학생**. PK는 확인 안 됨(코드 onConflict 동작·RLS상 `(cohort_id, profile_id)` 유니크로 추정).

### 소유·소속 판정
- **담당 강사 = `cohorts.owner_id`** (강사가 "내 반"을 owner_id로 인지).
- **학생 소속 = `cohort_members.profile_id`**.
- 강사는 owner_id, 학생은 cohort_members로 **명확히 분리**(코드 주석 `cohorts/queries.server.ts:2`: "admin 전부 / instructor 본인 소유 반 / student 자기 속한 반 read").

### 다대다 여부 ★ (게시판 접근 판정의 핵심)
- **스키마: 다대다 가능.** `cohort_members`는 순수 조인 테이블이고 "학생 1명=1반" 강제 제약이 없음. 한 학생이 여러 반에 속할 수 있는 구조.
- **현재 데이터: 사실상 1:1.** 운영 실측 — **반 1개 · 멤버십 10건 · 학생 10명 · 학생당 최대 1반 · 복수 반 소속 학생 0명**. 즉 다대다는 "지원되지만 미사용"(플랫폼 초기).
- → 설계 시 **다대다를 전제로 RLS·조회를 짜되**(스키마가 받쳐줌), 당장은 1반이라 UX는 단순해도 됨.

### 규모
- 반 1개, 멤버 10명. (강사별 다중 반·다중 강사 운영은 아직 데이터 없음 → "확인 안 됨" 수준.)

## 2. 기존 커뮤니티·공지 — 이미 있나 (얹기 vs 새로)

### (A) 커뮤니티 게시판 = `community_posts` — **전역, 반 스코프 없음**
- 보드: `community_board` enum = **free(자유) / study(스터디 모집) / review(합격 후기)** 3종. (UI 탭은 announce·qna 포함 5개로 보이나, announce/qna는 외부 feature 링크 — 실제 community_posts 보드는 3종.)
- 라우트: `/community/:board[/new | /:postId | /:postId/edit]` (`routes.ts:402-424`), API `/api/community/{post,comment,attachment,report,...}`.
- 화면: `community/screens/{community,community-board,community-post-new,community-post-detail}.tsx` + `components/community-shell.tsx`.
- **접근범위: 전체 공개(인증 회원).** `community_posts`에 cohort/subject 컬럼 없음, `features/community/**`에 `cohort` 0건. → **반별 통제 선례로는 부적합**(반면 사례).

### (B) 공지(강사→학생 일방향) = `announcements` — **반별 타게팅 이미 구현 ★**
- 테이블 3종:
  - `announcements`: `announcement_id, title, body_md, author_id, audience_kind(enum), is_pinned, published_at, ...`.
  - **`announcement_audiences`**: `announcement_id, audience_type(enum), audience_id, added_by, added_at` — **폴리모픽 타게팅**.
  - `announcement_reads`: `announcement_id, profile_id, read_at` (읽음 추적).
- `audience_kind`/`audience_type` = **`all | cohort | user`**. **반별 공지가 실제 동작**(`audience_type='cohort'` + `audience_id=cohort_id`).
- 가시성은 **RLS**가 처리(아래 §4 `announcement_audiences_self_read` 정책 — `user_is_in_cohort(audience_id, auth.uid())`).
- 라우트: 학생 `/announcements`, 운영자 `/admin/announcements`·`/admin/announcements/audiences`.
- **→ "반별 게시판" 타게팅의 가장 강한 선례.** 단 공지는 **일방향**(학생 작성·댓글 없음)이라 쌍방향 게시판엔 글/댓글 인프라를 더해야 함.

### (C) Q&A = `qna_threads` — 대상(조문/판례/문제) 스코프(반 무관). 본 설계와 별개.

**판정**: "반별 게시판"에 딱 맞는 기존 게시판은 **없음(미구현)**. community(전역 게시판 인프라)와 announcements/assignments(반 스코프 + RLS)가 **각각 절반씩** 존재 → 둘을 조합.

## 3. 글·댓글·첨부 데이터 모델 — 재사용 후보

| 자원 | 테이블 | 작성자 | soft-delete | 비고 |
|---|---|---|---|---|
| 게시글 | `community_posts` | `author_id`(FK profiles, ON DELETE SET NULL) | `deleted_at` (RPC `soft_delete_community_post`) | `board` enum·`is_pinned`·`view_count`·study용 `closed_at`/`max_members` |
| 게시판 댓글 | `community_post_comments` | `author_id` | `deleted_at` (RPC `soft_delete_community_comment`) | **`post_id` 직결**(폴리모픽 아님) |
| 좋아요 | `community_post_likes` | — | — | toggle_like |
| 첨부 | `community_post_attachments` | `uploaded_by` | — | 버킷 **`community-attachments`**, kind=image/pdf/file, signed URL |
| 신고 | `community_reports` | — | — | report/resolve |
| 콘텐츠 메모 | `content_comments` | `author_id` | `deleted_at`(직접 update) | **폴리모픽** target_type=article/case/problem. 가시성 "강사=전체공개 / 학생=본인전용" |
| Q&A | `qna_threads` | `asker_id`/`answerer_id` | `deleted_at`(RPC) | — |
| 주석 | `annotations` | userId | `deleted_at`(직접 update) | 메모/북마크/하이라이트 |

- **공통 패턴**: `author_id`(FK profiles, ON DELETE SET NULL → 탈퇴해도 글 보존) + `deleted_at` soft-delete(CLAUDE.md #9). SELECT RLS가 `deleted_at IS NULL`을 강제해 직접 UPDATE soft-delete가 막히는 테이블은 **SECURITY DEFINER RPC**(`soft_delete_*`)로 우회(community·qna 공통; [[soft-delete-rls-rpc]] 메모와 일치).
- **작성자명 표시**: `profiles` RLS가 본인 행만 허용 → 타인 이름 임베드 불가. community는 **`public_profiles` 뷰**(컬럼 4종) batch 조회로 해결. cohorts/admin은 **adminClient(RLS 우회)** 사용. → 반별 게시판에서 멤버 이름 표시 시 동일 제약·해법 필요.
- **첨부 재사용**: `community-attachments` 버킷 + 업로드 API(`/api/community/attachment`, multipart, adminClient.storage, 10MB, jpg/png/webp/gif/pdf, signed URL 조회)는 **추가 작업 없이 재사용 가능**. 공용 업로드 추상 헬퍼는 **미구현**(각 feature가 `adminClient.storage.from(bucket)`을 직접 호출).

## 4. 역할·권한·접근통제(RLS) 패턴 — ★ 가장 중요

### 역할 체계
- enum `user_role` = **student / instructor / manager / admin** (`core/lib/roles.ts`). `ROLE_RANK` student:0<instructor:1<manager:2<admin:3.
- `getStaffRole(client, userId)` (**`laws/queries.server.ts:745`**) = 사실상의 staff 판정 표준. instructor/manager/admin이면 그 값, **학생이면 `null`**. 라우트 loader/action 약 80곳에서 `const role=await getStaffRole(...); if(!role) throw 403;` 반복.
- `roleAtLeast(role, "manager")`로 instructor vs manager+ 추가 분기. `requireMinRole`(guards.server.ts:89, rank 기반). **`requireRole([...])` 배열 시그니처는 미구현**(docs에만 언급).

### 소속 기반 RLS — **이미 성숙, 재사용 가능 ★ (DB 실측 정책)**
DB에 **SECURITY DEFINER 헬퍼 함수**가 있고, 여러 테이블 정책이 이를 사용한다(운영 `pg_policies` 실측):
- `user_is_in_cohort(cohort_id, auth.uid())` — **학생 소속** 판정.
- `user_owns_cohort(cohort_id, auth.uid())` — **강사 담당(owner)** 판정.
- `private.is_manager(auth.uid())` — manager+ 우회.

**실측된 cohort 기반 정책 (그대로 새 게시판에 차용 가능):**
| 테이블 | 정책 | cmd | 조건(qual) 요지 |
|---|---|---|---|
| `cohorts` | `cohorts_member_read` | SELECT | `deleted_at IS NULL AND user_is_in_cohort(cohort_id, uid)` |
| `cohort_members` | `cohort_members_instructor_own` | ALL | `user_owns_cohort(cohort_id, uid)` |
| `cohort_curricula` | member_read / owner_all | SELECT/ALL | `in_cohort OR owns OR is_manager` / `owns OR is_manager` |
| **`assignments`** | `assignments_member_read` / `assignments_owner_all` | SELECT/ALL | **member_read: `deleted_at IS NULL AND (in_cohort OR owns OR is_manager)`** / **owner_all: `owns OR is_manager`** (with_check 동일) |
| `assignment_items` | member_read / owner_all | SELECT/ALL | 부모 assignment의 cohort 기준 EXISTS |
| `assignment_submissions` | staff_read | SELECT | 부모 assignment의 `owns OR is_manager` |
| **`announcement_audiences`** | `self_read` | SELECT | **`(type=user AND id=uid) OR (type=cohort AND user_is_in_cohort(id, uid))`** |
| `exam_results`·`lecture_views`·`pass_prediction_snapshots` | staff_read | SELECT | `is_manager OR EXISTS(cohort_members JOIN cohorts WHERE profile_id=row.user_id AND owner_id=uid)` |

→ **§4 핵심 답: "소속 반 기준 행 접근"을 DB 레벨에서 막는 기존 패턴이 충분히 존재.** `assignments`(cohort_id 직결 + member_read/owner_all)가 **반별 게시판 RLS의 가장 가까운 1:1 템플릿**. 학생=`user_is_in_cohort`, 강사=`user_owns_cohort`, manager+=`private.is_manager`.

### 화면에서만 막고 DB는 여는 사례 (반면교사)
- cohort 멤버·학생 데이터 집계는 **대부분 `adminClient`(RLS 우회)**로 하고 **접근 판정은 코드(loader)의 `owner_id===uid`/role 비교에 의존**(`student-progress.server.ts:1-3`, `cohorts/queries.server.ts:126` 등). 코드 가드가 1차 방어선.
- **갭(주의)**: 일부 staff-공용 action이 cohort 소유 재검증을 **코드에서 안 함** — `api/admin/assignment.tsx`(`getStaffRole`만, 임의 cohortId 수용), `api/admin/student-note.tsx`(담당 학생 검증 없음). 단 `assignments`는 **RLS `owner_all`(with_check user_owns_cohort)**가 DB에서 막아줌 → 코드 갭이 RLS로 backstop됨. (student_note RLS는 본 조사 범위 밖 — "확인 안 됨".)
- → **교훈: 새 게시판은 화면 가드에만 의존하지 말고 `assignments`처럼 RLS(member_read + owner_all)로 DB 레벨 강제**할 것.

## 5. 설계 관점 정리 (조사 근거 기반)

### (a) 반↔게시판 다대다 가능?
- **cohort 구조가 다대다를 받쳐줌**(cohort_members 조인 테이블). 게시판→반 타게팅은 두 방식 다 가능:
  1. **게시판당 단일 cohort_id**(assignments식, 직결·RLS 단순) — 1반 1게시판(들).
  2. **게시판↔반 다대다**(announcement_audiences식 `(audience_type, audience_id)` 폴리모픽) — 한 게시판을 여러 반에 노출.
- 현재 데이터가 1반이라 **(1) 단일 cohort_id 직결이 단순·충분**하고 RLS도 `assignments` 그대로 차용 가능. 다반 노출이 요구되면 (2)로 확장.

### (b) 게시판별 쓰기 권한(공지형 vs 소통형) 자리
- 기존에 **board별 쓰기정책 설정값은 미구현**. 단 announcements(`audience_kind`)·community(roleAtLeast로 pin/close staff 제한) 패턴 재사용 가능.
- 제안: 게시판 행에 `write_scope`(예: `staff_only`=공지형 / `all_members`=소통형) enum 컬럼 + RLS의 INSERT with_check에서 분기(staff_only면 `owns OR is_manager`, all_members면 `in_cohort OR owns OR is_manager`). **신규 설정**이지만 RLS 헬퍼로 구현 용이.

### (c) 접근통제(RLS): 소속 기반 강제 가능?
- **가능(이미 검증된 패턴).** 새 게시판/글 테이블에 `cohort_id` 두고 `assignments`의 `member_read`(`in_cohort OR owns OR is_manager`) + `owner_all`(`owns OR is_manager`) 정책을 복제. 댓글은 부모 글의 cohort 기준 EXISTS(=`assignment_items` 패턴). → **강사=담당 반, 학생=소속 반, manager=전체**를 DB 레벨에서 그대로 강제.

### (d) 기존 커뮤니티에 얹기 vs 새 틀?
- **community_posts에 얹기 = 비권장.** 전역 board enum 구조라 cohort 스코프를 끼워넣으면 "전역 글 + 반 글"이 한 테이블에 섞여 RLS·필터가 복잡(현재 RLS는 전역 공개라 cohort 분기를 새로 더해야 함).
- **권장 = 새 cohort 스코프 테이블** (예: `cohort_board_posts(cohort_id, author_id, title, body_md, is_pinned, deleted_at, ...)` + `cohort_board_comments(post_id, ...)`), **글/댓글/첨부 shape는 community에서 복제**(검증된 author_id/soft-delete/RPC/attachment 패턴), **RLS는 assignments에서 복제**(cohort 헬퍼). community UI 프리미티브(`community-ui.tsx`)·첨부 버킷(`community-attachments`)는 재사용.

### (e) 글·댓글·첨부 — 재사용 vs 신규
- **재사용(패턴/인프라)**: 첨부 버킷·업로드 API(`community-attachments`), soft-delete RPC 패턴, `public_profiles` 작성자명 조회, community UI 프리미티브, RLS 헬퍼(`user_is_in_cohort`/`user_owns_cohort`/`is_manager`).
- **신규(테이블/정책)**: cohort 스코프 게시판·글·댓글 테이블 + 각 cohort RLS 정책 + (선택) `write_scope` 설정 + 게시판 목록/작성 화면.

## 미구현 / 확인 안 됨
- **반별 쌍방향 게시판**: 미구현(community는 전역, announcements는 일방향).
- `cohort_members` PK·유니크 정확 정의: 확인 안 됨(동작상 `(cohort_id, profile_id)` 추정).
- 게시판별 쓰기정책 설정값: 미구현.
- `student_notes` 등 일부 staff action의 RLS 정책 본문: 본 조사 범위 밖 — 확인 안 됨.
- 다강사·다반·다대다 소속의 실데이터: 현재 1반·1:1이라 운영 검증 안 됨(스키마만 지원).
- 공용 스토리지 업로드 추상 헬퍼: 미구현(feature별 직접 호출).

## 변경 0 확인
본 조사는 **읽기 전용 SQL(SELECT) + 코드/타입 열람**만 수행했고 **코드·DB·스토리지를 일절 변경하지 않았다.** 산출물은 본 문서 1건뿐.
