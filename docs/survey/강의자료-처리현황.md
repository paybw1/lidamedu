# 강의자료(lecture_resources) 저장·연결·처리 현황 조사

> **목적**: 강의자료 재설계를 위한 사실 정리. **코드·DB 변경 없음(읽기 전용 조사)**.
> **조사일**: 2026-06-13 · **대상**: 운영 DB `mcgdoplo` (`.env` supabase-js / Management API) + 코드베이스.
> **표기 규칙**: 확인된 사실만 기재. 불명 = "확인 안 됨", 없음 = "미구현".

---

## 0. 한 줄 요약

현재 강의자료는 **PPTX 강의노트를 슬라이드 1장 = PDF 1장으로 쪼갠 조각**(활성 781건)이며,
조문·판례 연결은 **오프라인 import 스크립트가 슬라이드의 "제목 placeholder(조문)·본문(사건번호)"를
정규식으로 뽑아 DB와 정확일치(exact match)시켜 만든 것**이다. 런타임(앱 업로드)에서 자동 매칭하는
기능은 **미구현**이고, 수동 업로드는 운영자가 대상을 직접 고른다. **원본 통짜 파일은 시스템(DB/스토리지)에
없고**, 조각만 버킷에 있다(원본 PPTX/PDF는 운영자 로컬 `source/`에만 존재).

## 1. 저장 구조 — 무엇이 어떻게 들어 있나

### 1.1 테이블

| 테이블 | 역할 | 비고 |
|---|---|---|
| `lecture_resources` | **강의자료 본체** (조각 메타 + 연결) | 핵심 |
| `lecture_slide_candidates` | 자동매칭 실패 case-study 슬라이드의 **운영자 검토 큐** | §3 |
| `lecture_views` | **커리큘럼 강의영상** 시청 진행률 | 강의자료(PDF)와 무관 — `curriculum_items.kind='lecture'` 영상용. 혼동 주의 |

### 1.2 `lecture_resources` 컬럼 (실측)

| 컬럼 | 타입 | 의미 |
|---|---|---|
| `resource_id` | uuid PK | |
| `target_type` | enum `resource_target_type` | 연결 대상 종류 (polymorphic) |
| `target_id` | uuid | 연결 대상 id (FK 없음 — polymorphic) |
| `kind` | enum `resource_kind` | 자료 종류 |
| `title` | text | 표시 제목 (예: "제29조 신규성 (2005후3017)") |
| `url` | text null | 외부 영상 URL (현재 **전부 NULL**) |
| `pdf_url` | text null | **스토리지 객체 키** (예: `patent-lecture/ch2-s015.pdf`). 현재 전건 채워짐 |
| `duration_sec` | int null | 영상 길이 (PDF엔 미사용) |
| `ord` | int | 정렬 순서 |
| `source_pdf_id` | uuid null | **원본 묶음 식별자** — FK 아님. 책 이름 sha1 → 결정적 UUID(v5 유사) |
| `source_page_start` / `source_page_end` | int null | 원본에서의 페이지(슬라이드) 범위 |
| `created_by` | uuid null | FK → `profiles` (유일한 FK) |
| `created_at` / `updated_at` / `deleted_at` | timestamptz | soft-delete(`deleted_at`) 사용 |

- **FK는 `created_by → profiles` 단 1개.** `target_id`, `source_pdf_id`는 FK가 아니다(자유 uuid).
  → `source_pdf_id`는 **원본 파일을 가리키는 참조가 아니라 "같은 배치" 그룹핑 키**일 뿐이다.
  원본 메타를 담는 테이블은 **미구현**.

### 1.3 현재 들어있는 자료의 형태 (실측 카운트)

- 전체 1,181건 / **활성 781건** / soft-deleted 400건.
- 활성 781 = `kind=lecture_note` 전부. **target_type별: article 562 · case 219.** (그 외 kind/target은 0)
- **조각 단위 = 거의 1페이지**: page-range 있는 1,091건 중 `start==end`(1페이지) **996건(≈91%)**,
  2페이지 32건, 그 이상(범위 묶음) ≈63건. → "1슬라이드 = 1조각"이 원칙, 일부 범위 조각 존재.
- 활성 자료의 출처 폴더 분포:

  | 폴더(pdf_url prefix) | source_pdf_id | 활성 | 비고 |
  |---|---|---|---|
  | `patent-lecture/` | `d568c53f…` | **677** (art 477 + case 200) | 현재 주력 배치(7개 PPTX 통합) |
  | `manual/` | NULL | **86** (art 85 + case 1) | 운영자 수동 업로드 |
  | `patent-lecture-ch6/` | `b40ea9d5…` | 9 (case) | candidate 검토로 연결된 case-study |
  | `patent-lecture-ch2/` | `3888ce6e…` | 6 (case) | 〃 |
  | `patent-lecture-ch3/` | `d0e3a76b…` | 3 (case) | 〃 |
  | `lidam-patent-v10/`, `ch1/4/5/7` | (여러) | 0 (전부 deleted) | **폐기된 이전 세대**(아래) |

- **이력(중요)**: 강의자료는 여러 번 재적재됐다.
  - 1세대: 제10판 **PDF 책**을 페이지범위로 분할(`lidam-patent-v10/pNNNN-MMMM.pdf`) → 현재 **전부 삭제(폐기)**.
  - 2세대: PPTX를 **편(ch1~ch7)별**로 import(`import-pptx-lecture/case-study`) → 대부분 삭제, candidate 연결분만 일부 활성.
  - 3세대(현재): 7개 PPTX를 **하나의 배치로 통합** import(`import-all`/`import-case-notes`, 폴더 `patent-lecture/`) → 677건 활성.
  - 적재 방식이 "전량 soft-delete 후 재insert(`--apply`)"라 **재실행 가능**.

### 1.4 원본 전체 파일 — 시스템에 있나?

- **DB·스토리지에는 원본 통짜 파일이 없다.** 버킷에는 조각만 있다.
- 원본(7개 PPTX `1. 총칙…~7. PCT…`, 제10판 PDF)은 **운영자 로컬 `source/특허법 강의노트/`** 에만 존재.
  (이 디렉터리는 `.gitignore` 처리됨 — 251MB PDF는 GitHub 100MB 제한으로 제외. git/스토리지 어디에도 없음.)
- → **재설계가 "전체 적재"를 전제한다면, 원본은 로컬에서 다시 올려야 한다(시스템 보관본 없음).**

### 1.5 스토리지 위치·접근

- 버킷 **`lecture-notes`** (private). 객체 890개, 합계 ≈334MB, 개별 최대 4.2MB(범위 조각), 평균 ≈375KB.
- 객체 키 규칙: `patent-lecture/chN-sNNN.pdf`, `patent-lecture-ch2/cs_sNNNN.pdf`, `manual/<uuid>.pdf` 등.
- 접근: **signed URL 5분**(`getLectureResourceSignedUrl`, `app/features/lectures/queries.server.ts:314`).
  학생 클릭 시마다 재발급. RLS로 read 허용(authenticated), 쓰기는 staff.
- 버킷 객체(890) > 활성 자료(781): **버킷에 고아 조각 ≈100여 개**(삭제된 행이 가리키던 조각 + v10 조각)가 남아있음.

## 2. 조문·판례 연결 — 어떻게 연결돼 있나

### 2.1 연결 방식·단위

- **Polymorphic**: `lecture_resources.target_type` + `target_id`. (article→`articles.article_id`, case→`cases.case_id`)
  전용 링크 테이블 없음. FK 없음(코드/스토리지 레벨에서만 정합 보장).
- **연결 단위 = (대상 1 ↔ 조각 1) 한 행.** 다만 **같은 조각(pdf_url)이 여러 행으로 재사용**된다:
  - 한 슬라이드가 조문 + 그 슬라이드가 인용한 판례에 동시에 걸리면 → 같은 `pdf_url`로 **article 행 1 + case 행 N**.
  - `import-case-notes.mjs`는 조문 note의 `pdf_url`·`title`을 **그대로 복사**해 case 행을 만든다(완전 동일 PDF).
  - 즉 실질 **N:N** (조문 1 → 조각 多, 조각 1 → 대상 多), 각 (대상,조각) 쌍이 1행으로 물질화.

### 2.2 연결 건수 (활성)

- article 연결 **562** (스크립트 477 + 수동 85)
- case 연결 **219** (스크립트 200 + candidate검토 18 + 수동 1)

### 2.3 누가/어떻게 만들었나 (코드로 확인)

| 경로 | 코드 | 연결 주체 | 자동/수동 |
|---|---|---|---|
| 조문 일괄 | `scripts/lecture-notes/import-all.mjs` | 스크립트(운영자가 `--apply` 실행) | **자동**(빌드타임) |
| 판례 일괄 | `scripts/lecture-notes/import-case-notes.mjs` | 〃 | **자동**(빌드타임) |
| 판례 잔여 | `/admin/case-study-review` → `linkCandidateToCase` | 운영자 클릭 | 자동제안 + **수동확정** |
| 수동 업로드 | `app/features/lectures/api/lecture-resource.tsx` (intent=create) | 운영자 | **수동**(대상 직접 선택) |

## 3. 자동 매칭 — 실제로 도는 기능인가, 가능성인가 ★핵심

### 결론: **"자동 매칭"은 실재한다. 단, (a) 런타임이 아니라 오프라인 import 스크립트이고,
### (b) 자유 텍스트 인식이 아니라 PPTX의 구조화 필드(제목 placeholder)·본문 정규식 → DB 정확일치다.**

### 3.1 텍스트 추출 코드 — 있다 (PPTX XML에서)

- 위치: `import-all.mjs`, `import-case-notes.mjs`, `split-pptx.mjs`, `extract-slide-map.mjs` (+ `scripts/import-pptx-*.mjs`).
- 무엇을: PPTX zip 내부 `ppt/slides/slideN.xml`의 `<a:t>` 텍스트를 placeholder 종류별로 추출.
  - `title`/`ctrTitle` placeholder → **조문**(`jomun`)
  - `body` placeholder → 제목(`jemok`)
  - `sldNum` → 페이지번호 (변환 전 제거)
  - 전체 텍스트 → 사건번호 후보

### 3.2 조문·판례 표시 인식 → 자동 연결 로직 — 있다 (정확일치)

- **조문(article)**: `import-all.mjs`
  - `ART_NUM_RE = /제\s*(\d+)\s*조(?:\s*의\s*(\d+))?/` 를 **제목 placeholder**에 적용 → `articleNumber`(예: `29`, `29의2`).
  - `articles.article_number`와 **정확일치**(`artMap.get(articleNumber)`)해 `article_id` 확정 → insert.
  - 미일치 조문은 **업로드 제외 + 로그**(수동 확인). 범위면 첫 조문.
- **판례(case)**: `import-case-notes.mjs`
  - 슬라이드 본문에 `CASE|선고|판결|대법원|특허법원` 있을 때 `CASE_RE`(법원 사건부호 한정)로 사건번호 추출.
  - **유일 사건번호일 때만** `cases.case_number`와 **정확일치** → 조문 note의 PDF를 그 case에 동일 연결.
- **잔여 case (모호/다건)**: `scripts/export-unmatched-case-study.mjs` → `upload-unmatched-candidates.mjs`
  - 미매칭 슬라이드를 `lecture_slide_candidates`에 적재(`auto_candidates` = 정규식이 뽑은 사건번호 **후보 배열**, `body_preview` = 슬라이드 텍스트).
  - 운영자가 `/admin/case-study-review`에서 후보를 보고 case를 검색·선택 → `linkCandidateToCase`로 확정.
  - 실측: candidate 63건(전부 resolved), auto_candidates 총 11개 → **소규모 보정 경로**.

### 3.3 그래서 현재 조각-조문/판례 연결은 (a)수동 vs (b)자동 어느 쪽?

- **대부분 (b) 자동(빌드타임 스크립트)**:
  - article 562 중 **477** = 스크립트 자동(제목 placeholder 조문번호 정확일치).
  - case 219 중 **200** = 스크립트 자동(본문 사건번호 정확일치).
- **일부 (a) 수동**:
  - 수동 업로드 **86건**(article 85 + case 1): 운영자가 화면에서 대상 직접 선택, 추출·매칭 없음.
  - candidate 확정 **18건**: 자동제안 + 운영자 확정.

### 3.4 "런타임 자동 매칭"은? — **미구현**

- 앱에서 파일을 올리면 시스템이 텍스트를 읽어 자동으로 조문/판례에 붙이는 기능은 **없다**.
  업로드 API(`lecture-resource.tsx`)는 **PDF 파일 + 운영자가 고른 target_type/target_id**만 받는다(추출 0).
- 자동 매칭은 전적으로 **오프라인 스크립트(운영자 수동 실행)** 산출물이다.

## 4. 텍스트 추출 가능성 — 표시가 기계로 읽히는가

| 대상 | 텍스트 기계가독 | 근거 |
|---|---|---|
| **원본 PPTX** | **예(확정)** | placeholder `<a:t>`에서 조문/제목/사건번호 추출이 실제로 동작 |
| 조각 PDF (PPTX→LibreOffice 변환) | **확인 안 됨(미실측)** | 변환 특성상 텍스트 레이어 보존이 예상되나, 조각 PDF에서 재추출하는 코드는 없음(추출은 항상 원본 PPTX에서) |
| 1세대 `lidam-patent-v10` PDF 책 | **확인 안 됨** | 해당 분할 스크립트 미확인 · 현재 전부 삭제 |

- **추출 결과 저장 위치**: 일반적으로 **저장 안 함(빌드 시 일회성 사용)**.
  - `lecture_resources`에 **본문 텍스트 컬럼 없음** → 검색 인덱스/전문 텍스트 보관 **미구현**.
  - 유일한 보관: `lecture_slide_candidates.body_preview`(검토용 63건) · `title`에 조문·사건번호 흔적.
- 사용자가 말한 "텍스트 추출이 된다"는 **원본 PPTX 단계의 추출**을 가리킨 것으로 보이며, 사실이다.
  (조각이나 런타임에서 추출·저장되는 것은 아님.)

## 5. 재설계 관점 정리 (조사 기반 판단)

### 5.1 기존 조각 → 원본 통짜로 "합치기" 가능한가?

- **부분 가능하나 권장하지 않음.** 같은 `source_pdf_id` + `source_page_start`로 슬라이드 순서 복원은 가능하지만,
  ① 조각은 **sldNum 제거·LibreOffice 변환을 거친 가공본**이라 원본과 1:1 동일하지 않고,
  ② 페이지번호 placeholder가 빠져 있으며,
  ③ 활성/삭제·다중 배치(폴더)·고아 조각이 섞여 있다.
- **원본은 로컬 `source/`에 그대로 있으므로, "원본을 다시 적재"가 깨끗하고 비용도 낮다.** (재설계 전제와 일치)

### 5.2 조문·판례 → "전체 자료의 해당 위치" 링크를 자동 생성 가능한 상태인가?

- **예, 핵심 부품이 이미 있다.** 텍스트 추출(PPTX placeholder) + 표시 인식(조문번호·사건번호 정규식) +
  DB 정확일치 + 페이지 메타(`source_page_start/end`)가 동작 중.
- 즉 "전체 PDF/PPTX 1건을 올리고, 조문이 나오는 페이지마다 `(target, source_pdf_id, page)` 링크를 자동 생성"은
  **현재 로직 재사용으로 구현 가능**. 단 다음이 전제:
  - 조문이 **제목 placeholder에 규격대로** 들어가 있어야 한다(자유 본문 인식이 아님 → 비정형 자료엔 약함).
  - 매칭은 **정확일치**라 표기 흔들림(띄어쓰기·"의N"·구법)·DB 미적재 조문은 누락된다.

### 5.3 자료 갱신 시 자동 재매핑(페이지 밀림에 안 흔들림) — 현재/추가 필요분

- **현재**: 갱신 = "전량 soft-delete 후 재import"(`--apply`). 페이지가 밀려도 **매번 placeholder를 다시 읽어
  재매칭**하므로 결과적으로 밀림에 강하다. 단, **기존 행을 보존·정합 갱신하는 증분(diff) 방식은 미구현**
  (학생 메모/즐겨찾기가 자료에 안 붙어 있어 현재는 통삭제가 안전하지만, 향후 자료에 사용자 데이터가 붙으면 위험).
- **추가 필요**: ① 슬라이드의 **안정적 식별자**(현재는 "배치+페이지번호"라 재정렬에 약함 — 내용 해시/슬라이드 GUID 권장),
  ② 원본 보관(통짜 파일을 스토리지에 저장) + 원본↔조각 메타 테이블(현 `source_pdf_id`는 FK 없는 키일 뿐),
  ③ 증분 재매핑(삭제 대신 갱신).

### 5.4 기존 조각-조문 연결을 자동 매핑 "검증 기준"으로 쓸 수 있나?

- **예.** 현재 활성 477(article)/200(case)는 자동 산출물이고 운영 노출 중이라,
  새 자동 매핑 결과와 `(target_id, source_page_start)` 또는 `(article_number, 사건번호)` 기준으로 **대조 가능**.
  - 단 수동분(86) + candidate분(18)은 자동이 아니므로 **검증셋에서 분리**해야 한다(혼입 주의).
  - `source_pdf_id`로 "스크립트 자동분 vs 수동분(NULL)"을 구분할 수 있다(자동분은 결정적 UUID, 수동은 NULL).

## 부록 B. enum 정의 vs 실사용

- `resource_kind` = {`lecture_note`✅, `lecture_video`❌, `reference`❌, `answer_video`❌} — **lecture_note만 사용**.

## 부록 C. 미구현/확인 안 됨 명세

- **미구현**: 원본 통짜 파일 보관(테이블·스토리지), 원본↔조각 FK, 본문 텍스트 인덱싱/검색,
  런타임 업로드 자동매칭, 증분(diff) 재매핑, 슬라이드 안정 식별자.
- **확인 안 됨**: 조각 PDF 자체의 텍스트 레이어 유무(미실측), 1세대 v10 PDF의 분할 출처·텍스트 여부,
  버킷 고아 조각(≈100여) 정확 목록.
